# OQ 卡撰寫規範（open-question 層）

> 三層結構：動筆從 [[範本 - OQ]]（骨架）複製起手；合規樣貌對照 [[範例 - OQ]]（示範）；共用治理（撰寫流程／停下鐵則／撰寫紀律／修改既有卡原則）見 [[卡片撰寫共用規範]]——**本卡只寫 OQ 單元的特定標準**。
> 分工：本卡管「一張 OQ 卡長什麼樣」；`oq-manage` skill（`.claude/skills/oq-manage/SKILL.md`）管「OQ 怎麼流動」（五 mode 操作、去重、封存移檔、audience 判定、Notion 推送）；frontmatter 欄位定義與值域正本在 [[wiki-schema]] § 四。同一條規則只在一處宣告。
> 本卡 type 為 meta，不屬平層 open 佇列（豁免「平層只放 status=open」語意鐵則，比照範例卡，見 [[卡片撰寫共用規範]] § 一 治理鐵則 4）。

---

## 〇、OQ 卡是什麼（先懂定位再動筆）

**OQ 卡是待裁決佇列的單位**——商業決策當下無法定案、或為避免對話過大而先記錄的問題，作為實作前要釐清的細節載體。平層數量＝真實的待辦壓力，所以每張卡必須是「一個可獨立拍板的問題」，拍板後決議寫回卡、封存出平層。

**它不是知識的家**：拍板後的知識歸正本卡（03／04／05／06），OQ 只留裁決紀錄與脈絡；未消化的觀察素材歸 `raw/`；已定案的決策直接寫正本卡＋log，不經 OQ。

**北極星與已知陷阱**：一張卡＝一個裁決為目標、佇列可信為原則。最常見的失守——一張卡同時講兩個範圍（兩個範圍各自演化後互相矛盾，讀者無法判斷狀況）；引用他卡時複述他卡的問題內容（他卡更新後本卡變誤導）；決議段在拍板前就預寫（讀者誤以為已定案）。

## 一、判斷表（該不該開 OQ 卡）

| 情況 | 開卡？ | 去處 |
|------|--------|------|
| 設計討論出現當下無法拍板的問題 | 開 | `oq-manage` mode B（含去重） |
| 兩張正本卡（或卡與 spec）互相矛盾 | 開 | 矛盾呈報卡：並列兩方出處，不自行調和 |
| 問題含多個可獨立拍板的子題 | 拆成多張 | 每張一議題，互引＋分界句（§ 三） |
| 已拍板的決策要記錄 | 不開 | 直接寫正本卡＋wiki/log.md |
| 術語定義新增或更新 | 不開 | 對應術語表 |
| 一般討論備忘、未消化觀察 | 不開 | `vault-ingest`（raw 層） |
| 實作任務追蹤 | 不開 | OpenSpec change tasks |

## 二、前提確認（MUST 全部已確認才能動筆）

| # | 前提 | 缺了怎麼辦 |
|---|------|-----------|
| 1 | 問題能寫成**單一可回答問句** | 寫不成＝議題未收斂，回頭拆（§ 六停下） |
| 2 | 影響範圍列得出來（涉及哪些卡／流程／spec） | 列不出來＝問題還在素材階段，先走 raw |
| 3 | 去重已做（平層＋封存都搜過，流程見 skill mode B） | 命中 open 卡→評估擴充；命中封存卡→引舊決議問 Miles |
| 4 | audience 已判（判斷問句與值域見 [[wiki-schema]] § 四；操作時機見 skill） | 不判就預設 internal 屬失守 |
| 5 | 前綴有歸屬（enum 正本見 [[wiki-schema]] § 七） | 無可歸屬→先增列 enum 再開卡 |

## 三、撰寫規則

### 3.1 一卡一議題（鐵則）

一張 OQ 只問**一個可獨立拍板的問題**。判準：**一個決議段能否結案整張卡**——若拍板 X 之後卡上還剩沒被這次拍板覆蓋的待解答項，就是兩張卡。

多議題徵兆（出現即拆卡）：

- 待解答段有**互不相依**的多個問句（拍板甲不影響乙的答案）
- 問題描述同時講兩個範圍（如同一卡既問狀態列舉又問角色權責）
- 候選方案的 A／B 各自又分岔出獨立子選擇

例外：**互相依存**的問句（乙的答案由甲推導）屬同一裁決，可同卡多問句。

### 3.2 範圍宣告

問題描述段 MUST 明確寫出本卡涉及的範圍：影響哪些卡（逐卡 `[[卡名]]`）、哪段流程或 spec。與其他 OQ 範圍相鄰或重疊時，MUST 互引並各寫一句分界——「本卡管 X；Y 見 `[[某OQ完整檔名]]`」。

### 3.3 互引不複述

內文引用其他 OQ 時，**只寫連結＋一句分界**，禁止複述他卡的問題描述、候選方案或決議內容——他卡更新後本卡即成誤導源。需要他卡脈絡時讓讀者點過去，不搬過來。

### 3.4 檔名與序號

- 檔名 `<前綴>-<NNN>-<問題簡述>.md`：簡述繁中名詞、不含問號、不重複序號。
- 前綴 enum 正本 [[wiki-schema]] § 七（議題英文縮寫；無可歸屬先增列再開卡）。
- 序號取該前綴現有最大值＋1，**平層與 `_archives/` 一起算，永不重用**。

### 3.5 frontmatter

欄位定義與值域正本在 [[wiki-schema]] § 四（status 嚴格三值禁行內註解、audience 判斷問句、`related-oq`／`related-vault` 一律完整檔名禁別名禁短名、`expected-resolution-at` 一律選填、開卡不代填時點）。本卡不複寫，動筆時照骨架填、對 schema 查。

### 3.6 段落紀律

| 段 | 規則 |
|----|------|
| 問題描述 | 現況怎麼寫、缺什麼或與什麼衝突、為什麼不拍板走不下去；**矛盾型並列兩方出處**，註明「既有正本矛盾」或「本次討論產生」；含範圍宣告（§ 3.2） |
| 待解答 | 可回答問句的 checkbox；拍板後打勾並同行接結論一句或「見決議」 |
| 候選方案 | **兩案以上才留**（僅一條路整段刪）；每案附代價或風險；後接「不受影響項」（縮小裁決壓力）與「裁決後要同步的位置」（逐處） |
| 部分拍板 | 已定部分＋拍板日期與拍板者；其餘待裁決項；status 維持 open |
| 決議 | **未拍板前整段不留**；拍板時寫結論＋理由（採納案為何站得住、否決案哪裡不成立）＋拍板日期與拍板者＋落地去處（逐卡 `[[卡名]]`，無需落地則寫明） |

## 四、修改既有卡前的檢查

1. **擴充 vs 拆卡**：要加進 open 卡的新內容是否與原議題同屬一個裁決（同一決議段能結案）？是→擴充；否→開新卡並互引。
2. **封存卡只增不改**：決議是歷史紀錄；發現決議錯了不改舊卡，開新 OQ 引用舊卡。新 OQ 的結論推翻舊封存卡的結論時，MUST 雙向留痕——新卡背景段回指舊卡；舊封存卡檔尾**追加**一行「本卡結論已由 [[<新卡>]] 取代（YYYY-MM-DD）」（追加屬「增」、不屬「改」，原文一字不動）。理由：事實只從正本卡讀，但讀者可能不經正本卡、直接搜尋開到舊封存卡，沒有取代註記就會拿到過時結論而不自知。
3. **範圍變動要同步互引**：本卡範圍擴縮時，檢查互引卡的分界句是否仍成立，不成立則兩邊同步改。

## 五、邊際情境

| 情境 | 處理 |
|------|------|
| 部分拍板 | 寫「部分拍板」段，status 維持 open，不提前封存 |
| 議題跨多領域 | 前綴取主要歸屬議題的縮寫，領域 tag 多值標注（判定見 [[business-domain-taxonomy]]） |
| 問題被其他拍板實質取代 | status=cancelled，內文附原因與取代來源，封存 |
| 範圍與既有 OQ 重疊但議題不同 | 兩卡並存，互引＋分界句（§ 3.2） |

## 六、停下條件（OQ 特有；共用四條見 [[卡片撰寫共用規範]] § 三）

1. 待解答寫不成單一可回答問句——議題未收斂，回頭拆解再開卡。
2. 去重命中已拍板的封存卡——引舊決議向 Miles 確認是否真是新問題，不逕自重開。
3. 前綴 enum 無可歸屬——先在 [[wiki-schema]] § 七增列前綴再開卡。

## 七、產出格式

從 [[範本 - OQ]]（骨架）複製起手：frontmatter 樣板＋「問題描述／待解答／候選方案（選用）／部分拍板（選用）／決議（拍板時補）」段落結構與填寫提示以骨架為正本，本卡不複寫；各段規則見 § 3.6。

**卡內的 `#` 標題**：格式為 `# <序號> <完整問題描述>`，序號與檔名一致但不含連字號。例：檔名 `ORD-042-議價照收降價的帳務落點`，標題 `# ORD-042 議價照收（品質瑕疵降價）的帳務落點`。檔名受長度與字元限制只能寫簡述，標題寫得完整才指認得出問題本身，兩者不重複（L1-1）。OQ 常在對話與 Notion 之間搬運，離開檔案系統後靠這行認人。

## 八、不收清單

| 不收 | 去處 |
|------|------|
| 已拍板決策的記錄 | 正本卡＋wiki/log.md |
| 未消化的觀察素材 | `raw/`（vault-ingest） |
| 術語定義 | 對應術語表 |
| 實作任務追蹤 | OpenSpec change tasks |
| 他卡範圍的問題複述 | 互引＋分界句（§ 3.3） |
| 系統性議題與下一步建議 | `vault-audit` 報告的建議段（知識庫工作流待辦歸 `memory/` project 卡） |

## 九、稽核維度（goal-driven；稽核者逐項勾）

> 一張 OQ 卡的「完成」＝ **L1 共用維度**（正本見 [[卡片撰寫共用規範]] § 四之二，本節不複寫）**＋下列 L2 OQ 單元維度**全部通過，以 [[範例 - OQ]] 為通過樣本對照。執行者／稽核者分離原則見 [[卡片撰寫共用規範]] § 二。

| # | 維度 | 通過標準 |
|---|------|---------|
| 1 | **一卡一議題** | 一個決議段能結案整張卡；多問句時互相依存、屬同一裁決 |
| 2 | **範圍宣告** | 問題描述明列涉及卡與流程；與相鄰 OQ 有互引＋分界句 |
| 3 | **互引不複述** | 引用他卡處只有連結＋分界，無他卡內容複述 |
| 4 | 檔名與序號 | 前綴命中 enum、序號未重用、簡述繁中名詞無問號 |
| 5 | frontmatter 合規 | status 三值無行內註解；audience 已判；external 有 expected-resolution-at（L1-2 的 OQ 特化） |
| 6 | 段落紀律 | 未拍板無決議段；候選方案兩案以上且附代價；矛盾型並列兩方出處 |
| 7 | 位置正確 | open 在平層；answered／cancelled 已移封存區 |
