# QR-009 需求單狀態轉換的角色把關後端未擋，印務主管可呼叫成交

## 問題描述

[[需求單狀態]] 轉換表寫成交、流失、報價、重新評估、重新啟動由業務觸發，評估完成由業務部門（業務、諮詢）觸發，印務主管只協助成本估算與預計產線（[[QR-010-需求單成本評估的實務分工與系統把關落差]] 決議）。Dev 後端的狀態轉換 API 只驗物件層編輯權限（負責業務、建立者、或持編輯授權者），不看角色；而業務指定評估印務主管時，後端自動授予該主管編輯授權。結果是被指派的印務主管技術上可以呼叫成交、流失等業務動作，業務也可以呼叫評估完成。正式前端無角色把關，Prototype 已於 2026-09-08 依 wiki 隱藏非本角色的按鈕。矛盾來自既有正本（wiki）與已上線程式碼。

不拍板的後果：前端隱藏按鈕只是介面層，API 仍放行；wiki 的「印務主管只估成本不碰報價」與「成交由業務標記」沒有後端強制。

範圍：本卡只管狀態轉換 API 的角色把關。印件欄位的編輯範圍（印務主管只改成本估算與預計產線）屬同一層問題，一併在此卡裁決；業務主管的可見範圍見 [[QR-008-業務主管需求單全公司唯讀可見範圍後端未支援]]。

## 待解答

- [x] 後端狀態轉換要不要加角色維度：評估完成限印務主管角色、其餘轉換限業務／諮詢角色？→ 不加，見決議
- [x] 印務主管的編輯授權要不要限縮到成本估算與預計產線兩欄，還是維持整張需求單可編輯、靠前端隱藏？→ 維持整張可編輯，見決議

## 候選方案

- **A（後端加角色把關）**：轉換 API 依目標狀態檢查角色權限碼，印務主管的自動授權改成「限成本欄」的專用權限；代價是後端權限模型要加一層。
- **B（維持後端現況，只靠前端隱藏）**：不動 API；代價是繞過前端即可越權，wiki 的分工只有介面層保證。

不受影響項：物件層的負責人與分享授權判斷任一方向皆不動。
裁決後要同步的位置：後端轉換 API 與印務主管自動授權；[[需求單狀態]] 轉換表若採 B 要加註「角色分工僅介面層」。

## 決議

採 B 的方向，但前提已改：狀態轉換與印件欄位都不分角色把關，照物件層權限走。後端現況即符合，不用改。

理由：
- 2026-10-13 權責結構重構後，誰能做什麼的正本是活動清單。[[報價評估活動清單]] 寫明評估完成、進入議價、重新評估報價由「業務、諮詢（自己負責）」與「所有角色（被分享（編輯））」執行，不再依角色分工。
- 評估印務主管由系統自動列入分享成員（編輯（代理）層級），所以按得到這些動作是設計本意（G41）。
- 評估印務主管以編輯分享成員身分可改整張需求單（G66 第 65 題，QR-016 同時封存）。
- 否決 A：A 要後端多加一層角色權限，但現行權責正本已不要求角色分工，加了反而與活動清單不一致。
- 本卡提出時「前端依角色隱藏按鈕」的 Prototype 做法，已隨權限修正變更改為依範圍顯示。
