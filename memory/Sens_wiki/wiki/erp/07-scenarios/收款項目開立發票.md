讀完這張卡，你會知道：

- 說出客戶要發票時為什麼一律從某一期收款項目建立（發票金額直接取那一期談定的含稅金額，買受人與品項由訂單帶入，不必到開發票表單從頭再貼一次；開票資訊還沒齊時可先存成草稿，送出前被擋下也有地方停、有原因可看）
- 判斷這段過程從什麼情況啟動：訂單上有一期收款項目還沒有未作廢的發票，客戶需要發票時從該期選「開立發票」，一人一次坐定即可完成；訂單在任何狀態都可以建立與開立
- 走得完開立發票、核對發票種類與品項、視需要先儲存草稿、送出經電子發票加值服務開立
- 處置副流程：由被分享編輯權限的同事或全公司可編輯角色執行、開票資訊已齊直接送出、送出前被系統檢核擋下、開立失敗、送出期間所屬收款項目被取消或刪除、同一期已有未作廢發票、不要這張草稿、客戶指定品名或要看明細、已開立的要作廢重開、客戶指定開立日期或月份、開出後要減額改開折讓
- 說出走完之後這張發票與那一期各停在什麼狀態、哪一條進度線不受開發票影響

## 主流程

具體例子：訂單 ORD-2026-0803 應收總額 13,126（含稅），規劃成第一期 3,938、第二期 9,188。客戶先要第一期的票，先儲存草稿、等客戶給齊統編後送出開立，發票金額（含稅）就是 3,938，銷售額（未稅）3,750 與稅額 188 由系統導出。第二期開完，銷售額 8,750、稅額 438——各期取整的零頭落在稅額，兩張銷售額合計 12,500 與未稅基準 12,501 差的 1 元屬正常零頭；算法與整串驗算見 [[付款發票邏輯#五G、開發票的含稅與未稅兩個目標值]] 與 [[對帳一致性#具體例子]]。

| 步驟 | 活動 | 成立判準 |
|------|------|---------|
| 1 | [[收款項目開立發票活動清單]] ACT-INV-001 先存下開票資訊未齊的發票草稿 | 訂單上有一筆還沒有未作廢發票的收款項目，開發票狀態為「未開立」或「已作廢」（[[收款項目開發票狀態]]）。該期已有草稿時，系統帶入那張草稿的內容；沒有時，系統記下這張發票對應的是哪一期，發票金額、買受人各欄與品項在當下帶入，發票金額（含稅）取該期的預計金額（含稅）為目標值，銷售額（未稅）與稅額由系統導出（兩型目標值與稅額導出方式的正本見 [[付款發票邏輯#五G、開發票的含稅與未稅兩個目標值]]）；買受人各欄由訂單帶入（欄位正本見 [[帳務]]），要改客戶端資料走 [[訂單客戶與聯絡資料維護]]。引用轉換：[[發票狀態]] （建立）→ 草稿；該期開發票狀態維持原值。草稿不列在訂單的發票清單，草稿期間可多次回頭改發票種類、買受人統編與品項，草稿階段不檢核。一期能掛幾張未作廢發票見 [[發票狀態]]；收款項目上只有「開立發票」這一個入口，沒有不對應任何一期的開發票入口 |
| 2 | [[收款項目開立發票活動清單]] ACT-INV-004 開出客戶要的發票 | 依買受人有沒有統編選發票種類（B2B 或 B2C）、核對買受人統編、必要時改品項後送出開立，系統先檢核、再經電子發票加值服務（藍新）完成開立。以草稿內容送出、不重新帶入；含稅目標值取草稿上的發票金額，與該期當下預計金額不一致時只提示、不擋下（規則正本見 [[付款發票邏輯#五G、開發票的含稅與未稅兩個目標值]]）。品項改成多列時各列要在送出當下過電子發票平台的品項欄位與硬檢核這道關卡（品項規則正本見 [[付款發票邏輯#五G、開發票的含稅與未稅兩個目標值]]，平台硬約束見 [[發票法規硬約束-ezPay-MIG#二、發票品項五欄硬約束（核心，影響所有開發票邏輯）]]）；商品單價的未稅與含稅口徑隨買受人身分切換，正本見 [[發票法規硬約束-ezPay-MIG#三、B2B vs B2C 行為差異]]。藍新回傳成功時引用轉換：[[發票狀態]] 草稿 → 開立、[[收款項目開發票狀態]] 未開立 → 已開立；發票計入這張訂單的發票淨額，這一期不再出現開立發票的入口。買受人資訊每張開票時都可改，所以同一張訂單的不同期次可以一張開有統編的 B2B、另一張開無統編的 B2C |

## 副流程

| 分支點 | 條件 | 改走活動 | 成立判準 |

| 主流程第 1 步 | 執行者是被分享所屬訂單編輯權限的同事，或是對訂單有全公司範圍的角色 | [[收款項目開立發票活動清單]] ACT-INV-002 先存下開票資訊未齊的發票草稿或 [[收款項目開立發票活動清單]] ACT-INV-003 協助先存下開票資訊未齊的發票草稿；第 2 步改走 [[收款項目開立發票活動清單]] ACT-INV-005 開出客戶要的發票或 [[收款項目開立發票活動清單]] ACT-INV-006 協助開出客戶要的發票 | 自主流程第 1 步起同主流程；接單業務不因此改變 |
| 主流程第 1 步 | 開票資訊已齊，不先存草稿 | [[收款項目開立發票活動清單]] ACT-INV-004 開出客戶要的發票 | 帶入內容同主流程第 1 步，確認後直接送出；藍新回傳成功時引用轉換：[[發票狀態]] （建立）→ 開立、[[收款項目開發票狀態]] 未開立 → 已開立；系統檢核未過時擋下、不建立發票 |
| 主流程第 2 步 | **送出前被系統檢核擋下**：送出當下系統檢核未過（檢核內容見 [[付款發票邏輯#五G、開發票的含稅與未稅兩個目標值]] 與 [[發票法規硬約束-ezPay-MIG]]） | 系統事件：送出前系統檢核未過，擋下並顯示原因 | 不送平台；引用轉換：[[發票狀態]] 草稿 → 草稿，未存過草稿者不建立發票。該期開發票狀態維持原值。依原因修改內容後回主流程第 2 步 |
| 主流程第 2 步 | **開立失敗**：已送出開立，藍新回傳失敗，或逾時沒有回應；逾時時平台上可能已經開出這張發票（平台面的時點差異見 [[發票法規硬約束-ezPay-MIG#五之二、ERP 發票草稿與平台時點的對應]]） | 外部事件：藍新回傳失敗或逾時沒有回應 | 引用轉換：[[發票狀態]] 草稿 → 開立失敗，記下原因，列在訂單的發票清單並顯示原因；該期開發票狀態維持原值。系統內不能再改、再送，也不能在該期另開一張；以既有溝通管道通知後端人員，系統不另發通知。處置由後端人員在系統外執行：<br>1. 平台上沒有開出：引用轉換 [[發票狀態]] 開立失敗 →（記錄消失），之後回主流程第 1 步重新開立發票。<br>2. 平台上已經開出：引用轉換 [[發票狀態]] 開立失敗 → 開立，該期開發票狀態轉「已開立」，回收斂狀態。<br>隔日上傳財政部失敗不算開立失敗：發票維持「開立」，處置見 [[發票法規硬約束-ezPay-MIG]]。處置後系統內這一期的發票與平台上的開立結果一致，這一期只有一張未作廢發票 |
| 主流程第 2 步 | **送出開立期間所屬收款項目被取消或刪除** | 系統事件：寫入當下依既有規則判定 | 系統不另設機制，沿用兩條既有規則：已開立發票的期次要取消或刪除得先作廢那張發票（[[付款發票邏輯#五F、收款項目取消 / 刪除 / 金額調整（重分配）]]）；一個收款項目同一時間至多一張未作廢發票（[[發票狀態]]）。收款項目先被取消、平台之後才回應成功時，系統內不處置，這張發票不落系統，要到平台後台作廢該張發票（系統外）。發票開立成功後，這一期不會在發票未作廢的情況下被取消或刪除 |
| 主流程第 1 步 | **同一期已有未作廢發票**：該期已有開立或開立失敗的發票，或兩人同時對同一期送出 | 系統事件：寫入當下擋下後到的那一筆，提示重新整理 | 重新整理後該期有草稿時，選「開立發票」即帶入那張草稿；已有開立發票時，要改內容走作廢重開那條副流程；已有開立失敗發票時，等後端人員處置（見開立失敗那條副流程）。這一期始終只有一張未作廢發票（[[發票狀態]]） |
| 主流程第 1 步之後（已存草稿） | **不要這張草稿了** | [[收款項目規劃活動清單]] ACT-BPL-007 收掉不再要收的期次 | 系統不設草稿單獨刪除；引用轉換：[[發票狀態]] 草稿 →（記錄消失）。該期已有收款核銷分配時，依 [[付款發票邏輯#五F、收款項目取消 / 刪除 / 金額調整（重分配）]] 一併解除；需要時再重建一期（[[收款項目規劃]]） |
| 主流程第 2 步 | **客戶指定品名或要看明細**：客戶要求發票品名寫成「印刷品一批」這類統稱，或反過來要求把每件印件一列一項攤開 | [[收款項目開立發票活動清單]] ACT-INV-004 開出客戶要的發票 | 送出開立前直接改品項——改商品名稱、加列、把真實數量與整數單價填進去都可以，改列只是把同一筆錢攤開、不改發票金額（正本見 [[付款發票邏輯#五G、開發票的含稅與未稅兩個目標值]]）；改完仍過品項的硬檢核關卡，發票金額（含稅）不變。發票已經開出去之後客戶才提的，走作廢重開那條副流程 |
| 主流程第 2 步之後 | **已開立的發票要改內容（作廢重開）**：買受人統編或抬頭打錯、金額報錯、品名要改、客戶要換開立月份、規格調整後要重開、自家誤開、部分退款後要重開成正確金額 | [[收款項目開立發票活動清單]] ACT-INV-007 作廢開錯的發票，再以 [[收款項目開立發票活動清單]] ACT-INV-004 開出客戶要的發票 | 作廢原因必填；引用轉換：[[發票狀態]] 開立 → 作廢、[[收款項目開發票狀態]] 已開立 → 已作廢，重開後 [[收款項目開發票狀態]] 已作廢 → 已開立。作廢時限與字軌處理見 [[發票法規硬約束-ezPay-MIG#四、發票異動 API（作廢 / 折讓 / 確認 / 作廢折讓 / 字軌 / 金額 sign）]]；作廢張退出對帳、重開張照同一條算法算且不牽動其他張，見 [[付款發票邏輯#五G、開發票的含稅與未稅兩個目標值]] |
| 主流程第 2 步之後（作廢時） | **平台回應不可作廢**：發票已跨報稅期，不必自行判斷跨不跨期 | 外部事件：平台回應不可作廢；改走 [[收款項目開立發票活動清單]] ACT-INV-010 沖減已開發票的部分金額 | 系統引導改開折讓單，不另設「換開」捷徑；原發票維持「開立」，減額改由折讓單承接 |
| 主流程第 1 步 | **客戶指定開立日期或月份**：客戶指定發票要開在某個日期，或要求分兩期各開在不同月份 | [[收款項目規劃活動清單]] ACT-BPL-004 調整期次的金額、預計日期與款項方式，到日再以 [[收款項目開立發票活動清單]] ACT-INV-004 開出客戶要的發票 | 發票還沒開立時把該期的預計開發票日填成客戶指定的日期（可先存好草稿）；發票已經開立之後客戶才提出改月份的，改走作廢重開那條副流程。發票的開立時間就是實際送出的那一刻，系統不會預先把票開出去 |
| 主流程第 2 步之後 | **開出後要減額但不作廢（折讓）**：發票已跨報稅期不可作廢，或客戶不需要作廢、只要沖掉一部分金額——取消訂單、瑕疵退一部分數量、規格調整要重開、多收的運費要退（宅配改自取）都算這一型 | [[收款項目開立發票活動清單]] ACT-INV-010 沖減已開發票的部分金額 | 折讓金額以含稅整數填寫、直接扣抵這張發票的餘額，並須過剩餘可折讓額度這道關卡（正本見 [[付款發票邏輯#五C、發票異動三情境（作廢、折讓、改買受人）]]）；引用轉換：[[折讓單狀態]] （建立）→ 已確認。折讓確認後這張訂單的發票淨額扣掉折讓金額，發票本身仍停在「開立」；帳對不對此後看含稅的三方對帳，未稅面不再逐元追平 |

## 收斂狀態

發票開立成功後，這張發票處於「開立」狀態（[[發票狀態]]）、正式生效並計入這張訂單的發票淨額；對應的那一期開發票狀態轉為「已開立」（[[收款項目開發票狀態]]），這一期不再出現開立發票的入口。停在「草稿」或「開立失敗」的發票不計入發票淨額，該期開發票狀態維持原值。客戶取得發票後得以向其公司請款。那一期的收款狀態不受開發票影響、維持原值——兩條進度線各走各的，先開後收與先收後開都接得住。每張發票的銷售額由自己的期次含稅金額反推、取整零頭落在稅額，這張訂單已開立且未作廢的發票銷售額（未稅）合計與未稅基準差在零頭範圍屬正常；目標值怎麼算，正本見 [[付款發票邏輯#五G、開發票的含稅與未稅兩個目標值]]。含稅面則一律進入三方對帳比對。

## 範圍外

- 收款項目怎麼規劃、各期金額與時點怎麼定、拆期怎麼拆 → [[收款項目規劃]]；本卡的前提就是已有規劃好的期次可開。
- 發票狀態怎麼轉（含草稿、開立失敗、一期一張的寫入檢查）、作廢與折讓的轉換條件、字軌與配號機制、上傳財政部的時程 → [[發票狀態]] 與 [[發票法規硬約束-ezPay-MIG]]；本卡只引用狀態名與規則。
- 折讓單自身的建立、確認與作廢流程 → [[折讓單狀態]]。
- 退款與補收金額異動本身，含預開發票後實作金額低於預估要退的那一筆 → [[訂單異動流程]] 與 [[訂單異動規則]]；本卡只到把發票開出來或折讓掉為止。
- 收款登錄與核銷分配 → [[收款核銷分配]]；開發票不等於收到錢。
- 多期合併開一張發票（合期）：不支援——一個收款項目同一時間至多一張未作廢發票，客戶要求合開時先把多期併成一期再開（決議見 [[BI-007-合期開一張發票是否支援]]，已封存）。
- 無對應收款項目的臨時或雜項發票：不支援——開發票一律從收款項目進（決議見 [[BI-018-手動開發票是否一律需關聯收款項目]]，已封存）。
- 已作廢的發票被客戶拿去申報，須聯繫國稅局處理：屬人工處理，系統只留下作廢原因供追溯，本卡不涵蓋後續交涉。
- 客戶以紅利點數付款而誤開的發票：紅利金額現階段不參與任何金額計算（見 [[訂單#金額組成]]），點數怎麼折抵屬 EC 整合議題，不在本卡。
- 預開發票之後重新評估報價、重出並重簽報價單 → 屬需求單議價階段（範疇界定見 [[付款發票邏輯#八、不做系統化的範疇外]]）。
- 開立失敗的系統外處置作法（後端人員怎麼查平台後台、怎麼刪除紀錄或補登）：屬系統外作業，本卡只寫處置後的兩種結果。
- 誰在什麼範圍能做各活動 → [[收款項目開立發票活動清單]]、[[收款項目規劃活動清單]]。
- 開發票畫面怎麼呈現來源期次、電子發票加值服務的串接細節（加密、上傳排程、平台內部運作）→ 屬實作規格與外部平台，系統只呼叫其開立、作廢與折讓行為。
