# 卡片撰寫共用規範

> 分工：[[index]] § Wiki 憲章管「BRD 是什麼、收什麼」（why）；`.claude/rules/sens-wiki.md` 管操作與格式（frontmatter、連結、命名、log）；**本卡管跨單元共用的撰寫治理**（三層結構、流程、停下鐵則、紀律）；各單元規範（`_template-*`）只管該單元特定標準（定位、判斷表、產出格式、稽核維度）。同一條規則只在一處宣告。

## 一、三層結構（骨架／規範／範例）

每個會產「新卡」的單元，撰寫依據拆三層：

| 層 | 位置與命名 | 職責 | 誰用 |
|----|-----------|------|------|
| **骨架** | `wiki/範本/範本 - <單元名>` | 可直接插入（Obsidian「Insert template」）或複製起手的填空結構：frontmatter 樣板＋段落標題＋每段一行填寫提示 | 人與 AI 寫新卡時的起手稿 |
| **規範** | 各單元資料夾 `_template-<type>.md` | 該單元的規則正本：定位、判斷表、前提確認、撰寫規則、不收清單、稽核維度 | 撰寫時查規則、稽核時勾維度 |
| **範例** | 各單元資料夾 `範例 - <單元名>` | 合規卡在某時點的**凍結快照**，展示規範落地後的完整樣貌 | 撰寫時對照、稽核時當通過樣本 |

**治理鐵則**：

1. 寫新卡 MUST 從骨架複製起手，不從規範散文重組結構。
2. 撰寫方式變更時，骨架＋規範＋範例三層**同一 commit** 更新，不允許只改其一。
3. 範例卡是凍結快照、**不是所屬實體的正本**；它只在撰寫方式變化時更新，frontmatter 的 `synced-with-template` 記最後同步日，該日期不得早於對應規範檔的最後實質修改（稽核勾稽點）。
4. 範例卡與骨架不算所屬目錄的內容成員：不進 Obsidian 搜尋與 graph（`userIgnoreFilters` 排除）、豁免孤島與 frontmatter 完整性 lint、不受目錄語意鐵則約束（如 `08-open-questions/` 平層「只放 status=open」不適用於範例卡）。
5. 規範中的正面例子一律指向範例卡，**禁止指向會持續演化的實際卡**——實際卡因業務原因變動，會靜默推翻規範讚許的寫法。

**適用範圍（已接線單元）**：實體（entity）。其餘單元（角色／商業邏輯／狀態機／業務情境／營運原則／OQ／Insight／Raw 素材）依實體組驗證結果逐一接線。

## 二、撰寫流程（六步，所有單元共用）

```
辨識 → 歸位 → 確認前提 → 撰寫 → 稽核 → 定案
```

| 步驟 | 做什麼 | 卡住時 |
|------|--------|--------|
| **1. 辨識** | 該不該開卡？依該單元規範的判斷表 | 走不通 → 該單元規範的邊際情境節 |
| **2. 歸位** | 檔名（繁中語意化）＋落點資料夾＋領域 tag | 同上 |
| **3. 確認前提** | 依該單元規範的前提確認表逐項確認 | 任一缺 → 停下問使用者 |
| **4. 撰寫** | 從骨架複製起手，依該單元規範的撰寫規則填入 | 需要假設 → § 三停下鐵則 |
| **5. 稽核** | 依該單元規範的稽核維度逐項勾，以範例卡為通過樣本 | 不通過 → 回 3 或 4 |
| **6. 定案** | commit ＋ 追加 wiki/log.md（逐卡 `[[卡名]]`＋動機） | — |

**執行者／稽核者分離**：撰寫卡的 agent ≠ 稽核的 agent。稽核者拿該單元規範的稽核維度獨立勾，不採信撰寫者的「大致 OK」。

## 三、停下鐵則（共用 error handle，出現任一即停下）

1. **無來源依據**：內容只有推測，沒有訪談、既有介面、拍板來源。
2. **矛盾**：與既有卡、狀態機、規則卡、權責分工矛盾——停下並列出矛盾兩方，開 OQ，不自行調和。
3. **需要假設**：必須假設「應該是這樣」才能繼續。
4. **超出已知**：要描述的內容超出已確認範圍。

處理方式：標記具體問題、附已知事實提問；**禁止**用「一般來說」「通常」填充。改寫舊卡發現的問題，保留舊內容另開 OQ。各單元特有的停下條件（如實體的「欄位拆不出業務／技術」）見該單元規範。

## 四、撰寫紀律（共用五條）

1. **規則回引不複寫**：正本只有一處，其他卡 wiki link 指過去。
2. **禁中英夾雜、禁技術術語當主詞**：技術名僅必要時括號附註。
3. **不確定項開 OQ**（`oq-manage` mode B），不留 inline 標注、不用 callout 釘正文。
4. **檔名即標題；正文零迭代史**：change 歷史屬 wiki/log.md。
5. **不編造**：只收訪談、既有介面、拍板來源，無則停下問。

## 五、修改既有卡原則

結構性改動（新增／移除欄位、狀態、職責、關聯）是**商業決策不是編輯行為**，改之前 MUST 有依據（訪談定案／管理層拍板／OQ 拍板），不因下游實作重構而動。純措辭修正不需依據，但仍須通過語言紀律稽核。各單元特定的修改前檢查表見該單元規範。
