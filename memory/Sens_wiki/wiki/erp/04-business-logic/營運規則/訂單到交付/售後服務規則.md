讀完這張卡，你會知道：

- 說出客戶反映交付有問題時要走的五個步驟與各步由誰負責
- 判斷四種處理方式各自往下接什麼單據
- 分辨哪些錢掛在售後單內、哪些要另開新訂單
- 知道決議補做為什麼不建新印件、補做的量從哪條生產路徑長出來
- 認出哪些狀況不走售後（配送事件、換貨、客戶要改內容）

## 現況

客戶反映交付有問題時，目前靠業務在 Slack 與主管討論決定怎麼處理，沒有結構化的追蹤紀錄。處理結果（退款、重做等）散落在不同系統。

## 規則

客戶反映問題時由業務建立售後服務單，**訂單成立後任何時間都能建**（開一張單本身不動錢也不動生產，客戶什麼時候反映都記得下來），走五步流程（已取消訂單最常見的是取消後退款，見 [[訂單異動流程]]）：

1. **受理**：業務建立售後單，填客訴內容、事件分類（列舉正本見 [[售後服務]] 實體卡「售後類型」欄位，本卡不複寫；揀貨裝箱錯誤等自家出錯的特殊情況歸「其他」，不新增分類）；知道客戶反映的是哪幾件印件就一併記進「相關印件」，不知道也不擋存檔。受理段不設把關，必定存檔成功
2. **討論**：業務與主管在公司通訊軟體討論處理方式（系統外），討論完把連結貼回售後單
3. **決議**：業務填入處理方式並送出。四種處理方式都可選，決議段不依訂單狀態或印件狀態擋；完成前這筆錢也可以不走售後單、改直接增減訂單明細，兩條路怎麼選的判準見 [[訂單異動規則#訂單完成前金額異動兩路並行]]
4. **執行**：依處理方式分流執行（見下方）
5. **結案**：業務確認客戶滿意後手動結案

**四種處理方式**（值域正本為 [[售後服務]] 的「決議處理方式」欄位，本段只寫各方式怎麼走）：

- **不處理**：不建任何下游動作，直接結案（客戶反映但可接受、或雙方談定照常使用）
- **退款**：在售後單內建退款訂單異動——主管核可「能不能退」、業務與客戶談定退多少後執行「確認生效」才認列（兩段式認列的規則正本見 [[訂單異動規則]]），認列後再建退款款項與折讓單（折讓單品項欄位受 ezPay MIG 外部硬約束，見 [[發票法規硬約束-ezPay-MIG]]，欄位缺口追蹤 [[BI-021-折讓單缺ezPay折讓品項五欄]]）
- **補做**：由 [[印務]] 在客戶反映的那件印件上發起補做，於原工單加開補做生產任務（執行規則見下段）。公司吸收費用時不建任何金額單據；要向客戶收費則依這筆錢的性質分流，落點是本張售後單內的補收訂單異動（免審，認列於確認生效，見 [[訂單異動規則#補收免審]]）或另開一張新訂單，分流判準見 [[訂單異動規則#訂單完成後金額異動路徑分流]]，兩者實務上都少見
- **退款 + 補做**：同時走退款與補做路徑

**補做的執行規則**（補做量的載體是補做生產任務，欄位見 [[生產任務]]）：

- **只補做、不另建印件**：客戶反映的原印件維持在「已送達」（[[印件狀態]]），補做活動全在工單層——原印件的稿件與 [[審稿輪次]] 原封不動、審稿零處理，補做的成本自然歸戶到原印件的實際成本帳（品質成本才看得出來花在哪一件貨上）
- **穿越印製終態的工單重開**：售後觸發的補做落在已進印製終態的印件上時，工單重開的例外放行條件見 [[工單狀態]]
- **補做對象與數量在發起補做時才設定**：售後單的決議只記到「補做」這個層級（單頭決議、不逐印件明細決議），要補哪幾件、各補多少由印務發起補做時依客訴描述與業務同客戶確認的結果設定，記在補做生產任務的目標數量上
- **一張售後單只能發起一次補做**：該張售後單被補做生產任務的「補做來源」掛上後即為已承接，不得再發起第二次；還要補就另開一張售後單（與品檢缺口紀錄被承接後即消耗同一個道理）
- 補做走完整生產與出貨鏈（工單異動 → 生管確認 → 報工 → 品檢 → 完工良品數累計 → 可出貨額度長出 → 建出貨單），與大貨等效
- **補做不可同時改稿改規格**：客戶要改內容一律走新訂單流程，不在售後路徑（見 [[AFT-6-補印改稿情境入口設計]]（已封存））

**其他規則**：
- 補做收不收費不設欄位判斷：處理方式只記「補做」，要收費的事實由售後單內那張補收訂單異動或另開的新訂單體現，系統不自動帶建
- 售後單本身無核可關卡（把關擺在下游的訂單異動審核）
- 一張訂單最多一張未結案的售後單（結案後可建新的）
- 售後單不改變訂單狀態：已進終態的訂單不因售後單回退，未進終態的訂單照常自行推進——已送達印件的補做不進訂單完成判定，訂單完成也不中斷正在跑的補做
- 補做量出貨完成不自動結案（需業務確認客戶滿意）

## 為什麼這樣定

售後服務單只是容器與追蹤器，真正的金額動作（退款、補收）沿用既有的訂單異動流程，生產動作沿用既有的補做機制（原工單異動加開補做生產任務）——不為售後另開新流程、也不另建一件印件。這樣維護成本低，且退款的主管審核把關不因售後流程而被繞過。

補做不另建印件，是因為重做的是同一件貨：印件數不膨脹、審稿不必為了形式再跑一輪合格、品質成本歸在原印件才看得出這件貨實際花了多少，訂單的完成判定也不必為補做另設排除條款。

建單不設前提，是因為開一張單本身不會讓任何資源流出，而客戶什麼時候反映問題不受我們的訂單狀態控制；擋在建單那一關只會讓客訴又回到通訊軟體裡，反而查不到。決議選項的把關只看當下做不做得到的事實——貨還在自己手上就補不了做。錢的動作不靠訂單狀態代勞：該不該退錢由業務主管在退款訂單異動那一關核可（見 [[現金流出把關]]）。

討論放在系統外是因為印刷業售後判斷常需看照片和即時溝通，系統只記結果。

## 具體例子

例子 1（退款）：訂單已完成，客戶反映 5000 元瑕疵。業務建售後單（印件瑕疵）→ 與主管討論決議退款 → 建退款訂單異動 -5000 元 → 主管核可 → 業務與客戶談定退 5000 後執行「確認生效」、應收此刻減去 → 建退款款項 + 折讓單 → 確認客戶滿意後結案。

例子 2（免費補做）：訂單 ORD-2026-0470 已完成，客戶反映其中 100 份規格不符要重做，公司吸收費用。業務建售後單並記下相關印件 → 決議「補做」→ 印務在該印件發起補做、原工單加開目標數量 100 份的補做生產任務 → 生產、品檢驗過、可出貨額度長出 100 → 建出貨單送出 → 確認客戶滿意後結案。全程不建訂單異動、不另建印件，應收不變。

例子 3（不處理）：客戶反映輕微色差但可接受。業務建售後單 → 不建任何下游動作 → 直接結案。

## 例外情境

- 完成前的金額增減不一定要走售後單：訂單完成前還有直接增減訂單明細這條路，兩條路怎麼選的判準正本見 [[訂單異動規則#訂單完成前金額異動兩路並行]]；本卡只管走進售後單之後怎麼處理
- **不支援換貨**（收回舊貨再補出新貨）：沒有這個服務，客戶要重做就是補做、要退錢就是退款，收回舊貨不設單據
- **物流問題細分兩類**：配送事件（拒收、超商未取等出貨異常）由 [[出貨單狀態]] 承接——出貨單轉「異常」即自動回補可出貨額度，業務建新出貨單重寄，印件本身沒問題、不開售後單；貨損重製（運送過程破損送到客戶手上、需重製）開售後單處理，售後類型記「物流問題」、決議走補做
- 訂單異動本身的審核規則見 [[訂單異動規則]]，本卡不重述
