# 商業邏輯卡撰寫範本

> `04-business-logic/` 是 BRD 的營運層——記錄「公司怎麼做生意、怎麼決定事情、產業有什麼限制」。
> 核心紀律：**規則只寫一次**（Ronald Ross 原則），其他地方用 `[[wiki link]]` 引用，不複寫。
> 三層結構：動筆從 [[範本 - 服務藍圖]] 或 [[範本 - 商業規則]]（骨架）複製起手；合規樣貌對照 [[範例 - 服務藍圖]]、[[範例 - 商業規則]]（凍結快照）；共用治理（撰寫流程／停下鐵則／撰寫紀律／修改既有卡原則）見 [[卡片撰寫共用規範]]——**本卡只寫商業邏輯單元的特定標準**。

## 一、撰寫流程（所有卡型共用）

六步流程（辨識 → 歸位 → 確認前提 → 撰寫 → 稽核 → 定案）與執行者／稽核者分離原則見 [[卡片撰寫共用規範]] § 二；本單元各步驟對應的節為：辨識與歸位走 § 二分類判斷表、確認前提走 § 三／§ 四、撰寫走 § 八／§ 九產出格式、稽核走 § 十三稽核維度。

## 二、分類判斷表

### 四型（一型一骨架，載體為 `type` ＋ `mutability` 組合）

本層共四型，每型對應一張骨架、一組稽核維度、一個子目錄。四型互斥——同一內容只能落一型。

| 型 | 回答什麼問題 | `type` ＋ `mutability` | 骨架 | 子目錄 |
|----|-------------|----------------------|------|--------|
| **服務藍圖** | 公司提供什麼服務、商業行為的邊界在哪 | `service-blueprint` | [[範本 - 服務藍圖]] | `服務藍圖/` |
| **營運規則** | 公司的商業行為怎麼執行、怎麼分工 | `business-rule` ＋ `internal` | [[範本 - 商業規則]] | `營運規則/` |
| **領域知識** | 這個領域的事實與體系是什麼、系統設計時怎麼處理與看哪些指標 | `business-rule` ＋ `domain` | [[範本 - 領域知識]] | `領域知識/` |
| **外部約束** | 外部要求我們必須怎麼做 | `business-rule` ＋ `external` | [[範本 - 外部約束]] | `外部約束/` |

**服務藍圖的邊界（2026-07-30 修訂）**：服務藍圖圈定「我們做什麼生意」——服務範圍、商業邊界、為什麼這樣圈。**不含角色、不含時序**：誰做哪一段屬營運規則，單一目標的完成過程屬業務情境（`07-scenarios/`）。含角色交棒的端到端流程敘述**不是**服務藍圖。

**領域知識的兩種內容**：產業事實（換任何一家同業都一樣，如令的定義、印刷成本驅動因子）與系統設計方法論（MES／ERP 在這件事上怎麼建模、看哪些指標，如豐田式生產管理對映、生產績效指標）。兩者共同點是公司無權單方變更，且不遵守只是算不出結果或不合行規、不會違法。

### 三種可變性（`mutability`，商業規則專用）

`mutability` 是「誰能改」這一軸，與上表的四型一對一對應——同一分類的兩種問法，判斷時以歸類決策樹為準。

| `mutability` | 型 | 子目錄 | 誰能改 |
|---|---|---|---|
| `external` | 外部約束（法規／第三方規格／第三方介面契約，如金流 webhook 的欄位對應） | `外部約束/` | 只有外部來源變更時（如法規修訂、API 改版） |
| `domain` | 領域知識（產業事實與系統設計方法論） | `領域知識/` | 產業或方法論本身改變時（極少） |
| `internal` | 營運規則（公司決策） | `營運規則/` | 訪談、管理層拍板可改 |

### 歸類決策樹（互斥，依序問，第一個命中即歸）

| 順序 | 問自己 | 是 | 型 | `type` ＋ `mutability` | 子目錄 |
|---|---|---|---|---|---|
| 1 | 這是外部（法規、稅務機關、第三方系統）要求我們必須怎麼做嗎？ | 是 | 外部約束 | `business-rule` ＋ `external` | `外部約束/` |
| 2 | 這在講我們提供什麼服務、生意的邊界在哪嗎？（不含誰做、不含順序） | 是 | 服務藍圖 | `service-blueprint` | `服務藍圖/` |
| 3 | 這條內容公司能自行決定與修改嗎？（訪談或管理層拍板可改） | 是 | 營運規則 | `business-rule` ＋ `internal` | `營運規則/` 再依下表分流 |
| 4 | 剩下的：領域事實或系統設計方法論（公司無權變更，不遵守只是算不出結果或不合行規） | 是 | 領域知識 | `business-rule` ＋ `domain` | `領域知識/` |

**互斥判定句（兩兩比對，寫得出判定句才算歸對）**：

| 比對 | 判定方法 | 例子 |
|------|---------|------|
| 外部約束 vs 營運規則 | 來源在公司內還是公司外？無權變更的是外部約束 | 統一發票的品項與稅別格式（外部約束）vs 我們自己訂的開票時機（營運規則） |
| 外部約束 vs 領域知識 | 不遵守會違法或介接失敗嗎？會＝外部約束 | 發票格式不照做會被國稅局退（外部約束）vs 印刷計價不照令數算只是報價難談（領域知識） |
| 營運規則 vs 領域知識 | 公司可以自己改嗎？能改＝營運規則 | 難易度倍率是我們自己訂的（營運規則）vs 一令＝500 張是紙業慣例（領域知識） |
| 服務藍圖 vs 營運規則 | 講「做什麼生意」還是「怎麼做事」？ | 我們接哪些印件類型與最小量（服務藍圖）vs 生產怎麼分工（營運規則） |
| 服務藍圖 vs 業務情境 | 有沒有單一目標的完成過程與步驟？有＝業務情境 | 服務範圍與商業邊界（服務藍圖）vs 一張訂單怎麼從成立走到出貨（業務情境） |

**判斷不了時**：描述爭議、列出兩型各自的判定句試寫結果，向 Miles 確認後歸類（建卡當下即決，不動用 OQ 流程）。

**存量卡待重分類（2026-07-30 起）**：`服務藍圖/` 現有四張卡（[[生產流程]]、[[線下訂單流程]]、[[諮詢服務流程]]、[[帳務流程]]）為舊定義（含角色與時序的端到端流程）產出，依修訂後定義應重分類至營運規則、真正的服務藍圖卡另寫。重分類完成前這四張卡與 [[範本 - 服務藍圖]] 骨架不一致，屬已知待辦、非新違規。

**營運規則子目錄分流**：

| 問自己 | 是 | 子目錄 |
|--------|---|--------|
| 客戶還沒下單前的事？（諮詢、報價、議價） | 是 | `營運規則/售前/` |
| 下單後到客戶收到商品？（審稿、生產、出貨、售後） | 是 | `營運規則/訂單到交付/` |
| 金流相關？（收付款、開票、對帳、退款） | 是 | `營運規則/帳務/` |

## 三、服務藍圖撰寫規則

**觸發條件**：辨識到一條端到端的業務鏈（客戶有明確目標、有起點和終點）。

### 前提確認（MUST 全部已確認才能開始撰寫）

| 前提 | 確認狀態 |
|------|---------|
| 客戶目標（服務終點）是什麼？ | 已確認 / 待確認 → 停下 |
| 從哪裡開始？（觸發點） | 已確認 / 待確認 → 停下 |
| 經過哪些角色交接？ | 已確認 / 待確認 → 停下（不可假設角色職責） |
| 有哪些決策分叉？每個分叉走向？ | 已確認 / 待確認 → 停下 |
| 目前有什麼痛點？ | 已確認 / 暫無 → 可留空標「待訪談」 |
| 哪些不在範圍內？ | 已確認 / 待確認 → 停下（不可自行假設範圍） |

### 撰寫規則

| 強度 | 規則 |
|------|------|
| MUST | 段名一律依 [[範本 - 服務藍圖]] 骨架、不加卡名前綴（寫「流程階段」，不寫「生產流程階段」）；`###` 階段標題依業務語意自由命名 |
| MUST | 每個階段標註角色與交接對象 |
| MUST | 決策分叉只標方向，細節引用商業規則卡（不複寫規則內容） |
| MUST | 寫「範圍外」段 |
| MUST | 藍圖停在階段層（型）：不寫業務判準、不展開步驟級完成過程——那是業務情境卡（實例）的職責 |
| SHOULD | 痛點歸因到 [[痛點]]（暫無痛點可標「待訪談」） |
| MAY | 同一服務的可選子步驟（如打樣）寫在階段內，不另開卡 |

## 四、商業規則撰寫規則

**觸發條件**：辨識到一條決策邏輯、產業事實、或外部約束。

### 可變性分流

撰寫規則和產出格式相同，但子目錄和 `mutability` 不同。用以下判斷分流：

| 問自己 | 答案 | `mutability` | 子目錄 |
|--------|------|-------------|--------|
| 公司可以自己改嗎？ | 不行，是法規/第三方規定 | `external` | `外部約束/` |
| 公司可以自己改嗎？ | 不行，是產業本來就這樣 | `domain` | `領域知識/` |
| 公司可以自己改嗎？ | 可以，是公司決定的 | `internal` | `營運規則/` |

### 前提確認（MUST 全部已確認才能開始撰寫）

| 前提 | 確認狀態 |
|------|---------|
| 這條規則解決什麼問題？（為什麼存在） | 已確認 / 待確認 → 停下 |
| 目前公司怎麼處理？（現況） | 已確認 / 待確認 → 停下（不可假設現況） |
| 規則可變性？（外部約束 / 領域知識 / 營運規則） | 已確認 → 設定 `mutability` 分流 / 待確認 → 停下 |
| 在哪些流程階段生效？ | 對照服務藍圖 / 如無藍圖 → 標記「待補」 |
| 有沒有例外情境？ | 已確認 / 暫無 → 可留空標「待確認」 |

**外部約束額外前提**（`mutability: external` 時追加）：

| 前提 | 確認狀態 |
|------|---------|
| 約束來源（哪個法規/第三方）？ | 已確認且有外部文件佐證 / 待確認 → 停下 |
| 公司資料與外部的對應關係？ | 已確認且可在 `05-entities/` 找到對應 / 找不到 → 開 OQ |

### 撰寫規則

| 強度 | 規則 |
|------|------|
| MUST | 段名一律依 [[範本 - 商業規則]] 骨架、不加卡名前綴（寫「規則」，不寫「報價規則」）；`###` 子標題依規則主題自由命名 |
| MUST | 規則用商業語言描述，禁實作術語當主詞 |
| MUST | 現況段具體描述目前的工具與方式，不寫抽象描述 |
| MUST | 附至少一個具體例子（真實業務數字） |
| MUST | 標註適用範圍（引用服務藍圖的階段） |
| MUST | 外部約束卡（`mutability: external`）須標明外部來源文件（法規條號、API 文件版本） |
| SHOULD | 標註例外情境 |
| MAY | 規則多條時，「規則」段與「為什麼這樣定」段用**同名 `###` 子標**一一對應（讀者跨段對照不迷路） | 動機與本體分段是八段結構的取捨，同名子標補回配對性 |
| SHOULD | 標註規則來源（誰決定的、什麼依據） |
| SHOULD | 相關卡段依分類列出（角色/實體/狀態機/規則/OQ），只列有連結的分類 |
| MAY | 領域知識段補充印刷業背景 |
| MAY | 複雜規則（多條並列）可用「意圖/規則/營運動機」三欄表格呈現每條規則 |

### 產出格式

見 § 九。

## 五、修改商業規則前的可變性檢查

修改任何商業規則卡之前，MUST 先檢查 frontmatter `mutability`：

| `mutability` | 可以改嗎 | 改之前要確認什麼 |
|---|---|---|
| `external` | **原則上不可改** | 外部來源真的變了嗎？（法規修訂、API 改版）→ 須附外部變更依據 |
| `domain` | **原則上不可改** | 產業事實真的變了嗎？→ 須確認不是訪談中的誤解 |
| `internal` | **可以改** | 確認是管理層拍板或訪談確認的變更 |

**觸發 error handle 的情境**：訪談中有人說要改某條規則，但該卡 `mutability` 為 `external` 或 `domain` → 停下，與使用者確認是「外部來源真的變了」還是「對規則的理解有誤」。

## 六、邊際情境處理

| 卡住的情境 | 標準處理 |
|-----------|---------|
| 分類判斷表走完仍無法確定 | 開 OQ（`oq-manage` mode B），描述「內容是 X，不確定屬 Y 還是 Z，因為...」，暫放最接近的目錄，等使用者確認後搬移 |
| 一張卡跨兩個分類 | 問使用者：「這張卡 80% 的使用情境屬哪個分類？」放主要分類，另一個分類用 wiki link 引用 |
| 現有分類都不適合 | 向使用者提議新子目錄，說明為什麼既有分類不夠，等確認後再建 |
| 改寫舊卡時不確定某段保留還是下沉 | 問：「這段回答的是『公司怎麼決定事情』（保留），還是『系統怎麼實作』（下沉）？」答不出來 → 停下問使用者 |
| 同一規則疑似在別張卡已存在 | 先搜尋確認。已存在 → 併入不新建；不確定是否重複 → 問使用者 |

## 七、error handle（卡住時的標準處理）

### 觸發條件（本單元特有；共用四條——無來源依據／矛盾／需要假設／超出已知——見 [[卡片撰寫共用規範]] § 三）

1. **分類不明**：§ 二判斷表走完仍無法確定卡型或子目錄 → 開 OQ（`oq-manage` mode B），停下
2. **可變性衝突**：要修改 `mutability` 為 `external` 或 `domain` 的卡 → 停下，確認外部來源或產業事實是否真的改變（見 § 五）

### 處理方式

見 [[卡片撰寫共用規範]] § 三（標記具體問題、附已知事實提問、禁「一般來說」填充、改寫舊卡發現的問題保留舊內容另開 OQ）。

## 八、服務藍圖產出格式

一張卡 = 一條端到端業務鏈。以「客戶的目標」定義服務終點。**檔名即標題**。frontmatter 樣板與段落填空結構見 [[範本 - 服務藍圖]]（骨架），完整合規樣貌見 [[範例 - 服務藍圖]]。

**段落結構**（全部必填）：

| 段落 | 內容 |
|------|------|
| 概述 | 一段話說明這條業務鏈的商業目的與服務終點 |
| 流程階段 | 5-10 個階段，每階段標註角色、交接點、決策點 |
| 現況痛點 | 目前的問題，歸因到 [[痛點]]（隨訪談迭代擴充） |
| 適用規則 | 引用商業規則卡，標註在哪個階段生效（不複寫規則內容） |
| 範圍外 | 明確排除不涵蓋的範圍 |
| 相關卡 | 依分類列出 wiki link（業務情境/角色/實體/狀態機），只列有連結的分類 |

## 九、商業規則產出格式

一張卡 = 一條決策邏輯、一份領域知識或一條外部約束。**檔名即標題**。三種 `mutability` 各有專屬骨架與段落結構，依 § 二 歸類決策樹選型後套對應骨架：

| 型 | 骨架 | 段落結構見 |
|----|------|-----------|
| 營運規則（`internal`） | [[範本 - 商業規則]] | § 9.1（下表） |
| 領域知識（`domain`） | [[範本 - 領域知識]] | § 9.2 |
| 外部約束（`external`） | [[範本 - 外部約束]] | § 9.3 |

### 9.1 營運規則段落結構

完整合規樣貌見 [[範例 - 商業規則]]。（必填標 *，選填標 ?）

| 段落 | 內容 | 必/選 |
|------|------|-------|
| 現況 | 一句話描述目前公司怎麼處理這件事 | * |
| 規則 | 用商業語言描述（一段話講清楚） | * |
| 為什麼這樣定 | 營運動機（公司決策 / 法規 / 產業慣例） | * |
| 適用範圍 | 連結到服務藍圖的哪個階段或哪些業務情境卡生效 | * |
| 領域知識 | 印刷業特有的背景 | ? |
| 具體例子 | 真實業務數字說明（1-3 個） | * |
| 例外情境 | 什麼時候不適用 | ? |
| 範圍外 | 本卡不管什麼、正本在哪張卡（wiki link 逐條標歸屬），防下游腦補 | ? |
| 相關卡 | 依分類列出 wiki link（角色/實體/狀態機/規則/OQ），只列有連結的分類 | * |

### 9.2 領域知識段落結構

骨架見 [[範本 - 領域知識]]。**段落與 § 9.1 營運規則相同**，唯一結構差異在「規則」段：

> 領域知識的「規則」段**容許該領域的專業表示法**——分層表、計算公式與計算框架、換算鏈、指標定義表、方法論對映表，依知識本身的性質選，不強套散文。營運規則的「規則」段則以商業語言散文為主。

判斷理由：實測 8 張存量領域知識卡，段落與八段大致一致（現況 8/8、相關卡 8/8、為什麼這樣定 7/8），真正裝不下的只有承載公式與對映表的三張（[[齊套邏輯]] 數量帳與額度公式、[[生產績效指標]] 指標定義表、[[豐田式生產管理對映]] 對映表）。缺口是表示法而非段落結構，故不另立段落體系（骨架通用性評分表維度 5 的實測結論，見 [[卡片撰寫共用規範]] § 一）。

另一個判斷點：「為什麼這樣定」寫的必須是產業或方法論理由；若寫成公司決策理由，代表歸類錯誤、應改 `internal`（§ 十三 分型維度 12）。

### 9.3 外部約束段落結構

骨架見 [[範本 - 外部約束]]。與另兩型的差別：**來源必須可查證**（法規條號、規格文件版本），且獨有「變更追蹤」段——法規與外部介面會改版，沒有追蹤機制的外部約束卡遲早失效還沒人知道。

| 段落 | 內容 | 必/選 |
|------|------|-------|
| 一句話定位 | 哪個外部來源要求我們怎麼做、管住哪一段商業行為 | * |
| 約束來源 | 誰要求的、依據（法規名稱與條號／規格文件與版本）、生效時間；禁憑印象 | * |
| 約束內容（正本） | 外部要求的具體內容（必填欄位與格式、時限、門檻、交換規格） | * |
| 不遵守的後果 | 具體後果（罰則／單據被退／介接失敗／對帳不上），禁寫「會有問題」 | * |
| 我們的因應 | 公司與系統怎麼配合、誰負責；只寫方向與責任，實作規格屬 PRD 層 | * |
| 適用範圍 | 適用哪些單據與情境，不適用者明列 | * |
| 具體例子 | 1-3 個真實案例含數字或格式樣本 | * |
| 變更追蹤 | 怎麼得知外部改版、誰負責追、上次確認版本日期 | * |
| 範圍外 | 排除項＋歸屬去處 | * |
| 相關卡 | 依分類列 wiki link | * |

## 十、不收清單（商業規則卡排除的內容）

| 不收 | 應去的位置 | 判斷方式 |
|------|----------|---------|
| 欄位名稱與定義 | `05-entities/` 實體卡 | 看到 `field_name`、底線命名、駝峰命名 |
| 欄位的具體組成式 | `05-entities/` 欄位表（貼著欄位寫；本層只留 high-level 決策政策） | 看到「總額＝A＋B－C」逐欄組成敘述 |
| 計算公式（程式碼層級：取整、精度、邊界處理） | OpenSpec（不過紙本測試） | 看到 `floor()`、`min()`、`sum()`、程式碼片段 |
| 狀態枚舉值 | `06-state-machines/` 狀態機卡 | 看到 `status = '已完成'`、狀態清單 |
| API 規格（欄位長度、加密方式） | OpenSpec 或外部文件 | 看到 `Varchar(30)`、`AES-256` |
| Prototype 檔案路徑或行號引用 | OpenSpec `implemented-by` | 看到 `src/types/`、`L58-61` |
| 步驟級操作細節 | 業務情境卡（`07-scenarios/`） | 看到「第 1 步...第 2 步...」 |

**發現實作細節時的處置**：
1. 判斷該內容的正確歸屬位置
2. 確認目標位置的卡片存在
3. 如果目標位置已有該內容 → 直接從卡中刪除
4. 如果目標位置沒有 → 搬移過去後再刪除

## 十一、撰寫紀律

共用五條（規則回引不複寫／禁中英夾雜與禁技術術語當主詞／不確定項開 OQ／檔名即標題且正文零迭代史／不編造）見 [[卡片撰寫共用規範]] § 四，不在此重列。本單元特有四條：

1. **規則只寫一次**：商業規則卡是規則的唯一正本。服務藍圖與業務情境卡只能引用
2. **痛點掛在流程上**：現況痛點寫在服務藍圖（流程級別），商業規則只寫一句「現況」
3. **範圍外必寫**：服務藍圖和商業規則都要明確說不涵蓋什麼
4. **修改前檢查可變性**：修改商業規則卡前先看 `mutability`，外部約束和領域知識不可因訪談而改（見 § 五）

## 十二、擴張準則

### 何時新建卡 vs. 併入既有卡

| 情境 | 做法 |
|------|------|
| 新發現一條獨立的決策規則 | 新建商業規則卡 |
| 新發現的規則只是既有規則的補充說明 | 併入既有卡 |
| 一張卡超過 200 行 | 考慮拆分（但複雜規則如訂單異動規則例外） |
| 同一張卡涵蓋兩個不相干的主題 | 拆成兩張 |

### 何時拆子目錄

| 情境 | 做法 |
|------|------|
| 單一子目錄超過 10 張卡 | 考慮依子主題再拆一層 |
| 新的服務流程 | 在 `服務藍圖/` 新建卡 |
| 新的外部約束 | 在 `外部約束/` 新建卡 |
| 新的產業知識 | 在 `領域知識/` 新建卡 |

### 新服務藍圖的判斷

只有「客戶的目標不同」時才開新的服務藍圖：
- 諮詢服務：客戶目標 = 得到諮詢建議
- 商品販售：客戶目標 = 收到商品
- 帳務流程：不是客戶目標驅動，但獨立運作 → 可開藍圖

「同一個服務中的分支」（如打樣/大貨）不另開藍圖，在既有藍圖中標為可選步驟。

## 十三、稽核維度（vault-audit 用）

標竿對照：服務藍圖以 [[範例 - 服務藍圖]] 為通過樣本、商業規則以 [[範例 - 商業規則]] 為通過樣本。執行者／稽核者分離原則見 [[卡片撰寫共用規範]] § 二。

| # | 維度 | 通過標準 | 標竿對照 |
|---|------|---------|---------|
| 1 | 分類正確 | 卡片放在對的子目錄 | 兩張範例卡的落點與 `mutability` 一致 |
| 2 | 卡型對齊 | frontmatter type 是 service-blueprint 或 business-rule | [[範例 - 服務藍圖]]／[[範例 - 商業規則]] frontmatter |
| 3 | 可變性標記 | 商業規則卡有 `mutability` 欄位（external/domain/internal） | [[範例 - 商業規則]] 標 internal |
| 4 | 結構對齊 | 段落結構符合對應產出格式、段名無卡名前綴 | 兩張範例卡的段名逐字對照 |
| 5 | 不收內容 | 無欄位名、計算公式、API 規格、Prototype 引用 | 兩張範例卡正文無實作引用 |
| 6 | 規則唯一性 | 同一規則只寫一次，無跨卡重複 | [[範例 - 商業規則]] 分派邏輯指正本規則卡 |
| 7 | 引用完整 | 藍圖有引用規則；規則有引用適用範圍 | [[範例 - 服務藍圖]] 適用規則逐條標階段 |
| 8 | 語言紀律 | 無中英夾雜、無實作術語當主詞；wiki link 無別名 | 兩張範例卡全中文、連結無別名分隔符 |
| 9 | 範圍外 | 有寫「範圍外」或「例外情境」段 | [[範例 - 服務藍圖]] 範圍外逐條標歸屬 |
| 10 | 正文零迭代史 | 無「（YYYY-MM-DD 拍板）」等迭代日期敘述、無 change 更新 callout | 兩張範例卡正文無日期敘述 |

**分型追加維度**（依 `type` ＋ `mutability` 加勾）：

| 型 | # | 維度 | 通過標準 |
|----|---|------|---------|
| 服務藍圖 | 11 | 無角色與時序 | 正文未寫「誰做」與階段先後順序（那屬營運規則與業務情境）；只圈服務範圍與商業邊界 |
| 服務藍圖 | 12 | 商業邊界存在 | 有明列不提供什麼與限制條件，非只列提供什麼 |
| 領域知識 | 11 | 規則段為正本 | 「規則」段是該知識的唯一正本、其他卡引用不複寫；承載公式或對映表者採專業表示法、未強套散文 |
| 領域知識 | 12 | 理由非公司決策 | 「為什麼是這樣」寫產業或方法論理由；若寫成公司決策理由＝歸類錯誤，應改 `internal` |
| 外部約束 | 11 | 來源可查證 | 約束來源有法規條號或規格文件版本，非「聽說」「一般來說」 |
| 外部約束 | 12 | 變更追蹤存在 | 有「變更追蹤」段且填了負責追蹤者與上次確認版本日期 |
| 外部約束 | 13 | 後果具體 | 「不遵守的後果」寫具體罰則或失敗情形，非「會有問題」 |

## 十四、目錄結構

```
04-business-logic/
├── 規範 - 商業邏輯.md  ← 本檔（規範：本單元規則正本）
├── 範例 - 服務藍圖.md           ← 範例（服務藍圖凍結快照）

└── 營運規則/        ← 商業規則，mutability: internal（公司決策）
    ├── 售前/        ← 客戶下單前的互動
    ├── 訂單到交付/   ← 下單後到收到商品
    └── 帳務/        ← 貫穿全程的金流
```
