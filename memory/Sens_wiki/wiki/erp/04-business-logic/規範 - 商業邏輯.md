# 商業邏輯卡撰寫範本

> `04-business-logic/` 是 BRD 的營運層——記錄「公司怎麼做生意、怎麼決定事情、產業有什麼限制」。
> 核心紀律：**規則只寫一次**（Ronald Ross 原則），其他地方用 `[[wiki link]]` 引用，不複寫。
> 營運規則卡只承載兩種規則單元：**做法**（公司在幾種可行方式裡選了哪一種、為什麼）與**底線**（跨單據任何時候都必須成立的關係式）。其他內容各有家，見 § 二之二。
> 服務藍圖每個階段的活動清單卡是另一個卡型（`activity-list`），規範見 [[規範 - 活動清單]]，不屬本層四型。
> 流程架構（`process-architecture`）與受控清單（`controlled-list`）也是另外的卡型，各全庫一張，定義與段落要求見 [[wiki-schema]] § 四，不屬本層四型。
> 分層結構：動筆從 [[範本 - 服務藍圖]] 或 [[範本 - 商業規則]]（骨架）複製起手；合規樣貌對照 [[範例 - 服務藍圖]]、[[範例 - 商業規則]]（示範）；共用治理（撰寫流程／停下鐵則／撰寫紀律／修改既有卡原則）見 [[卡片撰寫共用規範]]——**本卡只寫商業邏輯單元的特定標準**。

## 二、分類判斷表

### 四型（載體為 `type` ＋ `mutability` 組合）

本層共四型，每型有專屬子目錄與稽核維度。四型互斥——同一內容只能落一型。骨架兩張：服務藍圖用 [[範本 - 服務藍圖]]，三種商業規則共用 [[範本 - 商業規則]]（卡頂引言＋八段，段內差異見 § 9.1–9.3）。

| 型 | 回答什麼問題 | `type` ＋ `mutability` | 子目錄 |
|----|-------------|----------------------|--------|
| **服務藍圖** | 公司的一門生意或一項支援工作從哪到哪、經過哪些階段 | `service-blueprint` | `服務藍圖/` |
| **營運規則** | 我們公司選了什麼做法、為什麼；跨單據必須成立什麼關係 | `business-rule` ＋ `internal` | `營運規則/` |
| **領域知識** | 這個領域本來就是這樣的知識（換任何一家同業都成立） | `business-rule` ＋ `domain` | `領域知識/` |
| **外部約束** | 外部要求我們必須怎麼做 | `business-rule` ＋ `external` | `外部約束/` |

**服務藍圖的判準＝有起點、終點與階段先後的端到端工作**：服務藍圖即 APQC 流程分類架構的流程群組，分兩類。營運類是客戶受益的服務（諮詢、下單到交貨、生產製作）；管理與支援類是支撐營運的內部工作（帳務、人力調度與職務代理、單據存取、主檔維護）。類別歸屬的正本在流程架構總卡。判定、門檻與做法不是藍圖，歸營運規則。服務藍圖寫階段與階段先後——它要說明「這項服務是在做什麼」，階段是說明的一部分；各階段誰在什麼範圍做什麼，由該階段的活動清單卡承載（[[規範 - 活動清單]]）；單一目標的活動先後與完成過程屬業務情境（`07-scenarios/`）。

**領域知識與營運規則必須拆開（MUST）**：一張卡不得同時承載業界知識與公司實作方式。判準——「換任何一家同業都成立」的歸領域知識，「我們公司決定這樣做」的歸營運規則。兩者常出現在同一主題上，此時**拆成兩張卡並互引**，不得混在一張。

例：生產管理必然有 BOM 這個概念、BOM 由料工裝三類組成、計價方式跟成本驅動因子走——這些是領域知識；我們的 BOM 三類分層長什麼樣、八種計價方法、計價引擎公式、誰維護主檔——這些是我們依 BOM 概念長出來的實作，歸營運規則。

**領域知識的兩種內容**：產業事實（如令的定義、印刷成本驅動因子）與系統設計方法論（MES／ERP 在這件事上怎麼建模、看哪些指標）。兩者共同點是公司無權單方變更，且不遵守只是算不出結果或不合行規、不會違法。

### 三種可變性（`mutability`，商業規則專用）

`mutability` 是「誰能改」這一軸，與上表的四型一對一對應——同一分類的兩種問法，判斷時以歸類決策樹為準。

| `mutability` | 型 | 子目錄 | 誰能改 |
|---|---|---|---|
| `external` | 外部約束（法規／第三方規格／第三方介面契約，如金流 webhook 的欄位對應） | `外部約束/` | 只有外部來源變更時（如法規修訂、API 改版） |
| `domain` | 領域知識（產業事實與系統設計方法論） | `領域知識/` | 產業或方法論本身改變時（極少） |
| `internal` | 營運規則（公司決策） | `營運規則/` | 訪談、管理層拍板可改 |

### 歸類決策樹（互斥，依序問，第一個命中即歸）

| 順序 | 問自己 | 是 | 型 | `type` ＋ `mutability` | 子目錄 |
|---|---|---|---|---|---|
| 1 | 這是外部（法規、稅務機關、第三方系統）要求我們必須怎麼做嗎？ | 是 | 外部約束 | `business-rule` ＋ `external` | `外部約束/` |
| 2 | 這在說明「一門生意或一項支援工作從哪到哪、經過哪些階段」嗎？ | 是 | 服務藍圖 | `service-blueprint` | `服務藍圖/` |
| 3 | 這條內容換任何一家同業都成立嗎？（領域本來就是這樣、我們無權改） | 是 | 領域知識 | `business-rule` ＋ `domain` | `領域知識/` |
| 4 | 這是公司的做法（幾種可行方式裡選了哪一種、為什麼），或跨單據任何時候都必須成立的關係式嗎？ | 是 | 營運規則 | `business-rule` ＋ `internal` | `營運規則/` 再依下表分流 |
| 5 | 第 4 題答否 | — | 不是本層內容 | — | 依 § 二之二 落點表找家；找不到停下問 |

> 第 3 題先於第 4 題問，是為了逼出「這段內容是業界知識還是我們的做法」的分辨。**一張卡若兩題都命中，代表它混了兩型、MUST 拆卡**（見上方 § 四型 拆開鐵則）。

**互斥判定句（兩兩比對，寫得出判定句才算歸對）**：

| 比對 | 判定方法 | 例子 |
|------|---------|------|
| 外部約束 vs 營運規則 | 來源在公司內還是公司外？無權變更的是外部約束 | 統一發票的品項與稅別格式（外部約束）vs 我們自己訂的開發票時機（營運規則） |
| 外部約束 vs 領域知識 | 不遵守會違法或介接失敗嗎？會＝外部約束 | 發票格式不照做會被國稅局退（外部約束）vs 印刷計價不照令數算只是報價難談（領域知識） |
| 領域知識 vs 營運規則 | 換一家同業還成立嗎？成立＝領域知識 | 生產管理必有 BOM、BOM 分料工裝三類（領域知識）vs 我們的 BOM 三類分層與八種計價方法（營運規則） |
| 服務藍圖 vs 營運規則 | 說的是階段與階段先後，還是判定、門檻與做法？前者＝服務藍圖 | 線下單從詢價走到交貨經過哪些階段、帳務從規劃收款到核銷經過哪些階段（服務藍圖）vs 開發票的時機怎麼判、生產怎麼分工判斷（營運規則） |
| 服務藍圖 vs 業務情境 | 是「這項服務的全貌」還是「一個目標的完成過程」？ | 生產服務含哪些階段（服務藍圖）vs 一張工單製程審核怎麼過（業務情境） |

**判斷不了時**：描述爭議、列出兩型各自的判定句試寫結果，向 Miles 確認後歸類（建卡當下即決，不動用 OQ 流程）。

**存量卡重分類（2026-07-30 執行完畢）**：全 35 張逐張重判後執行——[[BOM結構]]、[[數量換算規則]]、[[齊套邏輯]]、[[印件生產流程]]、[[打樣流程]]、[[稿件管理規則]] 六張由 `領域知識/` 移入 `營運規則/訂單到交付/`（內容主體是我們公司的做法）；其中 [[BOM結構]] 依拆開鐵則抽出 [[印刷成本結構]]（產業計價常識獨立成卡），其餘五張的產業背景份量不足以成卡、留在八段的「領域知識」段。`領域知識/` 現存 [[生產績效指標]]、[[豐田式生產管理對映]]、[[印刷成本結構]] 三張純領域知識卡。

**營運規則子目錄分流**：

| 問自己 | 是 | 子目錄 |
|--------|---|--------|
| 客戶還沒下單前的事？（諮詢、報價、議價） | 是 | `營運規則/售前/` |
| 下單後到客戶收到商品？（審稿、生產、出貨、售後） | 是 | `營運規則/訂單到交付/` |
| 金流相關？（收付款、開發票、對帳、退款） | 是 | `營運規則/帳務/` |

## 二之二、規則卡以外的家（知識單元落點表）

下列內容過去常寫進營運規則卡，各有自己的家。歸類決策樹第 4 題答「否」時依本表落點；規則卡要提到這些內容時只 wiki link 指過去。

| 知識單元 | 家 | 引用方式 |
|---|---|---|
| 欄位定義與算式（含運算元來自別的實體的算式） | 實體卡欄位表算式欄（[[規範 - 實體]] § 三） | `實體.欄位名` |
| 同一筆資料內的檢核 | 實體卡檢核區塊 | `[[實體卡]] § 檢核` |
| 操作的前提與擋下條件（做這個操作要過哪些底線、單據要在什麼狀態） | 實體卡操作段「前提」欄（[[規範 - 實體]] § 三） | 操作編號 |
| 單據在各狀態下哪些內容可改 | 狀態機卡「各狀態可改內容」表（[[規範 - 狀態機]] § 七）；單一欄位的狀態期限寫實體卡可否修改欄 | 狀態名 |
| 誰在什麼範圍能做哪個操作、單元列出哪些單據 | 活動清單卡（[[規範 - 活動清單]]） | 活動編號 |
| 清單或佇列的進入條件與移出條件 | 實體卡「具名清單」段（[[規範 - 實體]] § 七） | `[[實體卡]] § 清單名` |
| 多步計算框架 | 中間值升格為某實體的欄位，框架即該實體算式欄的推導序列；升不了格的留領域知識卡 | `實體.欄位名` |
| 範圍用詞、動作類型、單據代碼、流程類別 | [[受控清單]]、[[流程架構]] | 卡名 |
| 角色接力、步驟先後 | 業務情境卡、服務藍圖 | `[[情境卡]]` |
| 系統行為承諾（整批不寫入、併發重檢、導回預設頁、提示不擋） | OpenSpec（不進 wiki） | — |
| 某主題的數值與規則各在哪張卡 | 領域資料結構總覽卡資料流視圖（[[規範 - 資料結構總覽]]） | `[[總覽卡]] § 資料流視圖` |

## 三、服務藍圖撰寫規則

**觸發條件**：辨識到一條端到端的工作鏈（有明確目標、有起點和終點）。營運類的目標是客戶目標，管理與支援類的目標是內部目標。

### 前提確認（MUST 全部已確認才能開始撰寫）

| 前提 | 確認狀態 |
|------|---------|
| 目標（終點）是什麼？營運類寫客戶目標，管理與支援類寫內部目標 | 已確認 / 待確認 → 停下 |
| 屬營運類還是管理與支援類？已登記在流程架構總卡？ | 已確認 / 待確認 → 停下 |
| 從哪裡開始？（觸發點） | 已確認 / 待確認 → 停下 |
| 各階段的切分點與先後？（每階段從哪個事件開始、到哪個事件結束） | 已確認 / 待確認 → 停下 |
| 有哪些決策分叉？每個分叉走向？ | 已確認 / 待確認 → 停下 |
| 這條流程的痛點是否已在 [[痛點]] 有對應問題？ | 已有 → 引用即可 / 尚無 → 補進 [[痛點]] 後引用（不在本卡寫痛點現象）|
| 哪些不在範圍內？ | 已確認 / 待確認 → 停下（不可自行假設範圍） |

### 撰寫規則

| 強度 | 規則 |
|------|------|
| MUST | 段名一律依 [[範本 - 服務藍圖]] 骨架、不加卡名前綴（寫「流程階段」，不寫「生產流程階段」）；`###` 階段標題＝序號＋階段名，階段名依業務語意命名、不加角色括號；階段名是該階段活動清單卡名的前段，全庫唯一 |
| MUST | 「流程階段」段開頭先寫兩行條列：**起點**（這段工作從哪個事件開始；從上游藍圖接入時寫明接入點）／**終點**（到哪個事件或狀態結束），再接各階段子節 |
| MUST | 每個階段子節固定四行條列：**階段目標**（這階段要達成什麼）／**起訖**（必填；自哪個事件或狀態起、至哪個事件或狀態止；跨階段可做的活動與退回、重啟屬哪個階段一併寫明）／**活動清單**（`[[〈階段名〉活動清單]]`，卡名依 [[wiki-schema]] § 七）／**決策點**（有哪些分叉；無分叉寫「無」）。不寫成連續散文 |
| MUST | 階段子節不寫角色與交接敘述、不寫誰做什麼：誰在什麼範圍做什麼的正本在活動清單卡，藍圖再寫一份就是重疊 |
| MUST | 決策分叉只標方向，細節引用商業規則卡（不複寫規則內容） |
| MUST | 寫「範圍外」段 |
| MUST | 與其他藍圖的關係只寫交接點：「相關卡」段的服務藍圖分類逐條標上游、下游或平行，並寫交接點（在哪個事件或狀態交接）；不重述對方藍圖的階段內容 |
| MUST | 藍圖停在階段層（型）：不寫業務判準、不展開活動先後與步驟級完成過程——那是業務情境卡（實例）的職責 |
| MUST | 不寫痛點現象——痛點正本唯一在 [[痛點]]（專案層），流程卡要提痛點以 wiki link 指回 |
| MAY | 同一服務的可選子步驟（如打樣）寫在階段內，不另開卡 |

## 四、商業規則撰寫規則

**觸發條件**：辨識到一條決策邏輯、產業事實、或外部約束。

### 可變性分流

撰寫規則和產出格式相同，但子目錄和 `mutability` 不同。用以下判斷分流：

| 問自己 | 答案 | `mutability` | 子目錄 |
|--------|------|-------------|--------|
| 公司可以自己改嗎？ | 不行，是法規/第三方規定 | `external` | `外部約束/` |
| 公司可以自己改嗎？ | 不行，是產業本來就這樣 | `domain` | `領域知識/` |
| 公司可以自己改嗎？ | 可以，是公司決定的 | `internal` | `營運規則/` |

### 前提確認（MUST 全部已確認才能開始撰寫）

| 前提 | 確認狀態 |
|------|---------|
| 這條規則解決什麼問題？（為什麼存在） | 已確認 / 待確認 → 停下 |
| 目前公司怎麼處理？（現況） | 已確認 / 待確認 → 停下（不可假設現況） |
| 規則可變性？（外部約束 / 領域知識 / 營運規則） | 已確認 → 設定 `mutability` 分流 / 待確認 → 停下 |
| 在哪些流程階段生效？ | 對照服務藍圖 / 如無藍圖 → 標記「待補」 |
| 有沒有例外情境？ | 已確認 / 暫無 → 可留空標「待確認」 |

**外部約束額外前提**（`mutability: external` 時追加）：

| 前提 | 確認狀態 |
|------|---------|
| 約束來源（哪個法規/第三方）？ | 已確認且有外部文件佐證 / 待確認 → 停下 |
| 公司資料與外部的對應關係？ | 已確認且可在 `05-entities/` 找到對應 / 找不到 → 開 OQ |

### 撰寫規則

| 強度 | 規則 |
|------|------|

## 五、修改商業規則前的可變性檢查

修改任何商業規則卡之前，MUST 先檢查 frontmatter `mutability`：

| `mutability` | 可以改嗎 | 改之前要確認什麼 |
|---|---|---|
| `external` | **原則上不可改** | 外部來源真的變了嗎？（法規修訂、API 改版）→ 須附外部變更依據 |
| `domain` | **原則上不可改** | 產業事實真的變了嗎？→ 須確認不是訪談中的誤解 |
| `internal` | **可以改** | 確認是管理層拍板或訪談確認的變更 |

**觸發 error handle 的情境**：訪談中有人說要改某條規則，但該卡 `mutability` 為 `external` 或 `domain` → 停下，與使用者確認是「外部來源真的變了」還是「對規則的理解有誤」。

## 九、商業規則產出格式

一張卡 = 一條決策邏輯、一份領域知識或一條外部約束。**檔名即標題**。三種 `mutability` **共用 [[範本 - 商業規則]] 骨架**（卡頂引言＋八段），差異只在段內表示法與判準（§ 9.2／§ 9.3）——實測 31 張存量卡有 28 張可不變形套入八段，缺口是表示法而非段落結構，故不另立骨架（骨架通用性評分表維度 5 的實測結論，見 [[卡片撰寫共用規範]] § 一）。

### 9.1 段落結構（三型共用）

完整合規樣貌見 [[範例 - 商業規則]]。（必填標 *，選填標 ?）

| 段落 | 內容 | 為誰 | 必/選 |
|------|------|------|-------|
| 卡頂引言（無段名） | `讀完這張卡，你會知道：` ＋ 3 到 5 條，動詞開頭一條一行（這條規則管什麼與何時適用、怎麼判與結果、為什麼這樣定、有哪些例外）。不寫 frontmatter 已有的 `mutability` 與來源（通則見 [[卡片撰寫共用規範]] § 一之二）| 第一次接觸的 PM | * |
| 現況 | 一句話描述目前公司用什麼工具、什麼方式處理這件事，作為規則要解決什麼的事實基礎。**不是與規則並陳的另一時態**——規則段永遠寫拍板後生效的內容，現況段不承載「改完會變成什麼」，也不得用來保留已被取代的規則寫法 | 商業自足理解（規則要解決的是什麼） | * |

| 適用範圍 | 連結到服務藍圖的哪個階段或哪些業務情境卡生效 | 定位規則的作用點 | * |
| 領域知識 | 印刷業特有的背景 | 第一次接觸的 PM | ? |

| 例外情境 | 什麼時候不適用 | 防一體適用誤套 | ? |
| 範圍外 | 本卡不管什麼、正本在哪張卡（wiki link 逐條標歸屬） | 防下游腦補 | * |
| 相關卡 | 依分類列出 wiki link（角色／實體／狀態機／規則／OQ），只列有連結的分類 | 互連防孤島 | * |

### 9.2 領域知識的段內差異

**「規則」段以該領域的專業表示法為主**——分層表、換算鏈、指標定義表、方法論對映表，依知識本身的性質選，不強套散文，也不套規則單元表（領域知識不是公司的做法或底線）。營運規則的「規則」段只有規則單元表：底線以式子表示（§ 四），對映表與分層表不放營運規則（放了代表混了領域知識、須依 § 二 拆卡鐵則拆開）；算出某個欄位值的算式不論在哪一型都歸實體卡算式欄。

**「為什麼這樣定」段寫的必須是產業或方法論理由**（成本驅動因子、物理限制、業界共識、標準方法論推論）；若寫成公司決策理由，代表歸類錯誤或混型，應拆卡或改 `internal`。

### 9.3 外部約束的段內差異

**`source` 必須可查證**：法規名稱與條號、規格文件與版本、介面契約文件；禁「一般來說」「聽說」。

**「規則」段容許規格表示法**：必填欄位與格式對應表、API 規格表、時限與門檻表。

**「為什麼這樣定」段寫外部來源的要求與不遵守的具體後果**（罰則／單據被退／介接失敗／對帳不上），禁寫「會有問題」。

**「例外情境」段兼作變更追蹤**（選填但建議）：外部來源改版時怎麼得知、誰負責追、上次確認的版本與日期。法規與外部介面會改版，沒有追蹤線索的外部約束卡會靜默失效。

## 十一、撰寫紀律

共用各條（規則回引不複寫／禁中英夾雜與禁技術術語當主詞／不確定項開 OQ／檔名即標題且正文零迭代史／不編造／段落格式依骨架／一條列點一個主張／例子段只准驗算／動機段禁規則句／**流程用表格而規則才用句子**）見 [[卡片撰寫共用規範]] § 四，不在此重列。本單元特有下列各條：

1. **規則只寫一次**：商業規則卡是規則的唯一正本。服務藍圖與業務情境卡只能引用
2. **痛點只寫在 01-products 的專案目標與痛點卡**（[[ERP與MES建置專案]]、[[痛點]]）：痛點正本唯一在專案層 [[痛點]]——服務藍圖與商業規則描述的是**現況怎麼運作**，痛點是**專案挑了哪些問題要解**，兩者性質不同。本層任何一張卡要提痛點一律 wiki link 指回，不設痛點段、不寫使用上的不便（商業規則仍寫「現況」段描述現況運作，不寫痛點現象）
3. **範圍外必寫**：服務藍圖和商業規則都要明確說不涵蓋什麼
4. **修改前檢查可變性**：修改商業規則卡前先看 `mutability`，外部約束和領域知識不可因訪談而改（見 § 五）
5. **不寫畫面與功能需求**：本層不寫畫面呈現、清單排序、功能需求（要做什麼按鈕、提供什麼視圖）；介面設計的正本是 Prototype，寫進來就是雙重維護

## 十二、擴張準則

### 何時新建卡 vs. 併入既有卡

| 情境 | 做法 |
|------|------|
| 新發現一條獨立的決策規則 | 新建商業規則卡 |
| 新發現的規則只是既有規則的補充說明 | 併入既有卡 |
| 同一張卡的規則單元分屬兩個主題 | 拆成兩張，各自一個主題 |

### 何時拆子目錄

| 情境 | 做法 |
|------|------|
| 單一子目錄超過 10 張卡 | 考慮依子主題再拆一層 |
| 新的服務流程 | 在 `服務藍圖/` 新建卡 |
| 新的外部約束 | 在 `外部約束/` 新建卡 |
| 新的產業知識 | 在 `領域知識/` 新建卡 |

### 新服務藍圖的判斷

只有「目標不同」時才開新的服務藍圖：
- 諮詢服務（營運類）：客戶目標 = 得到諮詢建議
- 商品販售（營運類）：客戶目標 = 收到商品
- 帳務（管理與支援類）：內部目標 = 應收、發票、收款三者對得上

「同一個服務中的分支」（如打樣/大貨）不另開藍圖，在既有藍圖中標為可選步驟。

## 十三、稽核維度（vault-audit 用）

**全通過制、不計分**：一張卡的完成＝載入 L1＋L2＋L3 全部通過。L1（全 wiki 共用）正本在 [[卡片撰寫共用規範]] § 四之二，本節不複寫；以下只列 L2（商業邏輯層共用）與 L3（分型）。

標竿對照：服務藍圖以 [[範例 - 服務藍圖]]、商業規則以 [[範例 - 商業規則]] 為通過樣本。執行者／稽核者分離原則見 [[卡片撰寫共用規範]] § 二。

### L2 商業邏輯層共用維度

| # | 維度 | 通過標準 | 標竿對照 |
|---|------|---------|---------|
| 1 | 分類正確 | 依 § 二 決策樹落在對的型與子目錄；**未混兩型**（混型須拆卡） | 兩張範例卡的落點與 `mutability` 一致 |
| 2 | 卡型對齊 | `type` 是 service-blueprint 或 business-rule | 兩張範例卡 frontmatter |
| 3 | 可變性標記 | 商業規則卡有 `mutability`（external／domain／internal） | [[範例 - 商業規則]] 標 internal |
| 4 | 結構對齊 | 段落符合 § 八（藍圖）或 § 9.1（商業規則：卡頂引言＋八段）、段名無卡名前綴；商業規則的規則段為規則單元表，每列有單元名、種類（做法或底線）、意圖、規則、營運動機，底線的規則欄是式子且運算元限實體.欄位名 | 兩張範例卡段名逐字對照；[[範例 - 商業規則]] 規則段 |
| 5 | 來源可查證 | `source` 指得出具體出處（法規條號／規格版本／訪談場次／拍板來源／調研素材卡），禁「一般來說」 | 兩張範例卡 source 具名 |
| 6 | 不收內容 | 無 § 十 不收清單所列內容：無欄位名與欄位算式本體、無操作前提與擋下條件、無各狀態可改矩陣、無清單組成、無權限範圍表、無系統行為承諾、無正本歸屬索引、無 Prototype 引用、無畫面呈現與痛點描述 | 兩張範例卡正文無實作引用 |
| 7 | 規則唯一性 | 同一規則只寫一次、無跨卡重複 | [[範例 - 商業規則]] 分派邏輯指正本規則卡 |
| 8 | 引用完整 | 藍圖有引用規則；規則有引用適用範圍；他卡以 `[[卡名#單元名]]` 引用本卡的單元名在單元表存在 | [[範例 - 服務藍圖]] 適用規則逐條標階段 |
| 9 | 量詞紀律 | 規則句邊界以明確量詞（僅／任何／全部／任一）封閉；無「原則上」「通常」「視情況」等模糊詞；兩條件以上的組合已用決策表 | 規則句不靠例子撐語意 |
| 10 | 集合詞受控 | 規則句引用的狀態集合詞皆命中對應狀態機卡 UML 圖的複合狀態名；例子段只含驗算例（無算式的規則無例子段） | 集合詞查得到唯一定義 |

### L3 分型維度（依型加勾；每條均通過不可移植測試——套到同層其他型會無意義或有害）

| 型 | # | 維度 | 通過標準 |
|----|---|------|---------|
| 服務藍圖 | 11 | 類別與目標明確 | 已登記在流程架構總卡的營運類或管理與支援類；營運類寫得出客戶目標，管理與支援類寫得出內部目標；內容是階段與先後，不是判定與做法 |
| 服務藍圖 | 12 | 停在階段層 | 每個階段有起訖與活動清單引用；起訖寫得出起點與終點的事件或狀態；無角色與交接敘述；未展開活動先後、步驟級完成過程與判準（那屬業務情境） |
| 領域知識 | 11 | 換家同業仍成立 | 內容不含「我們公司決定這樣做」的實作方式；混了就拆卡 |
| 領域知識 | 12 | 專業表示法就位 | 承載公式、換算鏈、指標定義或對映表者放在「規則」段且未強套散文 |
| 領域知識 | 13 | 理由非公司決策 | 「為什麼這樣定」寫產業或方法論理由 |
| 外部約束 | 11 | 後果具體 | 寫得出具體罰則或失敗情形，非「會有問題」 |
| 外部約束 | 12 | 版本線索存在 | source 帶版本或條號；改版追蹤線索（誰追、上次確認版本）已記 |

## 十五、禁止清單（商業邏輯特有）

> 全卡型的禁止項見 [[卡片撰寫共用規範]] § 四之三；禁擴充的正面表列見同卡 § 四 第 12 條。本節只列商業邏輯單元特有的項目。與 § 十 不收清單的分工：不收清單管內容歸哪張卡，本節管不准怎麼寫。

| # | 不准寫 | 判斷訊號 | 改成什麼 |
|---|--------|---------|---------|
| B1 | 底線的規則欄寫句子不寫式子；做法的規則欄夾式子 | 種類＝底線的列沒有運算符號或數學函式；種類＝做法的列出現 ＋ － × ÷ ≥ ≤ 或 sum( min( | 底線寫式子、做法寫句子；一列只有一種 |

| B3 | 單元名改名或重用 | 他卡 `[[卡名#單元名]]` 解析不到；表尾沒有舊名指向新名的列 | 新名另立一列，舊名留在表尾指向新名 |
| B4 | § 二之二 落點表所列內容寫進規則卡 | 操作的前提與擋下條件、各狀態可改內容、清單的進入與移出條件、單一欄位算式、誰能做、步驟先後、系統行為承諾、正本歸屬索引 | 寫到落點表指定的家，本卡只留 `[[卡名]]` |
| B5 | 來源端列誰用它 | 「本底線被哪些操作引用」「供某某取用」 | 刪除；由操作的前提欄與算式欄引用本卡 |
| B6 | 模糊量詞 | 原則上、通常、視情況、一般來說、大致 | 僅／任何／全部／任一封閉條件；兩條件以上用決策表 |
| B7 | 動機重複與動機段寫規則句 | 「為什麼這樣定」段與營運動機欄寫同一理由；營運動機欄出現角色＋動作、狀態值、門檻數字 | 單元各自的理由只在營運動機欄；規則句只在規則欄 |

## 十六、機械自檢（商業邏輯特有）

全卡型條目的指令見 [[卡片撰寫共用規範]] § 四之四；判定規則同該節。下列指令在 repo 根目錄執行。

B0 規則單元表表頭（錯誤）：

```bash
grep -rn '^| 單元名' memory/Sens_wiki/wiki/erp/04-business-logic/營運規則 --include='*.md' | grep -v '| 單元名 | 種類 | 意圖 | 規則 | 營運動機 |'
```

B1 底線無式子、做法夾式子、種類欄值域（底線無式子與種類非法為錯誤；做法夾式子為警告，句子裡的比較詞可能誤判）：

```bash
awk -F'|' '/^\| *-+ *\|/{t=(p ~ /^\| 單元名 \| 種類/); p=$0; next} /^\|/{ if(t){k=$3; gsub(/ /,"",k); f=($5 ~ /＋|－|×|÷|≥|≤|≠| = |sum\(|min\(|max\(|floor\(|ceil\(/); if (k=="底線" && !f) print FILENAME":"FNR": 底線無式子 "$2; if (k=="做法" && f) print FILENAME":"FNR": 做法夾式子 "$2; if (k!="底線" && k!="做法") print FILENAME":"FNR": 種類非法 "$2" ⇒ "k}; p=$0; next} {t=0;p=$0}' memory/Sens_wiki/wiki/erp/04-business-logic/營運規則/*/*.md
```

B3 單元名引用解析（錯誤：`[[卡名#單元名]]` 指不到卡，或卡內沒有該單元名的列或段）：

```bash
grep -rhoE '\[\[[^]#|]+#[^]|]+\]\]' memory/Sens_wiki/wiki/erp/0[3-7]*/ --include='*.md' | grep -vE '卡名#|規則卡#' | sort -u | while IFS= read -r l; do c=${l#\[\[}; c=${c%\]\]}; card=${c%%#*}; u=${c#*#}; f=$(find memory/Sens_wiki/wiki/erp -name "$card.md" | head -1); if [ -z "$f" ]; then echo "卡不存在: $l"; elif ! grep -q "^| $u |" "$f" && ! grep -q "^#.* $u" "$f"; then echo "單元名不存在: $l"; fi; done
```

B4 落點表內容的訊號（警告；指向家卡的引用句不算）：

```bash
grep -rnE '擋下|進入條件|移出條件|可改／鎖定|整批不寫入|導回|正本歸屬' memory/Sens_wiki/wiki/erp/04-business-logic/營運規則 --include='*.md'
```

B6 模糊量詞（錯誤）：

```bash

```
