## 資料結構（JSON，鍵名不可增減；新增頁面時複製同單元既有 howto 頁的鍵）
- howto 頁 steps：每步是 ["步驟文字", "說明"]。
  - 步驟文字＝動作＋結果，寫在同一段。例：「切到「印件報價」頁籤，點「新增印件」。開啟新增印件表單。」
  - 說明＝只在該步驟有特別要提醒的事才填，否則填空字串 ""。全頁說明不超過兩處。
  - 目前資料是舊版「做什麼」＋「你會看到」機械合併，多數過長。要重寫成精簡版：一步一到兩句，總字數比現在少。
  - 步驟少抄欄位名，重點是讓讀者知道怎麼完成該業務情境。欄位細節放 fields 表。
- howto 頁 check：標題已改為「預期結果」。每點寫完成後的可觀察狀態，三點左右。
- howto 頁 fields：照表單實況完整列齊，不精簡。唯讀帶入的參考欄位可合併一列寫「唯讀」。
- overview 頁 how.stages：每列 [狀態, 負責角色, 在做什麼, 按哪個按鈕, 之後變成]。前三欄會渲染成概念階段帶，是讀者建立心智模型的主圖：「在做什麼」寫 20 字內、講這個狀態存在的目的，不是操作。例外狀態（流失、已取消、不合格、待改稿、重新確認製程、已作廢）也列進 stages，系統會自動畫成虛框。how.flow 欄位不再渲染，保留原值不動。
- overview 頁 goals：動詞用理解、分辨、判斷、找到；讀完要能說出各狀態在做什麼。

## 內容規則
- 全文不用具體單號（Q-、ORD-、PI-、WO-、BI-、SSP-、DO-、AU- 等格式一律移除）。改寫成「這張需求單」「該印件」「這張工單」。金額、數量、日期可留作例子。人名與公司名可留作虛構情境，不必與 prototype 假資料一致。
- 介面字串（按鈕、頁籤、欄位、對話框標題、提示、選單）逐字取自程式碡，用「」標示。提示文字裡的內層引號也用「」不用『』。
- 角色名依畫面與 wiki：業務、業務主管、諮詢、會計、訂單管理人、審稿主管、審稿人員、印務、印務主管、生管、師傅、廠務、品檢人員、主管。
- intro 第一句含人事時地物；「做完這頁你會」寫能力，禁「說出」「看懂」「知道有哪些」。
- 禁跨單元指涉（用階段名：需求單階段、訂單階段、款項與發票階段、審稿階段、工單階段、生產階段）。不註記資料來源。禁比喻、禁「順手」「刻意」。
- 只在你的單元 JSON 檔內改，不動其他檔。寫回同一個檔。

## 回報格式
表格：頁 id｜改了什麼（一句）｜依據（程式碼檔名:行號 或 報告差異編號）。最後一段列「無法判斷、需 Miles 決定」的事項（沒有就寫無）。
