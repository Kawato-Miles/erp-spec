### 第二段結果（2026-10-13，草稿第 6 輪版本）

3 位 Sonnet 受測者 9 題結論都與標準答案一致，判定通過。第 3、9 題依 N7 拿掉，第 11 題改用建立者與接單業務不同人的案例。

受測者指出、票上沒寫清楚的地方：

| 項目 | 指出人數 | 歸屬 |
|---|---|---|
| 複製的驗收案例只有複製者本人是接單業務，沒有複製他人單的案例 | 3 | 情境目錄缺具名案例 |
| 單價在需求確認中、待評估成本時怎麼填進去 | 2 | 上游矛盾 5（單價何時可改） |
| 重新啟動後，成本估算、單價、報價紀錄是否保留 | 3 | wiki 沒寫 |
| 重新啟動後，流失當時的活動紀錄是否保留 | 3 | wiki 沒寫 |
| 「自己負責」只定義在 project，Feature 權限表沒有重述 | 2 | 依 N1 設計，不改 |

## 第三段：Linear → 開發設計

受測者 3 位扮演後端、3 位扮演前端，只讀 Linear 草稿與開發看得到的 wiki、Prototype。

| 角色 | 題目 |
|---|---|
| 後端 | 列出你要開的 API（每支寫用途一句），以及你會回頭問 PM 的問題 |
| 前端 | 列出你要做的頁面與控制元件（動作按鈕、對話框、側板、頁籤），每項寫要接哪個資料操作，以及你會回頭問 PM 的問題 |

通過條件（Miles 判定）：
- 後端列出的 API 涵蓋各 Feature 權限表的每一列動作。
- 前端列出的控制元件涵蓋各 Task 票的清單。
- 3 位之間沒有互相矛盾的設計。
- 「會回頭問 PM 的問題」逐條檢查：屬於票上缺資訊的，回頭修票；屬於規範範圍外（例如 API 路徑）的，不算缺。
