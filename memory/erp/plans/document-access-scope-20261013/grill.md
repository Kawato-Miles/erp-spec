# wiki 權責結構重構 grill 拍板紀錄（2026-10-13）

起因：權限修正 change（openspec/changes/document-access-scope-alignment）盤點出 Prototype 61 筆落差（見同目錄 asis-gap.md）。根因是「誰能做什麼」散寫在角色、規則、實體、狀態機、情境五層。Miles 要求先以資料治理角度重構 wiki 結構，再處理 change。

## change 範圍（grill 前）

| 編號 | 問題 | 拍板 | 理由 |
|---|---|---|---|
| C1 | change 收哪些落差 | 範圍卡全表＋拍板直接造成的動作；既存漏洞（唯讀角色能改訂單內容、售後決議、印件備註、確認可製作與異動取消不看歸屬）另開 change | 既存漏洞不是本次 wiki 異動造成 |
| C2 | 業務主管「代操作任何訂單」涵蓋什麼 | 訂單模組本身（訂單、旗下印件、訂單異動、收款項目、發票、款項紀錄）中接單業務能做的動作，含送主管審核；出貨單、售後服務單不含 | Miles 選「含送審」；代操作者剛好是審核業務主管時會自己送自己核，Miles 接受 |

## 結構拍板

| 編號 | 問題 | 拍板 | 理由 |
|---|---|---|---|
| G1 | 權責記到哪個粒度 | 業務動作層級，不記欄位層級、不記權限名稱 | 對應組織分工；避開角色卡規範的「權限矩陣」陷阱 |
| G2 | 欄位能不能改 | 對單據有編輯權者可改一般欄位；建立後不可修改、系統計算者誰都不能改；只有特定角色能改的欄位升格為操作。頁籤層級可見性先規劃不實作（XM-016） | Miles 規則 |
| G3 | 整體原則 | wiki 以資料治理設計：不同卡資料不可重疊，商業資訊只放在正確的卡，連摘要也不留 | 散寫是 61 筆落差的根因 |
| G4 | 方法名稱 | 禁用帶數字的方法名稱（如「三分法」），改稱「職務範圍」 | 數字會變，造成資訊落差 |
| G5 | 角色卡的職務範圍段 | 刪除，角色卡只留職位定位與分工理由 | G3 |
| G6 | 動作類型受控清單 | 檢視、建立、編輯、刪除或作廢、狀態推進、審核、指派或改派、分享管理、輸出 | 每張單據逐類填，防漏；審核獨立以檢查送出者與核准者分權 |
| G7 | 權責與職責 | 「誰可以做」與「標準流程誰該做」是兩個事實；職責由情境卡主流程表達 | 送主管審核：可以做的有業務、諮詢、被分享（編輯）、業務主管，該做的是業務 |
| G8 | 框架 | 採 APQC 流程分類架構：類別（營運、管理與支援）→ 流程群組 → 流程 → 活動 | 業界通用流程目錄；缺流程會被看見 |
| G9 | 結構方案 | 活動資料化：活動是唯一資料來源，依單據、依角色的矩陣都是查出來的檢視；不設手寫權責總覽卡（取代先前「權責總覽放 03 角色層」的決定） | 讀者是 Claude，結構化且不重疊即如關聯式資料庫 |
| G10 | 活動存放形式 | 一個流程一張流程卡，卡內一張固定欄位的活動表 | 活動天生屬於某段流程 |
| G11 | 活動的定義 | 方案甲：一個活動＝一個角色為一個目的做一個操作，在一個範圍內 | 業務查訂單與業務主管查訂單目的不同，是不同活動；不多出可執行表 |
| G12 | 操作放哪 | 實體卡新增「操作」段：操作編號、名稱、動作類型，不寫角色 | 操作是單據的屬性 |
| G13 | 活動與狀態轉換的關係 | 記在狀態機：轉換列寫「觸發操作」（可多個）；活動表不寫轉換 | 一個轉換可由多個操作觸發；多個角色的活動共用同一操作 |
| G14 | 通用動作（檢視、輸出）歸屬 | 放進「單據存取」支援流程，每個活動都有所屬流程 | APQC 把資訊存取算支援流程 |
| G15 | 範圍的標準化 | 範圍只用標準用詞；另設「依據欄位」一欄，只寫欄位名稱；實體由操作決定；看上層單據寫「關聯欄位 → 欄位」；一個活動只看一個欄位，看兩個拆兩列；活動表拿掉單據欄 | 範圍用詞不再增加；每格一值 |
| G17 | 上下層延伸通則 | 刪除；每個延伸都寫成一列檢視活動 | 通則與活動說同一件事；售後服務單、款項清單的落差就是下游沒把通則推到底 |
| G18 | 撰寫流程的強制力 | 先只用技能；盲測後再決定要不要補檢查腳本、掛鉤或 mod | Miles 決定 |
| G19 | 被分享範圍的依據欄位 | 一律填分享成員欄 | 不留「何時可省略」的判斷 |
| G20 | 依據欄位寫法 | 一律寫「[[單據]] 欄位」，本單也寫；取代 G15 的「只寫欄位名稱」「關聯欄位 → 欄位」兩條 | 直接寫明看哪張單據的哪個欄位，不靠隱藏查找規則 |
| G21 | 操作登記在哪張實體卡 | 操作只登記在一張實體卡：使用者發起它時所在的那張單據（建立出貨單、複製訂單都登記在訂單）。規則正本放實體卡規範，寫卡入口 skill 的實體卡步驟只引用並檢核，範例卡示範 | 不同代理寫卡時放在同一位置；依據欄位不受影響（G20 已寫明單據） |
| G23 | change 與 wiki 重構的先後 | 先試點重構，盲測通過後把權限相關流程全部搬成活動表，change 從活動表取材做 Prototype 與測試，最後 Linear 改回 wiki 版 | change 的主要工作就是拼出誰能對哪些單做什麼，活動表正是這份成果，不必拼兩次 |
| G22 | 範圍與依據欄位對應 | 全公司：「—」；自己負責：[[單據]] 人員欄；被分享（檢視）、被分享（編輯）：[[單據]] 分享成員；所屬產線：[[單據]] 產線欄 | Miles 確認 |
| G24 | 試點範圍 | 報價評估（需求單）與出貨兩段 | 兩段涵蓋最多種權限情況；需求單是 Linear 等著改回 wiki 版的模組 |
| G25 | 盲測標準答案 | 主對話依新規範寫試點卡，答案取自現有 wiki；wiki 內容互相矛盾時才停下問 Miles | Miles 決定 |
| G26 | 情境卡是否保留 | 保留。活動清單卡只是活動的集合，不寫先後；改變狀態的活動先後由狀態機決定；特定情況的走法、分支、成立判準、具名例子由情境卡承載。情境卡刪行為者欄，成立判準改引用轉換 | 同一階段的走法隨情況不同；情境卡也是驗收條目與情境目錄的來源 |
| G27 | 藍圖與情境的先後 | 藍圖排階段先後（既有內容），情境排活動先後；情境卡跨階段時只引用活動，不寫階段先後 | 粒度與目的不同 |
| G28 | 卡名 | 活動的集合稱「活動清單卡」，服務藍圖一個階段一張；APQC 層級表的「流程」層改稱活動清單；只改名，結構不動 | 台灣用法的「流程」帶先後，會誤導 |
| G29 | 活動清單卡的存放 | 依服務藍圖分資料夾 | 卡數多 |
| G30 | 執行細節預設 | 編號：OP-單據代碼-流水號、ACT-代碼-流水號，不改不重用；服務藍圖改造為流程群組，留 04；流程架構總卡放 04；受控清單卡放 04 營運規則；單據存取範圍卡拆解後刪除；盲測受測者用 Sonnet；撰寫盲測以執行角色、範圍、依據欄位、操作四欄與標準答案一致為通過；查詢盲測以新結構全對、對照組錯誤落在本次錯誤種類為通過；新增活動清單卡規範、骨架、範例，改實體、狀態機、角色、情境四種規範 | Miles「先這樣試看看」 |
