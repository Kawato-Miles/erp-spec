# 需求單 PRD 試寫（Project 與 Feature 票）

試寫日期：2026-10-04，第五版。目的：讓 Miles 看到 Project、Feature 票、功能節三層各裝什麼，以及精簡後的功能節怎麼寫。
本檔是草稿，不是正本。

## 〇、三層怎麼分

| 層 | 回答的問題 | 顆粒度 | 需求單的例子 |
|----|-----------|--------|-------------|
| Project | 這個模組為什麼存在、誰用它做什麼、要做哪幾塊 | 一個平台的一個模組 | 中台 - 需求單管理 |
| Feature 票 | 這一塊做完，使用者能完成什麼事 | 一張票一個需求主題，開發排程與驗收的單位 | 需求單建立／成本評估與報價／需求單結案與轉單 |
| 功能節 | 使用者在這一塊能做的一個動作，以及系統要守的規則 | 一節一個動作 | 印件項目建立、送印務評估 |

Project 的 Scope 清單一條對一張 Feature 票。Feature 票的每個功能節是一個動作，節名用「受詞＋動詞」寫。

功能節固定段落，每段編號各自從 1 開始：

| 段 | 寫什麼 | 不寫什麼 |
|----|-------|---------|
| 使用者故事 | 身為誰，要做什麼，為了什麼 | 功能說明句 |
| 實體關係 | 這個動作牽涉的單據與項目怎麼對應：一對多、一對一、帶入、共用 | 欄位清單 |
| 驗證規則 | 流程面的受理條件：狀態條件、必填是否填齊、前置是否完成 | 單一欄位的必填或值域，Prototype 已呈現 |
| 算式 | 金額、數量、日期怎麼算 | 畫面怎麼顯示 |
| 驗收 | 用 Prototype 既有資料寫的具名案例，條列由 1 起 | 泛稱的「某筆」 |

權限寫在 Feature 票票頭一張表，三欄：權限名稱、動作、範圍。範圍詞彙固定：全公司、自己負責、被指派、被分享。哪個角色預設持有哪些權限，另在角色權限管理維護，不寫在功能票。狀態條件寫在功能節的驗證規則段。

## 一、Project：中台 - 需求單管理

### 概述

需求單讓客戶還在談、尚未成交的印刷需求有一張獨立的單據承載。談成時業務一鍵轉出訂單，談不成時留下流失原因。

現行報價靠業務與印務主管在 Slack 討論，客戶的參考檔散在對話裡，印務主管估價常漏看或回頭問。談不成的需求沒有收尾出口，管理層看不出輸單輸在哪。

### 使用情境

1. 業務接到詢價，建立需求單，逐筆登記印件項目與難易度，掛上參考檔。
2. 業務指定印務主管送出成本評估。
3. 印務主管填妥各筆成本。
4. 業務按評估完成，與客戶逐件談單價。
5. 客戶接受時業務標記成交並轉出草稿訂單；不接受時標記流失並選原因。
6. 客戶回頭時業務重新啟動已流失的需求單。

### Scope

| Feature 票 | 做完後使用者能做到什麼 |
|-----------|---------------------|
| 需求單建立 | 業務把客戶要印的東西登記成一張需求單並送出成本評估 |
| 成本評估與報價 | 印務主管填成本、業務拿到報價依據並與客戶談定單價 |
| 需求單結案與轉單 | 業務把談成的需求單轉成訂單、談不成的收掉或重啟 |

Out of Scope：成交轉訂單後各欄位在訂單上的行為歸中台 - 訂單管理。需求單的分享與職務代理沿用單據分享規則，不在本 project 另寫。

### 狀態機

需求單狀態機圖依 wiki 需求單狀態卡轉繪，此處略。

## 二、Feature 票：需求單建立

標題：[ Feature ] - 需求單建立
Milestone：需求單主流程

### 概述

這張票做完，業務能把客戶的詢價登記成一張需求單，逐筆登記印件項目，並送給印務主管評估成本。

### 權限

| 權限名稱 | 動作 | 範圍 |
|---------|------|------|
| 檢視需求單模組 | 檢視需求單列表與詳情 | 自己負責，或被分享 |
| 檢視全公司需求單 | 檢視需求單列表與詳情 | 全公司 |
| 編輯需求單模組 | 建立需求單、修改單頭、新增修改刪除印件項目、上傳刪除參考附件、送印務評估 | 自己負責，或被分享編輯 |

>>> ### 需求單建立

身為業務，我要把客戶的詢價開成一張需求單，以讓後續的估價、報價都掛在同一個對象上。

**實體關係**

1. 一張需求單屬於一個客戶，窗口聯絡人從該客戶底下的聯絡人選。
2. 從諮詢轉來的需求單記來源諮詢單，一對一，諮詢人員成為接單業務。

**驗證規則**

1. 建立需求單時驗證必填欄位是否填寫，未填齊則無法建立。

**驗收**

1. 假設業務填齊必填欄位、客戶為喜互惠量販股份有限公司、窗口許雅琪，當儲存，則需求單狀態為需求確認中、接單業務與建立者皆為該業務。
2. 假設業務有必填欄位未填，當儲存，則無法建立。

>>>

>>> ### 印件項目建立

身為業務，我要逐筆登記客戶要印的東西與數量，以讓印務主管有規格可估、客戶有金額可談。

**實體關係**

1. 一張需求單有多筆印件項目。每筆可掛多個參考附件、可選多條預計產線。
2. 印件項目是需求紀錄，不是印件。印件在成交轉訂單時才由系統建立。

**驗證規則**

1. 新增或修改印件項目時驗證必填欄位是否填寫，未填齊則無法儲存。
2. 需求單在成交或流失時，印件項目不可新增、修改、刪除。

**算式**

```
小計 ＝ 數量 × 單價，四捨五入至整數元
未稅金額 ＝ 全部印件項目小計加總
稅額 ＝ 未稅金額 × 5%，四捨五入至整數元
含稅總額 ＝ 未稅金額 ＋ 稅額
```

1. 單價為未稅，可到小數點後兩位。
2. 小計算出即定案，之後訂單、收款、發票都用這個整數，不再用單價回算。
3. 數量改動時用既有單價重算小計，單價不動。
4. 需求單不含運費與折扣，成交轉訂單後在訂單上填。

**驗收**

1. 假設 Q-20260601-01 的會員卡（客製燙金）數量 5,000、單價 9.8，當儲存，則小計 49,000、未稅金額 49,000、稅額 2,450、含稅總額 51,450。
2. 假設 Q-20260905-01 的福利禮盒外包裝數量 800、單價 18.75，當儲存，則小計 15,000。
3. 假設上一條數量改為 801，當儲存，則小計 15,019、單價仍為 18.75。
4. 假設 Q-20260601-01 已成交，當業務修改印件項目，則系統拒絕。

>>>

>>> ### 送印務評估

身為業務，我要指定印務主管協助估成本，以在報價前拿到可靠的成本。

**實體關係**

1. 一張需求單可指定多位評估印務主管。
2. 被指定的印務主管自動取得這張需求單的編輯分享，移出名單即撤銷。這份分享不含刪除需求單。
3. 送出後接單業務仍可增減評估印務主管。

**驗證規則**

1. 需求單在需求確認中才可送印務評估。
2. 任一印件項目難易度未填時不可送評估，系統列出缺漏的印件項目。

**驗收**

1. 假設一張新建需求單有兩筆印件項目、其中一筆難易度未填，當業務送印務評估，則系統拒絕並列出該筆，狀態仍為需求確認中。
2. 假設兩筆難易度皆已填，當業務送印務評估，則狀態轉待評估成本。
3. 假設 Q-20260905-01 的評估印務主管為吳國豪，當吳國豪開啟該需求單，則可改成本估算與預計產線，無送評估、新增印件、刪除。

## 三、Feature 票：成本評估與報價

標題：[ Feature ] - 成本評估與報價
Milestone：需求單主流程

### 概述

這張票做完，印務主管能把成本填進需求單，業務能按評估完成留下報價依據，再與客戶談定單價。

### 權限

| 權限名稱 | 動作 | 範圍 |
|---------|------|------|
| 填寫需求單成本 | 修改印件項目的成本估算、預計產線 | 自己負責、被分享編輯，或被指派 |
| 編輯需求單模組 | 評估完成、進入議價、重新評估、修改單價、成交 | 自己負責，或被分享編輯 |

>>> ### 成本估算填寫

身為印務主管，我要把各筆印件項目的成本填進需求單，以讓業務直接拿到數字、不必在 Slack 來回。

**實體關係**

1. 每次修改成本估算，系統記下修改人與時間。

**驗證規則**

1. 自己負責或被分享編輯者，在需求確認中、待評估成本、已評估成本可改成本。
2. 被指派者，在待評估成本、已評估成本可改成本。
3. 議價中任何人不可改成本，要改須先重新評估。

**驗收**

1. 假設 Q-20260905-01 停在待評估成本，當吳國豪把福利禮盒外包裝的成本估算改為 9,800，則該筆成本估算 9,800、修改人吳國豪。
2. 假設 Q-20260906-01 停在議價中，當吳國豪修改成本估算，則系統拒絕。

>>>

>>> ### 評估完成

身為業務，我要在成本填齊後按評估完成，以留下一份當下的報價依據。

**實體關係**

1. 按評估完成時系統寫入一筆報價紀錄，內容為各印件項目當下的成本估算、單價、小計與利潤率。一張需求單有多筆報價紀錄，輪次遞增。
2. 報價紀錄的評估者為按評估完成的人。

**驗證規則**

1. 需求單在待評估成本才可評估完成。
2. 任一印件項目成本估算為空時不可評估完成，系統列出缺漏的印件項目。單價未填不擋。

**算式**

```
利潤率 ＝（小計 − 成本估算）÷ 小計
```

算式正本在 wiki 生產績效指標，本票引用。

**驗收**

1. 假設 Q-20260905-01 的福利禮盒外包裝成本估算 9,800、單價 18.75、小計 15,000，當業務按評估完成，則狀態轉已評估成本、報價紀錄一筆、利潤率 34.67%。
2. 假設 Q-20260905-01 的成本估算為空，當業務按評估完成，則系統拒絕並列出該筆。

>>>

>>> ### 報價與成交

身為業務，我要用談定的單價標記成交，以讓訂單拿到的金額就是談好的數字。

**實體關係**

1. 議價中按重新評估，需求單回待評估成本。舊報價紀錄保留，再次評估完成會新增一筆。

**驗證規則**

1. 需求單在已評估成本才可進入議價，不需業務主管審核。
2. 需求單在議價中才可修改單價、重新評估、成交。
3. 任一印件項目單價為空時不可成交，系統列出缺漏的印件項目。
4. 成交後單頭與印件項目全部不可修改。

**驗收**

1. 假設 Q-20260906-01 的耶誕禮盒吊卡單價 6.2、數量 3,000，當業務按成交，則狀態轉成交、小計 18,600 不變。
2. 假設一張議價中的需求單有一筆印件項目單價為空，當業務按成交，則系統拒絕並列出該筆。
3. 假設 Q-20260906-01 停在議價中、報價紀錄一筆，當業務按重新評估後再按評估完成，則狀態回已評估成本、報價紀錄兩筆。

## 四、Feature 票：需求單結案與轉單

標題：[ Feature ] - 需求單結案與轉單
Milestone：需求單主流程

### 概述

這張票做完，業務能把成交的需求單一鍵轉成訂單，把談不成的記原因收掉，客戶回頭時重新啟動，不要的刪掉。

### 權限

| 權限名稱 | 動作 | 範圍 |
|---------|------|------|
| 編輯需求單模組 | 建立訂單、標記流失、重新啟動 | 自己負責，或被分享編輯 |
| 刪除需求單 | 刪除需求單 | 自己負責，或被分享編輯。因評估指派取得的分享不含 |
| 改派需求單接單業務 | 更換接單業務 | 全公司 |

>>> ### 成交轉訂單

身為業務，我要一鍵把成交的需求單轉成訂單，以免重打一次內容、金額也不會抄錯。

**實體關係**

1. 一張需求單只能轉出一張訂單，訂單反向記來源需求單。
2. 單頭帶入訂單：客戶、窗口聯絡人、接單業務、帳務公司、發票開立方式、出貨方式、收款條件備註。
3. 每筆印件項目建成一張印件，帶入：品名、印件屬性、數量、單位、單價、小計、難易度、是否免審稿、稿件備註、未扣急件內部完成日、出貨方式、包裝備註。小計原值帶入，不重算。
4. 印件項目的參考附件轉為訂單的其他附件，用途說明記為需求單參考附件。
5. 成本估算不轉。印件的預計成本另由工單計價彙總。

**驗證規則**

1. 需求單在成交且尚未轉單才可建立訂單。

**驗收**

1. 假設 Q-20260907-01 已成交未建單、春季新品型錄內頁單價 5.5、數量 5,000、小計 27,500、難易度 3，當業務建立訂單，則新訂單為草稿、該印件小計 27,500、難易度 3、需求單顯示該訂單編號。
2. 假設上一條訂單已建立，當業務再建立訂單，則系統拒絕。

>>>

>>> ### 流失與重新啟動

身為業務，我要把談不成的需求單記下原因收掉，以讓輸單原因可以統計；客戶回頭時再把它叫回來。

**驗證規則**

1. 需求單在任一非終態才可標記流失，流失時驗證流失原因是否已選，未選則無法流失。
2. 流失後需求單全部鎖定，唯一出口是重新啟動。
3. 需求單在流失才可重新啟動，重啟時驗證重啟原因是否填寫，未填則無法重啟。系統清空流失原因與流失補充說明，需求單回待評估成本。

**驗收**

1. 假設一張待評估成本的需求單，當業務標記流失且未選流失原因，則系統拒絕。
2. 假設一張流失的需求單，當業務重新啟動並填重啟原因，則狀態轉待評估成本、流失原因與流失補充說明為空。

>>>

>>> ### 需求單刪除

身為業務，我要刪掉開錯或不再需要的需求單，以讓列表只剩真的在談的單。

**實體關係**

1. 刪除為軟刪除，資料保留、不再出現在清單。
2. 已轉訂單的需求單被刪除後，訂單保留，只失去來源需求單連結。

**驗證規則**

1. 任何狀態都可刪除。

**驗收**

1. 假設 Q-20260601-01 已成交並轉出 ORD-2026-0601，當業務刪除該需求單，則需求單自列表消失，ORD-2026-0601 仍存在且來源需求單為空。

>>>

>>> ### 接單業務改派

身為業務主管，我要把需求單換給另一位業務，以在人員異動或離職時不讓單子斷頭。

**實體關係**

1. 改派記理由分類與補述，離職交接時清空分享成員。做法同訂單的改派接單業務。

**驗證規則**

1. 需求單在成交或流失時不可改派。
2. 改派時驗證理由分類是否已選，未選則無法改派。

**驗收**

1. 假設 Q-20260905-01 接單業務洪嘉駿，當業務主管改派給許雅雯並選理由，則接單業務為許雅雯。
2. 假設 Q-20260601-01 已成交，當業務主管改派，則系統拒絕。

>>>
