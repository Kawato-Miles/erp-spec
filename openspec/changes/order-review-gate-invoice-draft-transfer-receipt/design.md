| 項目 | 內容 |
|------|------|
| 拍板正本 | `memory/erp/wiki-iteration-20261004/grill-decisions.md`（第二輪裁決取代前文衝突處） |
| 設計方案 | `memory/erp/wiki-iteration-20261004/design.md`（第四輪，plan-audit 無未通過項） |
| 變動分級 | 結構性變更：新增兩張衍生狀態機卡、印件狀態拆卡、發票狀態新增狀態、收款項目對發票的基數改寫 |
| Prototype 位置 | erp repo `prototype/dispatch-and-shipping` 分支，只動 `apps/erp/src/app/(prototype)/` |
| 驗收 | Sens `erp-prototype-tests/`，mock 唯一正本為 `(prototype)/MOCK-DATA-CHAIN.md` |

2026-10-05 三條補充裁決對本 change 的影響：

| 裁決 | 影響 |
|------|------|
| 收款項目狀態拆為「收款項目開發票狀態」「收款項目收款狀態」兩卡 | order-billing 的「BillingInstallment 雙維度狀態機」改名並改寫為兩條狀態各自推進 |

| 應收總額為 0 時收款項目預計金額可填 0 | 送審條件「至少一期」在零元訂單也能成立；Prototype 的預計金額欄不設下限 |

約束：

- wiki 是商業規則、欄位與狀態列舉的正本；spec 只寫系統承諾與驗收條目，Prototype 是介面正本。
- 現場回報介面（點收、報工）要能在手機寬度操作；辦公角色介面只支援桌機。
- 本 change 修改 `floor-transfer-no-return` 新增或修改的 production-execution Requirement，以那份 change 的版本為基底。

## Goals / Non-Goals

### Goals

- 線下單送審前，主管就看得到四格備註與各期收款項目；核准當下條件已不齊時擋下。
- 訂單成立前不做的印件可以整筆刪掉，金額當下重算。
- 開票資訊不齊時可以先存草稿；開立失敗有地方停、有原因可看；同一期不會出現兩張未作廢發票。
- 收貨人照實點收；短少不再逼作廢重開，差額由來源任務停在「待點收」看得到。
- 報工錯了可以直接改，改動留前後值與原因。
- 生產任務列表看得出每一筆的轉交進度、交付進度與所屬產線。

### Non-Goals

- 凍結量、生管結案、補點收、數量異常標記、生管異常清單（拍板 § 五取消）。
- 「貨已在現場」建單分流、已送達單作廢重開（拍板 § 五取消）。
- 發票「處理中」狀態、草稿單獨刪除、審核當下的快照（拍板 § 五、§ 六）。
- 短少多收互抵、點收二次確認、待驗量扣短少、單條明細作廢、良品 0 觸發通知（拍板 § 六）。
- 設備主檔所屬產線的任何改動（拍板 § 六）。
- 排程與工廠總覽的產線視角改看產線欄：wiki 已定，但沒有對應的業務情境卡步驟，本 change 不寫 Requirement（見 Open Questions 後的「未寫入清單」）。
- 後端資料模型與 API 形狀。

## Decisions

### 1. 送審條件擋在按鈕，缺項當場列出

| 項目 | 內容 |
|------|------|
| 決策 | 「送主管審核」按鈕在條件不齊時停用，按鈕旁列出缺哪幾項（四格備註逐格列、收款項目列「至少一期」）。業務主管按「核准訂單」時系統重檢，不齊即擋下並以同一份缺項清單提示 |
| 替代方案 | 按下才檢核、彈出錯誤；核准時存一份審核快照 |
| 否決理由 | 按下才檢核會讓業務反覆試送。快照由拍板 § 六否決：核准看當下內容就夠，快照只多一份要對齊的資料 |
| Prototype 呈現 | 缺項清單用既有提示元件；核准擋下沿用同一份清單，不另做對話框 |

既有「空收款條件備註核准需二次確認」對話框隨之移除：送審已要求收款條件備註有值，核准重檢也會擋下，這個對話框不再有觸發時機。

### 2. 成立前刪除印件只放在印件列操作欄

| 項目 | 內容 |
|------|------|
| 決策 | 訂單成立前（線下單尚未首次進入「已回簽」），印件列操作欄出現刪除圖示，按下出確認對話框；刪除後活動紀錄留一筆「刪除印件 X」。成立後與線上單等待付款期間不渲染此圖示 |
| 替代方案 | 成立前也走「已棄用」；刪除時同時記錄被刪印件的購買數量與金額 |
| 否決理由 | 棄用會留下沒有生產事實的空殼印件（拍板第 2 條）。活動紀錄內容依拍板原文只留名稱 |
| Prototype 呈現 | 階段未到的操作鈕直接隱藏，不做停用加提示（既有 Prototype 慣例） |

刪除後應收總額重算、收款項目合計對不上時沿用既有差額提示、出貨單草稿自動移除該列，規則正本在 [明細時點分界](../../../memory/Sens_wiki/wiki/erp/04-business-logic/營運規則/訂單到交付/明細時點分界.md)。

### 3. 發票：草稿是發票狀態的初始態，不是另一個實體

| 項目 | 內容 |
|------|------|
| 決策 | 收款項目列只有「開立發票」一顆圖示：該期沒有未作廢發票或只有草稿時顯示（有草稿時帶入草稿），有開立或開立失敗的發票時不顯示。草稿不列在發票區；藍新回傳失敗或逾時轉開立失敗，列在發票區並顯示原因，業務端沒有操作，由後端人員在系統外刪除紀錄或補登號碼 |
| 替代方案 | 草稿另存一張暫存單；送出後標「處理中」排他 |
| 否決理由 | 另存暫存單會讓一期一張的檢查要跨兩種單據判斷。「處理中」由拍板 § 五否決，改以寫入當下檢查一期一張擋重複送出 |
| Prototype 呈現 | 開立視窗只有一種，內有「儲存草稿」（不檢核）與「開立」（送出時檢核）兩顆按鈕。被系統擋下時視窗不關並列出缺項，有草稿者維持草稿；藍新回應以單選模擬成功、回傳失敗、逾時，失敗或逾時時視窗關閉、發票轉開立失敗並列在發票區 |

放棄草稿不另設刪除鈕，業務取消該期收款項目即可，草稿一併消失（拍板第 3 條、§ 六）。

### 4. 收款項目兩條狀態改為兩個 Requirement 名稱下的同一組承諾

| 項目 | 內容 |
|------|------|
| 決策 | 既有「BillingInstallment 雙維度狀態機」以 RENAMED 改名為「收款項目開發票狀態與收款狀態」，內容改寫為兩條狀態各自推進並分別引用兩張 wiki 卡 |
| 替代方案 | 刪除舊 Requirement 再新增兩個 |
| 否決理由 | 刪除再新增會讓既有交叉引用全部斷掉；改名保留同一個區塊，封存時只動標題與內容 |

### 5. 點收：逐條填量、可多次點收、可修改，全部留在點收紀錄

| 項目 | 內容 |
|------|------|
| 決策 | 點收對話框逐條明細列出設定量，點收量欄預設帶設定量、可改成 0 至設定量。單頭已點收後，轉交單側板每條明細出現「再次點收」，預設帶設定量減點收累計。每條明細下展開點收紀錄，每筆可按「修改」填新數字與原因 |
| 替代方案 | 點收純確認、短少作廢重開（現行）；凍結量加生管結案（第一輪設計） |
| 否決理由 | 純確認逼現場對已送達的貨重走搬運與送達（拍板第 4 條）。凍結與結案由拍板 § 五取消：差額由設定量與點收累計的差、加上來源任務停在「待點收」就看得到 |
| Prototype 呈現 | 點收對話框沿用現場手機寬度版面；修改原因為必填文字框；擋下時訊息寫出是哪一條（超過設定量，或低於下游已報工量） |

點收、再次點收、點收修改的擋下條件與檢核時點，正本見 [場內轉交與更正](../../../memory/Sens_wiki/wiki/erp/07-scenarios/場內轉交與更正.md)。

### 6. 已送達不作廢、簽收照片逐條

| 項目 | 內容 |
|------|------|
| 決策 | 已送達的單在一般情況下不渲染作廢鈕；任一明細的來源任務已轉報廢或已作廢時，生管才看得到作廢鈕。抵達站點對話框逐條明細各有一個照片上傳格，任一條沒照片時送出鈕停用並列出缺照的明細 |
| 替代方案 | 已送達仍可作廢重開並勾「貨已在現場」 |
| 否決理由 | 拍板 § 五：作廢重開一律重走搬運與送達，不設「貨已在現場」；已送達的單數量不對就照實點收 |
| Prototype 呈現 | 轉交單側板單頭的「貨已在現場」格移除，簽收照片改列在明細表 |

### 7. 報工修改與作廢共用一組擋下條件

| 項目 | 內容 |
|------|------|
| 決策 | 報工紀錄列多一顆「修改」，對話框只開放生產數量、良品數、不良品數三欄與必填原因。擋下時訊息列出命中的條件與佔用的轉交單號 |
| 替代方案 | 只能作廢重報（現行）；修改另開一套擋下條件 |
| 否決理由 | 已完成任務的作廢被擋，短少就無法更正（拍板 § 五、§ 七）。兩套擋下條件會讓同一筆錯誤因更正方式不同而有兩種結果 |
| Prototype 呈現 | 已完成任務的報工列只顯示「修改」，不顯示「作廢」；修改紀錄在報工列下展開唯讀列出 |

既有 Requirement「報工作廢與留痕」以 RENAMED 改名為「報工修改、作廢與留痕」並改寫，報工修改與作廢的承諾放在同一處。擋下條件正本在 [場內轉交與更正](../../../memory/Sens_wiki/wiki/erp/07-scenarios/場內轉交與更正.md) 副流程。

### 8. 生產任務列表三個狀態欄

| 項目 | 內容 |
|------|------|
| 決策 | 工單詳情的生產任務列表帶出「生產任務狀態」「轉交狀態」「交付狀態」三欄與「轉交量 N／點收量 M／良品 K」進度文字，不另設貨已送達、待點收的標記。現場執行群組欄序為生產任務狀態、交付狀態、轉交狀態、轉交進度、完成量；完成量只顯示當前報工累計，下行良品與不良品。轉交狀態與交付狀態只讀，由系統依當下數字推導 |
| 替代方案 | 把轉交與交付進度併進生產任務狀態 |
| 否決理由 | 拍板第 7 條與新版狀態機規範：一張卡一個狀態機，同一實體的另一條進度線另開卡 |
| Prototype 呈現 | 推導函式放在 `(prototype)` 的共用計算檔，畫面只取結果；「－」以既有無值符號呈現 |

### 9. 產線欄與交付時間

| 項目 | 內容 |
|------|------|
| 決策 | 生產任務表單多一個必填的產線單選，建立時從所引用的部件配方工序段帶入，工序段沒有時留空待印務選。工單詳情多一顆「全部交付」，一次把旗下全部生產任務寫入交付時間 |
| 替代方案 | 產線沿用計畫設備的所屬產線推導（現行 spec） |
| 否決理由 | 拍板第 6 條：外發任務沒有我方設備，推導不出產線；產線歸戶改看本欄、不與計畫設備比對 |
| Prototype 呈現 | 產線選項取 mock 的產線標籤清單，外發用值由 mock 自行新增，不寫死 |

## Risks / Trade-offs

| 風險 | 緩解 |
|------|------|
| 報工與點收開放修改，改數字可能掩蓋短少 | 拍板 § 七接受此風險，以留痕承擔：報工修改紀錄與轉交單歷程記修改前後值、修改人、時間、原因（必填），事後查紀錄 |
| 首次點收由一人填完全部明細，其他明細直接沿用預設值 | 點收紀錄記按下的人；數錯由收貨人修改並填原因（拍板 § 七） |
| 搬運遺失以修改來源任務報工更正，遺失量計入來源任務折損率 | wiki [報工紀錄](../../../memory/Sens_wiki/wiki/erp/05-entities/報工紀錄.md) 修改原因欄填「搬運遺失」，事後可區分；不另設欄位 |
| 短少一直不處置時，來源任務停在「待點收」 | 拍板接受；停在這格就是目視化的停下訊號，不另做通知升級 |
| 報工改低後貨又找回，轉交點收量大於良品數 | wiki [生產任務轉交狀態](../../../memory/Sens_wiki/wiki/erp/06-state-machines/生產任務轉交狀態.md) 已定：點收不擋，推導落在「轉交中」，進度文字看得出差異 |
| 線下單送審前的議價修改也會累加收款項目變更次數 | 拍板 § 六接受：原始日凍結與變更次數維持首次儲存起算 |
| 兩筆數量動作同時寫入 | 以寫入當下數字判定，先寫入者成立，後到者重新檢核 |
| 本 change 與 `floor-transfer-no-return` 修改同一批 Requirement | 以該 change 的版本為基底撰寫，封存順序固定（見 Migration Plan） |
