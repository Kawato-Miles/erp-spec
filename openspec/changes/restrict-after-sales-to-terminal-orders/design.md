## Context

售後服務單的建單前提在 spec 與 wiki 之間出現方向相反的兩版：spec 寫「建單零前提」，wiki 正本已於 2026-08-28 收緊為「限終態訂單」。本 change 只把 spec 這一面對齊，不引入新機制。

現況約束：

- 後端 `sens-print-core` 已實作建單狀態檢查，但只放行「訂單完成」；已取消訂單建不了單。
- 訂單異動的終態守門（終態訂單未掛售後服務單即擋下）已上線，本 change 不動它。
- 開發修正已以留言交付 Linear BE-169，前端調整已交付 FE-378。

## Goals / Non-Goals

### Goals

- `after-sales-ticket` spec 的建單前提與 wiki 正本一致。
- 受理段與決議段的把關條件在 spec 內只有一套說法。
- 已取消訂單的售後受理與退款路徑在 spec 內走得通。

### Non-Goals

- 不改訂單異動的終態守門。
- 不處理諮詢取消退費撞上終態守門的矛盾（見 ORD-049，另案）。
- 不改決議處理方式的內部鍵值（顯示文字改「補做」，鍵值維持現狀）。
- 不做補做的聯動與相關印件欄位（與 BE-169 範圍段一致）。

## Decisions

**以「移除既有 Requirement ＋ 新增取代 Requirement」處理建單前提，不用同名 MODIFIED。**
原 Requirement 名為「售後服務單建單零前提」，收緊後名實不符。同名改寫會留下一個標題與內容相反的條文，日後搜尋「零前提」仍會命中。替代方案是 RENAMED ＋ MODIFIED 兩段操作，但 delta 的 RENAMED 只處理改名、內容仍要另寫一段，反而多一層。

**決議段的四個選項改為恆可選，一併移除「補做限印件已送達」這道判定。**
該判定是收緊前的產物：當時售後單可在生產中建立，才需要用印件狀態擋掉做不到的補做。收緊後售後單只存在於終態訂單，判定的適用面消失；且 2026-08-28 拍板決議四值全開由業務判斷。留著會與 wiki 正本相反。替代方案是保留判定但改條件，代價是系統要替業務判斷它看不到的事實（與客戶談的結果、現場還有沒有料）。

**單內金額動作的入口不再各自檢查訂單狀態。**
三處條文（與 OrderAdjustment 關聯、OA 連動、退款三組件）原本各寫一次「不依訂單終態開關」。收緊後售後單只存在於終態訂單，這道檢查在建單那一關已經做完，單內重複檢查是同一把關做兩次。三處統一改為引用建單前提。

## Risks / Trade-offs

- **製作中的客訴在系統內無處記錄** → 已知取捨，Miles 2026-08-28 接受。既有處理路徑（改印件明細、建訂單異動、退回審稿、品檢補做）各自承接；客訴脈絡寫在訂單活動紀錄或異動備註。
- **spec 內殘留「售後服務單內新增請款期次」條文，與 BE-169「售後服務單內不建請款期次」相反** → 屬本 change 之外的既有落差，另案處理，不在本次修正範圍。
- **既有已建立的售後服務單不受影響** → 規則收緊只影響新建，不回溯既有資料。

## Migration Plan

1. spec delta 併回主 spec（`/opsx:archive` 或 `/opsx:sync`）。
2. 後端依 BE-169 留言調整建單狀態集合、錯誤訊息、顯示文字與測試。
3. 前端依 FE-378 調整建立入口的停用條件與說明文案。
4. 回滾策略：本 change 只改文件，回滾即還原 spec；後端回滾則恢復原有的「僅訂單完成可建」，已取消訂單退款重新回到無路可走的狀態。
