# 設計：出貨單草稿態與品檢待驗清單改版（Prototype 層）

## Context

商業層正本在 wiki（見 proposal § Background）。Prototype 現況（erp repo `(prototype)/qc-shipping/`）：出貨單一步建立即檢核額度、出貨方式與物流商兩欄、送達一律人工；待驗清單自已點收轉交明細彙總、點收者依角色特判。本 change 的 Prototype 已於 0cff790f 落地，本文記錄落地時的設計決策供 spec 與後端對照。

## Goals / Non-Goals

### Goals

- 同一張出貨單承載草稿與正式兩段：草稿只有單頭與預計出貨印件，建立時轉出貨明細；不另立「出貨計畫」實體
- 額度檢核只在建立那一刻跑；草稿的預計數量不進任何額度、累計與收尾算式
- 待驗量為印件層即時推導值（齊套完成數 − 已驗量），不另存欄位、不看轉交
- 點收可見範圔只由人員所屬產線決定；生管、印務、印務主管代點收
- 第三方物流送達兩條路徑共用同一條狀態弧與同一套收尾判定

### Non-Goals

- 物流商介接的技術方式（Prototype 以模擬按鈕代替）
- 打樣印件的待驗量（QC-008 另案）
- 草稿欄位的鎖定時點、預計出貨日正名、草稿對辦公角色的可見範圍（待拍板）
- 品檢站頁的位置視圖或到站量（貨在哪一律查轉交單管理）

## Decisions

- **草稿為狀態、不為實體**：出貨單狀態加「草稿」初始態，預計出貨印件與出貨明細為同一張單上的兩組明細（草稿期只有前者）。替代方案「出貨計畫」獨立實體被否決——同一批貨要在計畫與指令之間再對一次帳，且訂單取消連鎖要多收一層。
- **草稿不屬「未離廠」、出口只有刪除**：作廢弧自未處理起算。替代方案「草稿走作廢」被否決——草稿沒有明細、沒佔額度，作廢紀錄沒有東西可記，理由欄只會被填「不用了」。
- **兩段檢核順序固定、擋下訊息一句**：必填未齊不比額度；額度不足只顯示「可出貨額度不足，出貨單未成立」。替代方案「逐印件列額度並帶兩條出路」被試用回饋否決——業務看到擋下就知道要等品檢或談短出。
- **出貨方式與物流商合一欄六值**：自取、專車配送、順豐、新竹物流、超商、其他；第三方判定以「非自取且非專車配送」為準，選項可增不改流程。自印件出貨方式帶入時三值對六值：自取與專車配送直接對應，第三方物流留空由業務挑。
- **寄件資訊取帳務公司現值、不存副本**：依訂單帳務公司代號對照（SSP、BRO）。替代方案「出貨單存一份寄件欄」被否決——公司抬頭改了舊單會印舊的。
- **「出貨中」觸發點移到草稿轉未處理**：建立草稿不觸發，第二張成立不重複觸發。
- **待驗量即時推導**：對每件印件取其工單清單（同印件詳情頁的取法）餵給既有齊套完成數算式，減去品檢紀錄通過與不通過的代數和；只列齊套完成數大於 0 或已有品檢紀錄者、已棄用排除。替代方案甲（點收才算任務完成）、乙（品檢站到料量兩軌＋目的站點把關）、丙（印件層轉交）皆被否決，理由見 QC-007。
- **驗收上限不夾值**：移除輸入框上限，改在送出時以當下待驗量整筆檢核。替代方案「輸入框自動夾到上限」被否決——600 被悄悄改成 500 成立，帳從這裡開始錯。
- **點收判定三段**：管理角色（生管、印務、印務主管）代點收 → 當前使用者所屬產線含目的站可點收 → 否則不可並說明「不屬於該站」。刪除對品檢人員與師傅角色的特判。
- **第三方送達兩條路徑同一條弧**：模擬物流商回報與人工送達確認都走「運送中 → 已送達」，確認人分別記物流商同步與操作人；收尾判定共用。

## Risks / Trade-offs

- [待驗清單數字與品檢站現場可能不一致（做出來還沒搬到）] → 品檢人員到轉交單管理查貨在哪；品檢站頁首提示句寫明
- [草稿長期未建立，佔著業務清單] → 清單可依狀態篩選；是否加提醒屬後驗，不在本 change
- [六值出貨方式若物流商增加] → 只增選項，第三方判定以排除法寫，不需改流程
- [模擬物流商回報與真實介接行為不同] → 介接屬後端實作；spec 只承諾兩條路徑與收尾一致
