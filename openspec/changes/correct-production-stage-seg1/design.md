商業層設計已定案於 `production-stage-seg1-design.md`（過 plan-audit：0 項未通過；Miles 七項裁決已落 wiki 12 卡）。**本文件只寫實作層的技術決策**，商業規則、欄位、狀態列舉一律不重述，依據見該設計文件與 wiki 正本卡。

實作環境的既有約束：

- Prototype 在 erp repo（Next.js，`apps/erp/src/app/(prototype)/`），分支 `prototype/production-stage`，不開 PR；實作經 `prototype-from-prompt` skill
- 模擬資料由七個模組各自持有（訂單、印件總覽、工單、派單、現場派工、品檢出貨、配方），跨模組目前完全不連動
- 審稿印件詳情頁已存在於 `prepress-review/detail`，含審稿紀錄與活動紀錄兩個 Tab；印件總覽以側邊抽屜承載檢視

## Goals / Non-Goals

### Goals

- 五份 spec 的行為與 wiki 正本一致（含 B1、B9、A3 與段 1 七項裁決）
- Prototype 段 1 動線可從「訂單管理人確認製作細節」一路走到「交付產線與派工派單」，中途不需人工改模擬資料
- 印件詳情頁收斂為單一頁面，審稿與生產階段共用
- 建立跨模組狀態連動的最小可行機制（四條線），為段 2 至段 4 留擴充位置

### Non-Goals

- **不做報工、品檢、出貨、副流程**（歸段 2 至段 4）
- **不建貨運單頁面、不做運費關稅攤回**（歸段 3；認列工單在段 1 暫掛派單介面）
- **不建全域事件匯流排**（四條連動線各自直接通知即可）
- **不動 wiki**（商業層已落卡完成）
- **不做行動版版型**（段 1 全部是辦公角色的桌機介面；現場四介面歸段 2 與段 3）

## Decisions

### D1：印件詳情頁採「搬遷升格」而非「新建並存」

把 `prepress-review/detail` 升格為統一印件詳情頁、路由搬到 `print-items/detail`，舊路由導向新路由；印件總覽的側邊抽屜廢除、內容併入詳情頁。

替代方案是保留抽屜快速檢視、另建詳情頁。不採用的理由：抽屜的四段內容（基本資訊、旗下工單、歷次品檢紀錄、缺口處置留痕）與詳情頁完全重疊，兩套並存等於同一份資訊兩處維護，且使用者無法預期點哪裡看到什麼。

搬遷保留審稿紀錄與活動紀錄兩個 Tab 不動——審稿人員的既有動線不能因為生產階段的需求而退化。

### D2：跨模組連動採「事實單一持有 ＋ 由下往上單向推動」

每個狀態值只有一個模組持有（印件與訂單狀態在訂單模組、工單與生產任務在工單模組、派單在派單模組、工作包與派工在現場派工模組），其他模組要顯示就去讀，不複製自己的值。連動一律由下往上：交付產線推動工單 → 工單推動印件 → 印件推動訂單。

替代方案是各模組各自保有狀態、以同步函式對齊。不採用的理由：兩份值必然分岔，且分岔後無法判斷哪個是真相。單向推動則不設反向回寫——反向會製造第二個真相。

段 1 只接四條線（確認製作細節、外包交付即派單發送、自有交付進待派清單、全部交付推動工單與印件與訂單）；報工推動「製作中」屬段 2、品檢累計屬段 3，此刻不接。

### D3：認列工單段 1 暫掛派單點收介面

wiki 正本是「揀貨人員於貨運單認列工單」（一趟併櫃勾多張工單），但貨運單的其餘內容都屬段 3。段 1 先在派單的點收介面做單張派單視角的認列（這張的貨到了），讓派單走得到「已到貨品檢」；段 3 建貨運單頁面時遷回併櫃視角並接上運費關稅攤回。

替代方案是段 1 就建貨運單頁面。不採用的理由：為了一個動作把整張貨運單拉進來，等於把段 3 尚未定案的成本設計提前做。

此為實作階段的暫置安排、不是商業規則變更，故 wiki 不改。

### D4：spec 的 delta 操作依「標題斷言是否仍成立」選擇

標題本身仍成立、只有內文行為變的用 MODIFIED；標題本身已成為錯誤陳述的用 REMOVED ＋ ADDED（如「外發數量以回廠點收為準」在 B1 之後斷言錯誤，改內文救不回標題）。

改名一律不與內容變更混在同一個 Requirement 上——本 repo 的 archived change 無 RENAMED 先例，混做有 archive 同步失準風險。因此「任務交付」「交期倒推建議日期」兩個標題維持原字，內文的動作名與欄位名全改（交付產線、預計開工日）。

### D5：介面呈現層不寫進 spec

製程規劃的三段區塊與段內拖曳、BOM 下拉不顯示價格、審核佇列的欄位與排序，都只在設計文件與 tasks 承載，不進 spec。依既有分工：spec 管系統行為，介面與互動以 Prototype 為正本。

## Risks / Trade-offs

- **跨模組連動改動七個模組的模擬資料層** → 一次只接四條線、每條線獨立可驗；連動前後的狀態值以既有欄位表達，不新增中介結構
- **印件詳情頁搬遷可能破壞審稿既有動線** → 搬遷後審稿待審清單的點入路徑一併更新；審稿兩個 Tab 的內容與行為不動，只加不改
- **訂單模組的印製狀態與訂單狀態從靜態模擬值改為衍生** → 段 1 之後這兩個值不再可任意設定，模擬資料的初始值需重新校準，否則會出現「初始值與工單事實對不上」的展示錯誤
- **五份 spec 同時改，archive 時的合併衝突面積大** → delta 的 MODIFIED 已逐字比對 main spec 標題（22/22 命中）、`validate --strict` 通過；archive 前再驗一次
- **段 1 暫置的認列工單在段 3 要搬** → 已在設計與 spec 明記暫置範圍，段 3 的差異清單會接住

## Migration Plan

實作順序依相依性分四批，每批可獨立驗證：

1. **規格層**：五份 delta spec（已完成）
2. **入口與詳情頁**：待確認佇列頁、製作討論串、印件詳情頁搬遷升格（前兩者相依於印件的新欄位、詳情頁相依於既有審稿頁）
3. **工單全流程**：加開與刪除空草稿、審核佇列、收回守衛、三段區塊、BOM 無價格、預計開工日、完稿圖唯讀、交付產線改詞
4. **派工與派單**：接收確認、待排區欄位、工作包上機日與移除狀態欄、B9 後派單、認列與點收登記、印務切終態

跨模組連動（D2 四條線）在批 2 至批 4 各自落地，不獨立成批——每條線隨它的動作一起實作與驗證。

回滾策略：Prototype 在獨立分支、未合併 main，任一批出問題可單獨 revert 該批 commit；規格層的 delta 未 archive 前不影響 main specs。
