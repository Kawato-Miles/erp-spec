## Context

終態守門原本套在建立、送審、核可、確認生效四個動作，條件為「訂單在終態且該異動未掛售後服務單」。這造成兩個卡住點：製作期間合法建立、未掛售後服務單的在途單據，訂單一進終態就三個動作全被擋、只能作廢重開；諮詢取消退費由系統在取消動作內建單，建單那一刻訂單已終態又無售後服務單，建不出來也推不動。

設計方案已過 plan-audit 復審（無未通過項）並經 Miles 拍板。本 change 只把 PRD 層對齊，不引入新機制。

## Goals / Non-Goals

### Goals

- `order-adjustment` 與 `consultation-request` spec 與 wiki 正本一致。
- 建立那一關的四條分支在 spec 內可逐條驗收。
- 狀態推進不檢查訂單狀態這條規則有明文，實作者不再沿用舊守門範圍。

### Non-Goals

- 不改認列時點（仍為執行確認生效那一刻）。
- 不改退款送業務主管核可這道把關。
- 不處理重核提示的覆蓋範圍（BI-029，另案）。
- 不為破口新增把關（Miles 裁定不處理）。

## Decisions

**建立分流寫成表格四分支，不寫成散文條件句。**
四條分支的判準是兩個維度相乘（訂單狀態 × 訂單類型），散文會讓實作者漏掉分支三與四的差別。替代方案是只寫「終態須掛售後服務單，諮詢除外」，代價是「諮詢除外」會被讀成整個諮詢類型豁免，而實際上只豁免系統內生的取消退費那一筆。

**諮詢取消退費靠建單排序放行，不在守門條件加類型例外。**
排序寫在流程步驟裡看得見；守門加例外分支則是日後改動容易漏掉的隱性條件。代價是實作若把順序寫反，會回到建不出來的狀態，因此該排序在 spec 內標為 MUST。

**「確認可執行」改回不是終態。**
wiki 狀態列舉是狀態的唯一正本，spec 不得複寫也不得相反。這一處是既存落差，順帶消掉。

## Risks / Trade-offs

- **破口：先建草稿、終態後生效** → Miles 裁定不處理，由對帳的重核提示留下痕跡；已取消訂單不在提示覆蓋範圍（訂單不記取消時間），缺口記於 BI-029。
- **諮詢取消退費後端尚未實作** → 本 change 只定行為契約，實作時機由開發排程決定。
- **關聯層一致性未經資料結構總覽卡驗證** → 訂單管理與款項與發票兩領域尚無總覽卡，本次為逐卡人工比對（plan-audit 5-2 覆蓋降級）。

## Migration Plan

1. delta 併回主 spec，另修 `order-adjustment` § Purpose 的「確認可執行（終態、不可逆）」措辭（Purpose 非 Requirement，於 apply 階段直接改）。
2. 後端調整守門引用範圍與建立分流；前端調整入口可用性。
3. 回滾策略：本 change 只改文件，回滾即還原 spec；後端回滾則回到在途單據跨越終態即死的狀態。
