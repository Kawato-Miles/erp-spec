## Context

清整的難點不在寫新條文，而在「該砍的要砍乾淨」。舊 spec 的過時內容不會讓任何檢查失敗，只會安靜留著等下次撞到——本輪的七處矛盾（工單建立來源散在七卡、派單六值被寫成工單屬性、任務層殘留、QC 單與印件層品檢紀錄並存）全都是這樣累積出來的。

capability 的切法本身也是矛盾來源：`task-dispatch-board` 用介面名當模組、`scheduling-center` 混了待排區與外包追蹤、`production-task` 63 條 Requirement 橫跨工單結構、派工、報工、轉交、QC、成本六件事。沿用舊切法重寫等於把病灶原封不動留下。

## Goals / Non-Goals

**Goals**

- 生產核心三模組的 Requirement 與 wiki 商業正本、Prototype 實際行為三方一致
- 廢除的 capability 不留殘骸，也不留指向它們的引用
- spec 只承載系統行為（Requirement + Scenario + 轉換規則），欄位表與狀態列舉引用 wiki，介面與互動交給 Prototype

**Non-Goals**

- 不改 wiki（商業正本已於 2026-07-30 對齊，本 change 只引用）
- 不做 Phase 切分與開發排期
- 不碰 M4／M5／外圍 spec（批二）
- 不為未實作的機制寫 Requirement（物料庫存量帳、成品庫存、拼版、OEE 三率、行動版皆為掛點）

## Decisions

**一、capability 按模組重組，不沿用舊名**

新切法：`work-order`(M1)／`production-execution`(M2)／`production-overview`(M3)。生產任務的**結構**（展開、欄位帶入、相依、成本凍結）歸 M1，**執行**（派工、報工、轉交）歸 M2，**可視化**（三視角、指標、卡點）歸 M3。判準是「誰在什麼時候操作它」：印務規劃時看到的是工單底下的任務結構，生管與師傅看到的是工作包與報工，管理層看到的是負荷與指標。

代價：`openspec/changes/archive/` 裡的舊 delta 會指向已廢除的 capability。這是歷史記錄，不回改。

**二、任務層移除後的分組職責**

外包分組唯一歸 `dispatch-order`（批二），場內派工分組唯一歸工作包。交付畫面的「按廠商分組」是衍生呈現、不是實體。狀態鏈三層（生產任務 → 工單 → 印件），異動鏈直接生產任務 → 工單鏡像。

**三、展開行為的正本歸 `recipe-expansion`，`work-order` 只留三條建立路徑**

原本兩份 spec 各寫一份展開行為（帶入哪些欄位、生產單位類別怎麼決定、機台留空）。收斂後 `work-order` 的「工單草稿建立」只寫「怎麼來的」（引用 wiki [[工單]] § 建立來源的五建一不建），展開的細節全在 `recipe-expansion`。

**四、BOM 行項目層廢止（PT-037 A 案）**

印件不再持有 BOM 行清單。有配方者由印件配方與部件配方展開；無配方的全客製品由印務直接對 BOM 三類主檔挑項目建生產任務，料工資訊落在生產任務本身。印件層的料工彙總改由印件詳情頁跨工單彙總承接（Prototype 待補，屬批二範圍的介面工作）。

理由：Prototype 現行行為就是 A 案；成本追溯的職能已由「預估成本分項」（展開時凍結四分項）承擔，不需要再留一個快照層。

**五、工單已交付的觸發條件取「全部」**

wiki [[工單狀態]] 定「全部任務交付產線後觸發（取最落後）」，Prototype `deliverTasks` 亦為 `tasks.every(t => t.delivered)`。舊 spec 的「首個任務交付」寫法廢止（PT-028 已拍板，取 wiki）。

**六、五指標全部即時衍生，不存欄位**

時間稼動率、良率、折損率、毛利率、成本達成率一律由報工事實即時算（Prototype `calcMetrics` 亦如此）。不新增指標欄位、不做快照，避免出現「指標欄位與報工事實對不上」的第二個真相。

## Risks / Trade-offs

- **一次重寫三個模組，verify 負擔集中在最後**：以機械檢查（六項 grep，成功條件皆為零命中）＋對抗式找漏補足，不只靠人工讀。
- **廢除五個 capability 會讓 archive 裡的舊 delta 路徑失效**：接受，歷史層不回改；但 main specs 內不得留任何指向已廢除 capability 的引用（列入驗收檢查）。
- **M6 併入本 change 會擴大 diff**：換到的是 M1 與 M6 不會在中間狀態互相打架。

## Migration Plan

無資料遷移。生產階段尚未交付 Linear、尚未進入 `erp` repo 的正式實作，Prototype 為靜態 mock。

執行順序：先廢除五個 capability 並清掉指向它們的引用 → 再寫 M1 → M2 → M3 → 最後補 M6 三處校對，讓 M6 對 M1 的引用在 M1 定稿後才寫。

## Open Questions

擋本批的 OQ 於 apply 前集中裁決，判準是「不裁決就寫不出 Requirement 或 Scenario」。已知擋批一的候選：

- `PT-006` 工單欄位修改規則（決定哪些欄位在哪個狀態可改，直接影響 M1 的 Scenario 守衛）
- `PT-021` 外發生產任務數量取數與到料判定（影響 M1 的數量欄位與 M2 的到料放行）
- `XM-009` 合批派工合併邏輯（影響 M2 的工作包建立條件）
- `PT-007` 前置受影響警示通知對象與形式（影響 M2 的派工把關提示）

不擋本批的（在 spec 中引用 OQ 卡、不寫入行為）：`PT-013` 倒扣耗料口徑、`PT-015` 供應商月結對帳、`PT-023` 材料用量帳與放損換算鏈正本歸屬、`PT-026` 外部廠商協作門戶、`PT-027` 製作中單價變更。

已判定議題不成立、待封存：`PT-032`（工單類型二值與六值的收斂——六值經查證為派單自身欄位，本無收斂問題）。
