## Context

現況交期推導鏈只掛在訂單單頭一個欄位（訂單的「客戶交期」），旗下每件印刷品的承諾日一律由它減掉急件天數算出，無法同單各件各自談定交期。交期在需求單、訂單、印件、工單四層各有不同名稱（客戶期望交期／客戶交期／訂單交期（扣除急件）／印件交期），開發重複實作、讀單的人分不出哪個是對客戶承諾、哪個是系統內部算的。

商業層設計已拍板並落卡（wiki commit 11a534c）：印件新增獨立、選填的「訂單交期」欄；印件「預計交期」改算式（訂單交期 − 1 − 急件選項凍結天數）；訂單「客戶交期」改名「訂單交期」、刪除「是否急件」欄。本 change 只處理系統行為規格（Requirement / Scenario）與交付層（Prototype、測試）的同步，不重新做商業層設計決策。

約束：本次不新增資料表或關聯（總覽差異零條，見設計方案第十二節），全部是既有實體的欄位新增／改名／改算式；平台限制沿用現行（僅桌機瀏覽器）。

## Goals / Non-Goals

### Goals

- 四份既有 spec（order-management、quote-request、work-order、prepress-review）的 Requirement 與 Scenario 與 wiki 正本一致，交期算式、欄位可編輯性、通知規則三處全部同步。
- Prototype 七處介面與 mock 主鏈反映新交期模型，並補齊對應測試情境。
- 後端已知落差（印件建立 API 不收印件類型與急件選項、`is_urgent` 廢除、審稿前後預計出貨日落差）明確標記為 Linear 另案，不在本 change 施工範圍內誤植。

### Non-Goals

- 不重新裁決商業規則——訂單交期算式、通知與否、欄位必填/選填等拍板已由 wiki 落卡定案，本 change 不重跑釐清。
- 不處理準時交貨率指標的取數層級下沉（OQ ORD-050，另案）。
- 不新增審稿「交期未定」標記、不新增交期逾期提醒——這些是設計方案明確列出的「不支援」項，本 change 延續不做。
- 不動 wiki 任何卡（已於本 change 之前落地）、不動 openspec/specs/ 主 spec（只寫本 change 的 delta）。

## Decisions

**D1：交期算式下沉到印件層，訂單層交期不再參與任何印件推導**
印件的「預計交期」＝印件自身的「訂單交期」− 1 天 − 急件選項凍結天數。訂單層「訂單交期」只作為單頭參考值：列表篩選依據、內部製作截止日預設來源、新增印件時的預設值。取代方案（維持訂單層單一推導源、靠急件等級各自加減）已被現況證明無法處理「同單名片趕、型錄不趕」的真實情境，故不採。

**D2：欄位必填改為選填，空值不補、不擋**
需求單印件項目與新增/加開印件的「訂單交期」皆為選填；轉單、加開留空時系統一律照空值處理，不拿單頭值回補。理由：業務常在尚未跟客戶談定個別交期時就要建印件卡位，強制必填或自動回補都會製造一個沒人談過的日期。與 2026-08-08 前的拍板（必填、單頭回補）不同，此為 Miles 2026-09-08 改判並已落 wiki，spec 依新版撰寫。

**D3：急件選項與訂單交期變更統一走「留痕＋同步」，不通知**
兩個欄位的變更都只重推導預計交期、同步非終態工單、寫活動紀錄，不再推送任何通知（含既有的印件急件選項變更通知）。取代舊有「必須通知負責印務」的機制，因為印務可從工單列表的預計交期變動自行察覺，通知只增加噪音。這也連帶要求「製作後印件規格異動系統自動通知」Requirement 明確排除這兩個欄位，避免同一次變更被兩套通知機制重複處理。

**D4：內部製作截止日與印件預計交期不設比對關係**
移除「工單預計交期不晚於內部製作截止日」的既有約束（ORD-044 以此結案），兩個日期各自獨立、系統不檢查、不阻擋。理由：內部製作截止日是業務對整張訂單的判斷，覆寫它不代表旗下每一件印刷品的內部節奏都要跟著移動；連動會讓一次覆寫悄悄改掉所有非終態工單的日期。

**D5：Requirement 改名採 REMOVED + ADDED，不採 MODIFIED 改標題**
凡涉及 Requirement 標題变更（如「印件訂單交期（扣除急件）推導」→「印件預計交期推導」、「印件急件選項變更通知」→「印件急件選項與訂單交期變更留痕與同步」），delta spec 一律用 REMOVED（附 Reason + Migration）搭配 ADDED（新標題全新內容），不使用 MODIFIED 修改標題——因為 MODIFIED 的同步機制以標題做比對鍵，貿然改標題會讓 archive 後主 spec 出現與舊標題不匹配的孤兒內容。單純內容變更、標題不變的 Requirement（如「印件急件選項」「訂單階段印件規格編輯時機」）維持用 MODIFIED。

## Risks / Trade-offs

- **[風險] 四份 spec 交叉引用多，遺漏任一處會讓某個模組讀到過期的「客戶交期」或「是否急件」字樣** → 已透過全文 grep 逐一核對四份 spec 內所有「客戶交期」「訂單交期（扣除急件）」「是否急件」出現位置，delta 逐條覆蓋（見各 delta spec 檔）。
- **[風險] Prototype mock 主鏈（ORD-2026-0820）改交期數值後，既有測試情境可能因為排序或顯示斷言而失敗** → tasks.md 要求 mock 異動順序固定（先改 MOCK-DATA-CHAIN.md、後改各模組 mock-data.js）並跑 smoke 測試優先驗證主流程不斷。
- **[風險] 後端尚未支援印件建立時收印件類型與急件選項、`is_urgent` 尚未廢除** → 本 change 的 Prototype 與 spec 皆照拍板後的目標狀態撰寫，後端落差另開 Linear 票追蹤，避免這次交付因為等後端而卡住。
- **[取捨] 訂單準時交貨率指標暫不下沉到印件層** → 短期內「對客戶的整體承諾是否達成」這個問題仍只能用訂單單頭交期回答，逐件履約率要等 ORD-050 拍板後才有精確答案；這是刻意的範圍收斂，非疏漏。

## Migration Plan

1. wiki 落卡（已完成，commit 11a534c，本 change 不重做）。
2. OpenSpec delta spec（本 change，已完成）：order-management、quote-request、work-order、prepress-review 四份。
3. `openspec archive` 後 delta 併回主 spec，四份 main spec 生效為新正本。
4. Prototype（erp repo `(prototype)`）依 tasks.md 逐項施工：需求單印件列、訂單資訊 Tab 分區編輯、新增/複製加開印件 Dialog、印件詳情兩交期欄、工單交期顯示、審稿待審清單排序。
5. Mock 資料鏈同步：先改 `MOCK-DATA-CHAIN.md`，再改各模組 `mock-data.js`，主鏈 ORD-2026-0820 依錨例改日期值。
6. Sens `erp-prototype-tests`：依 `docs/scenario-catalog.md` 節號更新既有情境、新增交期相關情境；先跑 smoke、改哪章跑哪章、提交前跑全套。
7. 無回滾特殊步驟：本次為欄位與規格文字變更，若需回退，逐份 spec 與 Prototype commit 各自 revert 即可，不涉及資料遷移或不可逆操作。
