## Context

wiki 正本在 2026-08-28 更新了三件與發票金額有關的規則（單價兩位小數、品項加總容許一元差、一期改收多期兩條路並陳），order-billing spec 還停在舊版。核對時另外發現收斂張的減法基數在 spec 寫成「訂單未稅總額」，wiki 正本是「未稅基準」。

這是一次把 PRD 拉回 BRD 的同步，不是新設計。所有規則本體都已在 wiki 定案，本 change 不重新做決策。

## Goals / Non-Goals

### Goals

- order-billing spec 的六處與 wiki 正本一致。
- 收斂張的減法基數改取未稅基準，訂單有已認列異動時不再算錯銷售額。
- 期次重分配的兩條路都寫進 Scenario，開發不會把其中一條當成唯一路徑實作。

### Non-Goals

- 不改後端 sens-print-core 與前端 erp 的程式碼。修正需求已於 2026-08-28 留言交付 BE-310 與 FE-376。
- 不改訂單側的金額規則。訂單項目維持單價兩位小數、小計取整定案，這次放寬只發生在發票品項那一層。
- 不動 wiki。wiki 是本次的依據，已先行更新並提交。

## Decisions

**單價小數以實測為準，不以文件型別欄為準。** ezPay 文件把 `ItemPrice` 寫成 Int(10)，實測以字串送出即接受小數。替代方案是照文件擋掉小數、要業務改用較大單位（每千張 500 元），但印刷業每張 0.33 元這類單價很常見，硬要湊整數會讓發票上的數量與客戶認知的數量對不起來。

**品項加總容許一元差，不改對帳等式。** 替代方案是把銷售額改取品項加總，讓兩邊逐元相等。這條被否決——銷售額一律是整數元，改取加總會把角分帶進三方對帳，反而讓應收、發票淨額、收款淨額三方對不起來。容許一元差的前提是這個差只出現在發票這張紙上，不進任何等式。

**一期改收多期不做專屬操作。** 收款項目本來就能編輯金額、取消與新增，兩條路都走得通。替代方案是保留系統內生的拆期操作，但那會讓同一件事有兩條路徑，開發維護兩套、業務記兩種入口。

## Risks / Trade-offs

**開發已按舊 spec 實作，改 spec 不會自動修好程式。** 緩解：三方落差已逐條留言交付 BE-310（九條）與 FE-376（六條），本 change 只負責讓 spec 不再是錯的依據。

**品項加總容許一元差，可能被誤讀成金額可以隨便填。** 緩解：Scenario 同時寫了「差 0.01 允許」與「差 2 元擋下」兩個對照案例。
