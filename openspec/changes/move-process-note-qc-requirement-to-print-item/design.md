# 設計說明

## Context

工單目前持有「製程說明」一欄，品檢需求則只存在於紙本工單的表頭、系統內無欄位可填（PT-047 懸置多時的落點問題）。一件印件拆成多張工單時，這兩份文字要各寫一次，讀的人分不出哪一份算數。

Miles 2026-09-15 拍板兩欄一起搬到印件層，並於同日落 wiki 正本卡。本 change 只做系統行為規格的同步，不重做商業層決策。

約束：不新增實體、不新增關聯。兩欄皆為印件既有欄位表的新增欄，工單側為欄位移除。

## Goals / Non-Goals

### Goals

- 兩欄在 spec 內只有一個歸屬——印件，工單側不留任何自持條文。
- 兩個編輯入口（工單詳情、印件詳情）明寫為同一筆印件事實，可驗收。
- 品檢需求在驗收介面看得到，落成 qc 側可驗收的條文。

### Non-Goals

- 不重新裁決落點。PT-047 已以選項 A（印件層加欄）結案，製程說明一併搬移為同日追加指示。
- 不為漏填加任何把關：不擋送審、不提示（沿用現行）。
- 不改動 wiki 任何卡，不改動 `openspec/specs/` 主 spec，只在本 change 底下建規格差異檔。
- 不處理既有 mock 與後端資料的欄位遷移細節，那是 tasks.md 與 Linear 另案的範圍。

## Decisions

**D1：兩欄的唯一事實來源是印件，工單不持有自己的副本**

工單側刪欄、不留「工單可覆寫印件值」一類的例外。取代方案（印件填一份、工單可各自覆寫）不採——覆寫一旦存在，紙本工單上那份文字就答不出是誰寫的，品檢人員讀到的又是哪一份；而多工單印件正是搬家的起因，允許覆寫等於把問題原樣搬到新位置。

既有 mock 中同一印件的多張工單各有不同說明時，合併成一段文字、以部件名分段（例：「本體：…／封面：…」），不為此設結構化的部件欄位。分段是文字慣例，不是資料結構。

**D2：不鎖到草稿段，編輯時機看印件印製維度、不看工單狀態**

兩欄在印件印製維度未達終態前皆可改，工單狀態（草稿、製程審核完成、製作中）SHALL NOT 作為把關條件。取代方案（比照生產任務鎖在草稿與重新確認製程兩態）不採——製作中才發現品檢需求漏寫是常態，鎖住只會逼出口頭補充，系統內留不下那份要求，品檢人員照樣看不到。

印件達終態（已送達、已棄用；短出結案收尾後印製維度為已送達）時兩欄唯讀，理由與印件層其他欄位一致：活已收束，改了沒有可做的動作。

**D3：編輯角色沿用工單負責人分權，不另立一套**

可改的人 ＝ 負責該印件任一張非終態工單的印務、其工單編輯（代理）層級的分享成員、印務主管。不另設「印件層的製程說明編輯權」這種新權限。理由是兩欄的填寫時機就在製程規劃，寫的人本來就是那張工單的負責印務；代理層級沿用既有的單據分享機制（正本見 wiki 單據分享與職務代理卡），不為兩個文字欄開例外路徑。

業務、訂單管理人、品檢人員等其他角色唯讀。品檢人員只讀得到品檢需求，製程說明不在其驗收介面上——他要的是檢查什麼，不是怎麼做。

**D4：兩個編輯入口，一筆事實**

工單詳情與印件詳情兩頁都可編輯，寫入同一筆印件事實。取代方案（只在印件詳情頁可改）不採——印務規劃製程時人在工單詳情，要他跳到印件詳情再跳回來，實際會變成寫在別處或不寫。兩頁同源是可驗收的斷言：任一處改完，另一處與同印件其他工單立刻是同一個值。

**D5：品檢需求在驗收介面唯讀顯示，不進品檢紀錄**

品檢需求顯示在驗收介面上供品檢人員依循，但 SHALL NOT 寫進品檢紀錄本身。品檢紀錄是只增的現場事實底稿（通過數、不通過數、原因），把當下的品檢需求快照進去只會讓同一份要求在多筆紀錄裡重複，而印件上的那份改了之後又對不起來。無值時顯示「－」，不擋下驗收——這兩欄本來就沒有必填檢核。

## Risks / Trade-offs

- **[風險] 既有多工單印件的製程說明合併時可能漏字或錯配部件** → 合併是一次性的 mock 資料整理，範圍與做法寫在 tasks.md；正式資料的遷移屬後端另案，不在本 change。
- **[風險] 不鎖編輯時機，製作中改品檢需求時現場拿到的紙本會過期** → 與紙本工單「每次列印即時依當前已生效內容產生」的既有裁決同一條路線：改了就重印，系統不留快照。本 change 不加變更通知。
- **[取捨] 兩欄無必填檢核，品檢人員可能拿到空白的品檢需求** → 沿用現行，漏填不擋不提示。驗收介面顯示「－」讓「這件沒寫」看得出來，比擋下送審誠實——寫不出檢驗要點的印件確實存在（規格標準化的線上單就是）。
- **[取捨] 工單列印單據的 MODIFIED 與 `delivery-date-naming-convergence` 動到同一條 Requirement** → 以歸檔順序解決：本 change 後歸檔，基底取自該 change 的版本。順序寫進 tasks.md 第 1 節。

1. wiki 落卡（已完成，2026-09-15，本 change 不重做）。

4. Prototype（erp repo `(prototype)`）依 tasks.md 逐項施工。
5. Mock 資料鏈同步：先改 `MOCK-DATA-CHAIN.md`，再改各模組 `mock-data.js`，含多工單印件的說明合併。
6. Sens `erp-prototype-tests`：依 `docs/scenario-catalog.md` 節號更新既有情境、新增兩頁同源與驗收介面顯示的情境；先跑 smoke、改哪章跑哪章、提交前跑全套。
7. 無回滾特殊步驟：本次為欄位搬家與一條唯讀顯示，若需回退，逐份 spec 與 Prototype commit 各自還原即可。
