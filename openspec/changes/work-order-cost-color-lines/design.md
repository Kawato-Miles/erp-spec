## Context

工單的預估成本自 2026-08 起凍結為材料費、工序費、裝訂費、設備費四項。平版設備費＝開機費加各色貢獻，顏色的錢因此埋在設備費裡。

商業層已於 2026-09-16 定案並落卡，正本為 wiki [計價快照](../../../memory/Sens_wiki/wiki/erp/05-entities/計價快照.md)、[生產任務](../../../memory/Sens_wiki/wiki/erp/05-entities/生產任務.md)、[工單](../../../memory/Sens_wiki/wiki/erp/05-entities/工單.md)、[BOM結構](../../../memory/Sens_wiki/wiki/erp/04-business-logic/營運規則/訂單到交付/BOM結構.md) § 計價引擎計算框架。設計正本（拍板逐題紀錄、錨例驗算、稽核結論）為 [工單成本呈現收斂設計方案](../../../work-order-cost-color-lines-design.md)。本文件只承接落地方法。

## Goals / Non-Goals

### Goals

- 讓印務與印務主管在工單層看得出單黑、CMYK、Pantone、金屬色（合印）、獨立印各自花了多少
- 把生產任務的成本收為一個數，不再逐任務攤材料費、工序費、裝訂費、設備費——這些欄位對非印刷任務大多是 0
- 預估與實際兩張表用同一組列結構，逐列比得起來
- spec 條文與 wiki 欄位正本一致，同一個名詞只有一種寫法

### Non-Goals

- 登記色數當下的金額即時回饋（拍板不做，另案處理）
- 開機費獨立列（拍板後方向調整，開機費留在任務小計）
- 逐任務展開顏色金額（2026-09-16 拍板不做，追因回各任務的色數登記）
- 線上售價引擎的公式與輸出
- Linear 交付（另案處理）
- 工單匯出版式（不含成本，不受影響）

## Decisions

### 決策一：顏色費用凍在計價快照，不即時回算

作法：生產任務存檔時，除任務小計（不含顏色）外，另依色數登記與設備計價參數算出各顏色的金額，一併凍入該任務的計價快照。

替代方案：顏色費用不落庫，工單詳情開啟時依色數登記即時回算。否決理由是主檔調價後回算值會與凍結的任務小計混在一起，同一張表兩個時點的價，預估與實際比不起來。

### 決策二：顏色費用在工單層加總為列，不在任務列展開

作法：工單詳情把各生產任務列成一列（顯示任務小計，不含顏色），顏色費用：單黑、CMYK、Pantone、金屬色（合印）、獨立印各自一列，同一顏色跨任務加總。

替代方案：每筆任務列下展開自己的顏色金額。否決理由見拍板第五題——同一顏色可能跨兩台不同機，階梯價與倍率不同，逐任務展開會讓表列暴增且追因價值低。追因的解析度定為各任務的色數登記（色數，非金額）。

### 決策三：空的顏色列照列不隱藏

作法：顏色費用：單黑、CMYK、Pantone、金屬色（合印）、獨立印的列固定顯示，未登記該顏色即 0；完全沒有印刷任務的工單，這些列一律顯示 0。

替代方案：有值才列。否決理由是列數浮動會讓兩張工單的成本表對不起來，而且看的人分不出「沒登記」與「這張表少了一列」。

此處與既有回饋「當前狀態用不到的操作鈕直接隱藏」不衝突——該回饋針對操作鈕，本處是資料列。

### 決策四：報廢任務的顏色費用留在工單層，作廢任務排除

作法：沿用既有「成本留、數量除」規則。生產任務轉報廢時，任務小計與其各顏色貢獻都留在工單彙總；轉已作廢時兩者一併排除。

替代方案：報廢任務的顏色費用另做排除。否決理由是顏色費用屬成本，成本規則已有正本，不為本案另開分支。

### 決策五：取整以列為單位

作法：各列金額各自取整，合計取各列相加。

風險是通則上與舊的材料費、工序費、裝訂費、設備費合計可能差個位數。處置：以新列相加為正本；錨例 WO-2026-0820 前後皆為 43,009，無差額。

### 決策六：Prototype 的資料結構改為巢狀

作法：預估成本與實際成本的輸出結構改為小計欄加一組顏色欄，顏色欄的鍵沿用 mock 的 snake_case 命名，單黑、CMYK、Pantone、金屬色（合印）、獨立印各一鍵。

替代方案：把任務小計與各顏色平舖為同層的鍵。否決理由是顏色群要整組傳給列渲染與加總，巢狀讓彙總與縮放（依數量比例調整）只寫一次。

### 決策七：頁籤名稱去掉「分項」

作法：工單詳情的「預估成本分項」頁籤改名「預估成本」。既已不分項，名稱留著會誤導。

## Risks / Trade-offs

| 風險 | 緩解 |
|---|---|
| 舊成本分項的措辭散在 work-order、order-management、dispatch-order、production-overview，改漏就出現新舊並存 | delta 完成後掃描「四分項」「四個分項」，change 內命中數須為 0 |
| mock 的預估成本值重算錯誤，錨例對不上 | 以設計 § 六的錨例為驗收值：WO-2026-0820 合計 43,009；延伸例加登記 Pantone 一色後合計 43,503 |
| 顏色列的實際值取數錯誤（誤含開機費）| 沿用既有規則：實際側只取階梯價；測試以 § 工單成本對照的情境覆蓋 |
| 外發任務登記色數卻被算進顏色列 | 既有規則為純記錄不參與計價；情境覆蓋外發任務顏色列為 0 |
| 既有測試以舊成本分項為期望值，改名後仍通過但驗錯東西 | 測試檔連同檔名一併改，期望值取自 delta 的情境描述，不由實作重算 |

## Migration Plan

| 順序 | 動作 | 驗收 |
|---|---|---|
| 1 | wiki 落卡（已於 2026-09-16 完成）| wiki 平層掃描「四分項」「設備預計成本」命中數為 0 |
| 2 | 本 change 的差異規格檔（delta）寫入並驗證 | `openspec validate --change work-order-cost-color-lines` 通過 |
| 3 | Prototype mock 主鏈文件先改，再改各模組 mock 資料 | 錨例合計 43,009 |
| 4 | Prototype 計算模組輸出結構改寫，再改畫面 | 顏色計價自檢腳本通過 |
| 5 | 測試改寫與新增，依影響對映跑測試 | 冒煙測試通過，受影響章全部通過 |
| 6 | 歸檔 change，差異併回 main spec | 歸檔前掃描本 change 的未解問題 |

回滾策略：本案只改凍結欄的呈現與歸戶，計價公式不動。回滾即還原 delta 與 prototype 提交，mock 值以合計守恆為準，不會產生資料不一致。
