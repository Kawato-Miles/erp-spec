# 稽核維度

本檔是 vault-audit 各維度判定標準與門檻值的唯一出處。值域、欄位、命名的定義層在 [[wiki-schema]]（`memory/Sens_wiki/wiki/erp/00-meta/wiki-schema.md`），本檔只寫怎麼查、怎麼判。

類別分兩種。機械：腳本或 obsidian-cli 執行，結果直接採用。判讀：派子代理判讀，再由懷疑者複核，任務書見 `判讀派工單.md`。
每個維度產出命中清單與判定（OK、Warning、Error）；維度 10 只出 Info。

## 二、維度

本輪異動卡：與 origin/master 分岔點至今的提交，加上工作區的改動與新檔。模式 D 改用指名提交的檔案清單。

### 維度 1：頁面間矛盾（判讀）

- 範圍：依 [[business-domain-taxonomy]] 領域 tag 分組。每次全量輪掃不超過 `domains_per_round` 個領域；一組＝該 tag 全卡加 `領域/全域` 卡。本輪掃了哪些領域記進 log 條目變更行，下輪接續。
- 每輪必掃的高風險概念：工單建立來源、狀態轉換的觸發角色、欄位計算口徑、退款收尾接力、報工者。
- 與維度 13 共用同一次掃描。判定：Error＝明確矛盾（A 卡寫 X、B 卡寫非 X）；Warning＝補充性差異。
- 發現矛盾：並排呈報，建議 `oq-manage` mode B 開 OQ；不自行調和。

### 維度 2：過時宣稱（機械，腳本）

- 範圍：status=active 的卡，排除範例卡、`log.md`、`wiki/範本/`。判定：last-reviewed 早於門檻 `stale_days` 計一筆。OK＝0；Warning＝1 至 `d2_warn_max`；Error＝超過。

### 維度 3：孤島頁面（機械，obsidian-cli）

- 方法：obsidian-cli 查入鏈為 0 的檔。
- 先扣豁免再計數：README 與 index、`wiki/範本/`、各資料夾「規範 - 」與「範例 - 」卡（[[卡片撰寫共用規範]] § 一鐵則 4、5）、`raw/` 全層、`09-canvases/`、`08-open-questions/_archives/`。
- 判定：OK＝0；Warning＝1 至 `d3_warn_max`；Error＝超過。

### 維度 4：死鏈（機械，obsidian-cli）

- 方法：obsidian-cli 查未解析連結。只計 03～07 正本卡與 `00-meta/`。排除 `raw/`、`08-open-questions/_archives/`、`log.md` 與 `changelog.md`、`09-canvases/`、`wiki/範本/`。
- 不計：指向 vault 外的相對路徑 markdown 連結（合規寫法，Obsidian 一律算未解析）。指向 OpenSpec 或 Prototype 的計 Error。
- 判定：OK＝0；Warning＝1 至 `d4_warn_max`；Error＝超過。

### 維度 5：frontmatter 完整性（機械，腳本）

依 wiki-schema § 四各 type 的欄位表檢查，不用一體適用清單。腳本逐項：

| 檢查 | 等級 |
|------|------|
| 缺 frontmatter；type 不在 § 一值域；status 不在 § 三值域 | 錯誤 |
| 缺該 type 的必填欄位（yaml 區塊內、註解未標選填或條件填寫者） | 錯誤 |
| 正本卡型（§ 4.0 所列）缺 source；status=deprecated 免 source 與 tags | 錯誤 |
| 領域 tag 必標範圍內缺 tag；tag 值不在 taxonomy 值域 | 錯誤 |
| 含 `business-domain`（`_archives/` 除外） | 錯誤，維度直接判 Error |
| 正本卡型含 `module`、`implemented-by`、`related-spec` | 錯誤，維度直接判 Error |
| title 與檔名相同（§ 四通則一）；欄位無值或空清單（通則二） | 警告 |
| module 的英文值殘留 | 提醒 |

- 必標範圍照 taxonomy § 領域 tag 標注規則：03～07 的非規範、非範例卡，加 `08-open-questions` 平層的 open 卡。豁免：`wiki/範本/`、type=example（範例卡由維度 12 勾稽）。`_archives/` 只檢 type 與 status 值域。
- 濫標 `領域/全域`（只沾一兩個領域卻標全域）不進腳本，由維度 1 判讀時順帶標出。
- 判定：OK＝0 錯誤且 0 警告；Warning＝錯誤 1 至 `d5_warn_max`，或只有警告；Error＝超過，或有直接判 Error 的項。

### 維度 6：規約遵守（機械，腳本；第 3、4 項判讀）

| 項 | 檢查 | 類別 |
|----|------|------|
| 1 | 08 以外的卡有 `> [!question]` callout | 機械 |
| 2 | 03～07 的卡有「待補」「待釐清」：排除同行含 `[[`、「待補件」、規範卡 | 機械 |
| 3 | 卡名與段落直譯、中英夾雜（`memory/Sens_wiki/CLAUDE.md` § 一） | 判讀 |
| 4 | 正文迭代史堆疊（「A 已棄用 → 改 B」並陳） | 判讀 |
| 5 | wiki link 用別名 `[[卡名\|…]]`：排除 `log.md`、`changelog.md`、`_archives/` | 機械 |

- 「待確認」「需確認」「尚未確認」不進機械掃描：這些詞在正本卡大量作業務語意（狀態名、結果值、業務事實），由判讀者讀卡時判。OQ 卡命名在維度 8 檢查。
- 判定：OK＝0；Warning＝1 至 `d6_warn_max`；Error＝超過，建議 `oq-manage` mode D 遷出。

### 維度 7：出鏈有效性與方向（機械，腳本）

- source 方向與例外以 wiki-schema § 4.0 為準：禁指 OpenSpec spec 與 Prototype；後端現況、計畫工作檔、「change <名稱> grill.md G編號」可指。grill.md 寫成路徑者照下列檢查報錯。
- 腳本檢查：source 欄含 `openspec/` 或 `sens-erp-prototype/`；03～07 正文含 `openspec/`、`sens-erp-prototype/`、`/erp/apps/`；兩卡 source 直接互指。
- 深層繞回（A→B→C→A）不在腳本範圍，判讀者發現時列入。
- 判定：OK＝0；任一命中即 Error。

### 維度 8：OQ 健康度（機械，腳本）

範圍：`08-open-questions/` 平層的 open-question 卡；`_archives/` 不掃。

| 檢查 | 等級 |
|------|------|
| status 不在 open、answered、cancelled，或 status 行有行內註解 | 錯誤，維度直接判 Error |
| status=answered 或 cancelled 留在平層，未封存 | 錯誤，維度直接判 Error |
| 檔名不符「前綴-三位序號-簡述」，或前綴不在 wiki-schema § 七值域 | 錯誤 |
| open 停留超過 oq-manage 門檻（priority high 另標） | 警告 |
| 缺 source-link | 警告 |

- 判定：OK＝0；Warning＝命中 1 至 `d8_warn_max`；Error＝超過或有直接判 Error 的項，建議 `oq-manage` 整理；open 量大時在建議段點出該收割的 OQ 群。

### 維度 9：Raw 健康度（機械，腳本；唯讀，不動 raw 任何檔）

| 檢查 | 等級 |
|------|------|
| status 不在 raw 值域 | 錯誤 |
| source=claude-research 或 miles-upload 缺 raw-source-link；miles-upload 缺 attached-files | 錯誤 |
| status=raw 或 reviewed 停留超過 vault-ingest 門檻（以 created-at 起算） | 警告 |
| 同一 topic-tag 的 status=raw 卡達 vault-ingest 同主題門檻 | 警告，建議 vault-ingest mode B |
| status=raw 張數達 vault-ingest 累積門檻 | 提醒，建議 vault-ingest mode C |

- 判定：OK＝無命中；Warning＝只有警告；Error＝有錯誤。

### 維度 10：標題錨點（機械，腳本；Info，不計分）

- 本輪異動卡含 `spec.md#Requirement:` 錨點即列（Requirement 改名即斷鏈）。存量卡不回頭批量改。

### 維度 11：log 條目完整性（機械，腳本）

- 本輪異動的 03～06 卡：`wiki/log.md` 在本輪起日之後有含 `[[卡名]]` 的條目；實質異動條目（非健檢、非 ingest）的動機行非空、不是「免」。
- 判定：OK＝全有；Warning＝缺條目或動機空白。

### 維度 12：撰寫規範勾稽（判讀）

範圍：本輪異動的正本卡，加全部「範例 - 」卡。

1. 異動正本卡：L1、L2、L3 全過才算完成。L1 是 [[卡片撰寫共用規範]] § 四之二。L2、L3 依 type 取：entity 取 `規範 - 實體` § 十；role 取 `規範 - 角色` § 十；state-machine 取 `規範 - 狀態機` § 十；scenario 取 `規範 - 業務情境` § 十二；service-blueprint 與 business-rule 取 `規範 - 商業邏輯` § 十三（依 mutability 加勾 L3）；activity-list 取 `規範 - 活動清單` § 十；process-architecture 與 controlled-list 取 wiki-schema § 四該型段落要求；open-question 取 `規範 - OQ` § 九。
   以該單元範例卡為通過樣本。L1-9 用詞的取證走維度 14。本輪有 Miles 核對過的落點表（[[卡片撰寫共用規範]] § 二之二）時，逐條驗一條內容只有一個落點。
2. 規則正本回歸：本輪動到 00-meta 規則正本或任一規範卡正文時，全庫比對各規範卡卡尾稽核維度表與規則正本是否一致。不一致計 Error。
3. 範例卡：`synced-with-template` 不得早於對應規範檔最後實質修改日（`git log -1 --format=%ad --date=short -- <規範檔>`）；範例卡與快照來源卡至少段落結構同構。

- 判定：OK＝異動卡全過且範例卡同步日有效；Warning＝未過 1 至 `d12_warn_max` 項；Error＝範例卡同步日早於規範修改，或超過。

### 維度 13：規則複寫（判讀）

- 正本原則見 [[erp_index]] § 增修紀律。範圍：本輪異動的 03～07 卡；存量與維度 1 共用同一次領域掃描。每輪必掃：工單建立來源、狀態轉換的觸發角色、欄位計算口徑、外包與委外的粒度、退款收尾接力、報工者變體。
- 方法：逐條抽規則句（含數值、角色、狀態值、觸發條件），每句取關鍵詞用 obsidian-cli 全庫搜尋，排除歷史層與 OQ。命中第二處時分類：

| 類 | 判定 | 處置建議 |
|----|------|---------|
| 實質重述：兩處都在定義同一規則 | Error | 依 [[scope-boundary]] 與規範的正本歸屬判正本，另一處改引用 |
| 引用：一處定義，另一處以 `[[卡名]]` 指過去 | 不計 | — |
| 同名不同物 | Error | 正名，不改引用 |

- 判定：OK＝0；Warning＝1 至 `d13_warn_max`；Error＝超過或有同名不同物。哪張是正本由 Miles 裁決。

### 維度 14：欄位名跨卡一致（判讀）

- 規則正本：[[卡片撰寫共用規範]] § 四之二 L1-9；本維度只取證與判讀。方法：
  1. 掃 `05-entities/` 各卡「欄位（業務可見）」表第一欄，得欄位名全集。
  2. 反向掃 03、04、06、07：形似欄位的名詞（尾詞為金額、日期、狀態、數量、總額、淨額等）比對是否命中全集。
  3. 未命中者逐項判：實體卡改名而下游未跟上（Error）；自創同義詞（Error）；業務概念詞（不計）。
- 判讀前先問：把這個詞換成欄位全名，句子語意還對嗎？換了會錯就是概念詞。
- 判定：OK＝0；Warning＝1 至 `d14_warn_max`；Error＝超過或同一概念兩個名字並存。正名方向由 Miles 裁決。

### 維度 15：權責結構（機械，`scripts/authority_check.py`）

- 在 repo 根目錄執行 `python3 .claude/skills/vault-audit/scripts/authority_check.py`，檢查項見腳本檔頭。時機：權責相關卡有異動時提交前跑一次，總計行附在提交訊息；全量稽核一併跑。
- 判定：OK＝錯誤 0；Warning＝錯誤 0 但有新警告（逐筆判讀，「同主流程第 N 步」轉引列與系統外作業列合法）；Error＝錯誤 1 筆以上。

### 維度 16：規範契約機械自檢（機械，規範卡指令）

- 依序執行 [[卡片撰寫共用規範]] § 四之四與各單元規範「機械自檢」段的指令：實體 § 十二、商業邏輯 § 十六、活動清單 § 十二、資料結構總覽 § 十二、狀態機 § 十二、業務情境 § 十四、角色 § 十二、OQ § 十一。指令正本在那些段。
- 範圍：全庫正本卡；規範卡與 `_archives/` 排除。錯誤與警告分級以規範段標示為準。
- 判定：OK＝錯誤類零命中、警告已逐筆判讀；Warning＝有未判讀的警告；Error＝錯誤類任一命中。存量命中列建議段，不擋本輪。

### 維度 17：審查知識層健康（機械，腳本）

範圍：`11-review-knowledge/`。寫法依據 [[審查知識路由]] § 二、§ 四。

| 檢查 | 等級 |
|------|------|
| 參考模型卡引用的 raw 卡不存在，或 status 仍是 raw | 錯誤 |
| 參考模型卡正文引用的 raw 卡沒列進 source | 錯誤 |
| 業界做法、守恆量每列的出處沒有 raw 卡連結 | 錯誤 |
| 公司偏離每列的狀態與出處不是「已定：…」或「待裁決：…」 | 錯誤 |
| [[稽核誤判記錄]] § 二案例與 § 三評測反例對照依日期不能一一對應 | 錯誤 |
| 審查知識路由列的評測集路徑不存在（只測存在，不讀內容） | 警告 |

- 判定：OK＝無命中；Warning＝只有警告；Error＝有錯誤。處置建議：raw 卡未精練轉 `vault-ingest` mode B；誤判對照缺列轉 `erp-audit`。

## 三、報告與 log 格式

對話報告：

```markdown
# Vault 健檢報告（YYYY-MM-DD HH:MM）

## 摘要
- 模式／總體判定（OK、Warning、Error）／維度通過 X／總數

## 維度結果
### 維度 N <名稱>：<判定>
（命中筆數與主要案例；OK 維度一行帶過；跳過的維度寫原因）

## 主要發現
## 建議下一步
- 可修復項（模式 C 轉介對象）／需 Miles 裁決項
## 建議調查的新問題與該補的素材
- 值得調查的新問題：被多張卡提及卻沒有自己頁面的概念、資料缺口、同類 OQ 聚成的系統性議題；待裁決者走 `oq-manage` mode B
- 該補的素材：哪個主題缺訪談、法規、業界參照；素材到手走 `vault-ingest` mode A
- 知識庫或工作流本身的待辦：寫 `memory/` project 卡，不在 `wiki/` 留卡
```

`wiki/log.md` 追加一筆，最新在上；長敘事留在對話報告：

```markdown
## [YYYY-MM-DD HH:MM] 健檢(audit) | <模式>，稽核維度 X 通過
- 變更：稽核 ERP_Vault，<總體判定>；只列非 OK 維度與筆數；維度 1、13 本輪掃的領域
- 動機：免（健檢類）
- 衝突：無（或列發現的矛盾與已開 OQ）
```
