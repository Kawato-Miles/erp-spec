# linear-delivery

## 目標

開發拿到可動工、不用回頭問 PM 的票：Linear 自包含，規則對得到 wiki，介面對得到 Prototype。
交付前由撰寫者以外的稽核者與受測者審查，合格才寫入 Linear。

## 產出

| 產出 | 落點 | 誰寫 |
|------|------|------|
| project 描述、milestone、Feature 票、Task 票（狀態密集模組另含狀態機圖） | Linear | 撰寫者寫草稿，主對話寫入 |
| 問題清單 | 對話；格式見規範 § 十「審查輸出格式」 | 稽核子代理 |
| 盲測紀錄 | 對話 | 受測子代理作答，主對話比對 |
| 案例紀錄 | `references/blocked-cases-log.md` 追加 | 主對話 |
| 交付回報：各容器網址、本次交付到哪個 Prototype 提交 | 對話 | 主對話 |

## 限制

- 取材只從 wiki 與 Prototype（含情境目錄與 mock），後端現況只作查證。不讀 OpenSpec。
- 寫法規則、審查標準只在 `references/規範 - Linear 交付.md`；本檔以規則短名引用。
- 門檻值（合格條件、輪數、受測者人數與模型、驗收條數、收合門檻、免派稽核者）只在規範 § 十一。
- 撰寫者、稽核者、受測者三方分離。受測者之間互不知道答案。撰寫者不自判完成。
- 未合格不寫入。每面寫入前把要動的 project 與 issue 清單列給 Miles。
- 只改本次交付的 project 描述與指定 issue 描述。既有票不動 estimate、assignee、cycle、priority、milestone、labels；例外見規範。
- 上游互相矛盾、驗收對不到規則：停下，依規範「上游矛盾先停」「驗收對不到規則先停」，不在 Linear 補。規格缺口無法不捏造時，轉 `oq-manage` mode B，票上標「另案處理」，不算問題。
- 撰寫、稽核、受測子代理的任務書 MUST 指名先讀非商業術語對照：`/Users/b-f-03-029/Sens/memory/shared/non-business-terms.md`；另附規範、範本、範例三檔路徑。

## 順序

開工先寫交付宣告，替換 `<...>`：
```text
# /goal：交付「<模組名>」到 Linear（project <project-id>）
## 目標結果
<模組> 的 project 描述、milestone、Feature 票、Task 票〔狀態密集模組另含狀態機圖〕齊備，出處核對與盲測達規範 § 十一合格條件。
## 驗證方式
稽核子代理依規範 § 十輸出問題清單，每筆引草稿位置；第二段、第三段盲測由獨立受測者作答。
## 限制
依規範、範本、範例撰寫，不以其他既有 issue 當對照。<本次特有限制>
## 迭代規則
依本檔步驟 5 與規範 § 十一。
## 例外處理
規格來源未定義 → oq-manage mode B，標「另案處理」。達停止條件 → 停下回報 Miles：已試什麼、卡在哪、需要什麼。
```

| 步 | 動作 | 誰做 |
|----|------|------|
| 1 | 取材，清掉上游矛盾 | 主對話 |
| 2 | 依規範、範本、範例寫草稿。既有票改寫或 project 重整時順序不可顛倒：定 Scope（一條一張 Feature 票）→ 切功能節（一節一個動作）→ 列全票功能節名表（一條規則只在一節）→ 依 Prototype 列 Task 清單；跳過會讓 Task 票整段複寫規則 | 主對話或撰寫子代理 |
| 3 | 送審前自掃 | 撰寫者 |
| 4 | 審查：出處核對，合格後跑第二段與第三段盲測 | 稽核子代理、受測子代理 |
| 5 | 審查循環：未合格就修正後重審 | 主對話、稽核子代理 |
| 6 | 合格才寫入 Linear，回報每個容器的網址 | 主對話 |

### 步驟 1：取材

取材順序固定：wiki → 情境目錄與 Prototype → 後端現況。

| 來源 | 拿什麼 | 不拿什麼 |
|------|-------|---------|
| wiki 商業邏輯卡、實體卡、狀態機卡、業務情境卡 | 概述與 Use Case、實體關係、算式、狀態條件 | 欄位表、狀態列舉以外的轉換敘述 |
| wiki 活動清單卡（檢視與輸出在單據存取流程群組） | 權限表每一列：執行角色、範圍、依據欄位、操作 | 活動編號、活動清單代碼 |
| wiki 實體卡操作段 | 權限表的動作名稱，照抄；動作類型用來查漏列 | 操作編號 |
| wiki 受控清單 | project 範圍用詞段的定義 | 單據代碼、活動清單代碼 |
| wiki 角色卡 | 使用者故事、Use Case、驗收的角色名 | 權限與範圍（改取活動清單卡） |
| wiki 參考模型卡公司偏離段（`11-review-knowledge/參考模型/`） | 與業界做法的取捨段，取法見規範「與業界做法的取捨段」 | raw 卡名、拍板編號 |
| 情境目錄 `erp-prototype-tests/docs/scenario-catalog.md` 與其測試 | 驗收情境與具名案例；哪些情境已走通、哪些標未實作 | 情境編號、測試檔名 |
| Prototype（`/Users/b-f-03-029/erp/apps/erp/src/app/(prototype)/`）該模組頁面、`_lib/permissions.js` | 權限核對、驗證規則的受理條件、Task 票的功能與控制元件名稱 | 欄位、值域、版面、按鈕文案；具名案例（改經情境目錄） |
| 後端現況（`sens-print-core`） | 已實作模組的範圍與分享機制，確認票上寫法一致 | 代碼、判定式、權限名稱 |

- 後端現況與 wiki 不一致且沒有 OQ 承接：停下。情境目錄缺具名案例：先補上游。交付前 Prototype 先補齊該模組 wiki 已定義的逆流程（退回、收回、作廢、取消連鎖）。情境目錄第十六章標待辦者先補 Prototype，不以票文代替畫面。
- 來源缺口：wiki 有、Prototype 沒有的動作先補 Prototype；Prototype 有、wiki 沒有的行為先轉 `wiki-amend`；兩邊都沒有的開 OQ 標另案。
- 用 `list_projects`、`list_issues` 確認既有欄位與同平台既有功能節。迭代差異依 wiki/log.md 與 Prototype 提交紀錄，從上次回報的提交起算。
- 核心邏輯與狀態機變動投中台 project；業務平台是視圖層，只沿用。平台上沒有的模組，內容併入該平台既有 project 的情境擴充段。

### 步驟 3：送審前自掃（自掃清單）

撰寫者掃全部票的全部段，不只掃上一輪被點名處。結構性交付缺結構件者不得送審。

| 掃什麼 | 怎麼掃 |
|-------|-------|
| 一條一件事與句法 | 受理條件、受理後的寫入、對其他單據的影響各一條（「拒絕並回傳」算一件事）；依 `ste100-pm.md`；列舉前不寫死數量詞 |
| 具名案例 | 單號、品名、人名、數值回情境目錄查原文；人名另查 mock 的角色與指派；歷程類照 Prototype 實際寫入字樣 |
| 沿用規則 | 規則的 wiki 正本卡領域標籤與本 project 不同就刪，改在 Out of Scope 寫一次 |
| 改規則 | 先列出全部出現處（Use Case、Scope、概述、功能節、權限表、milestone 描述），一次改完 |
| 驗收對得到規則 | 每條驗收在同節規則段找到對應條目 |
| 實體關係不越界 | 不複寫狀態轉換、不寫畫面排序與顯示方式 |
| 權限表 | 一列一動作、一格一範圍；動作照抄操作名稱；角色與範圍照抄活動清單卡 |
| 取捨段 | 只在有偏離拍板時出現；每列對得到參考模型卡；沒有 raw 卡名與拍板編號 |
| Task 清單 | 只寫名稱；後端一條一個畫面功能，讀取類也列 |
| 來源標記、提及、編號、收合 | 無情境編號與測試檔名；issue 寫識別碼、project 用原生提及；段內編號各自從 1 起；超過收合門檻的段與功能節整節已收合 |

### 步驟 4：審查

| 審查 | 誰做 | 讀什麼 |
|------|-----|-------|
| 出處核對 | 稽核子代理，模型 opus | 完整草稿、規範、範例、wiki、情境目錄 |
| 第二段盲測（wiki → Linear） | 受測子代理，人數與模型依規範 § 十一 | 只讀草稿；答第一段判定題 |
| 第三段盲測（Linear → 開發設計） | 受測子代理扮演後端或前端 | 草稿與開發看得到的 wiki、Prototype；Miles 判定 |

- 盲測只改部分票時，任務書寫明不改的票不在範圍、受測者只問業務規則。盲測問題由主對話依規範 § 十分類，併入下一輪問題清單。審查不重審上游設計。

### 步驟 5：審查循環

- 換人輪每輪換新稽核者，不判停；續核輪由同一稽核者續核，依停止條件判停；任何輪次到安全上限即停。各值見規範 § 十一。
- 每輪重審餵完整修正後草稿，不暗示改了什麼。格式類由撰寫者自修，不必重審。不放水、不降標、不表面改字。
- 每輪記：第幾輪、改了什麼、前兩類各幾筆、下一步。前兩類追加 `references/blocked-cases-log.md`，不論最終是否合格。

### 步驟 6：寫入 Linear

依序：建 milestone → 開全部 Feature 票（PM team 建立、不轉隊，掛 milestone 與 Label）→ 覆寫 project 描述（Scope 填 Feature 票識別碼）→ 依阻擋順序開 Task 票（PM team 建立，轉 FE 或 BE，parentId 掛回 Feature 票）→ 在 Task 層建 blocking 關係 → 回填原生提及。寫完請 Miles 確認狀態機圖渲染。

## 情況對應檔案

| 情況 | 讀哪個檔 |
|------|---------|
| 流程、步驟、誰審查、何時停 | 本檔 |

| 規範、範本、範例改動後記版本 | `references/CHANGELOG.md`（交付時不載入） |

交付出現新型錯誤、被開發退回的票、或要調整審查方式時，規範演化依序：記進 blocked-cases-log → 歸到規範既有章節（放不進才新增）→ 寫成帶短名的規則附反例 → 門檻只改規範 § 十一 → 用新規範重審範例檔與被退回的票，範例不合格直接改範例 → CHANGELOG 追加版本與理由。規範、範本、範例同一次提交。

## 陷阱

| 陷阱 | 出處 |
|------|------|
| 直接開在 FE、BE team 不會產生 GitHub 同步票。先 `save_issue` 帶 `team: "PM"` 建立，再帶 `id` 轉隊；識別碼換新，附件保留 | 舊版操作注意事項；memory `feedback_linear_issue_via_pm_team` |
| 轉隊會靜默解除 project 關聯：目標 team 不在 project 的 teams 清單時不報錯。開票前 `save_project` 帶 `addTeams` 加 FE、BE；轉隊後逐票驗 `projectId` 非空 | 舊版操作注意事項 |
| `save_project` 會把狀態帶到「Kick off」，且描述整段覆寫：同時帶交付前原狀態；改一段也重傳完整描述 | 舊版操作注意事項 |
| 覆寫既有票多傳欄位會改掉 estimate 等：只傳 `id` 與 `description`（全域規劃 milestone、補標題前綴與 Label 例外）；In Progress 的票不覆寫，例外依規範「進行中票可覆寫的情況」 | 舊版操作注意事項 |
| `parentId` 傳識別碼可能不生效：傳 UUID，寫入後逐票驗；提及猜錯 UUID 會降級成純連結，issue 直接寫識別碼 | 舊版操作注意事項 |
| `save_issue` 的 `patch` 對中文 `old_string` 常回 not found：只插一段用 `insert_before`，改多處重傳完整描述 | 舊版操作注意事項 |
| 修正留言用 Markdown 連結引 issue、只寫新內容：改寫成原本／現行對照表，新增項也進表；issue 寫識別碼；寫後讀回查錯字 | 2026-09-04 memory `feedback_linear_comment_format` |
