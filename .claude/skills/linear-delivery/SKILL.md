# Linear 交付與稽核（linear-delivery）

把已定案的規格交付到 Linear，讓開發團隊拿到可動工的需求。交付前由與撰寫者分離的稽核者與受測者把關品質。

## 檔案分工

| 檔案 | 內容 | 誰讀 |
|------|------|------|
| 本檔 | 流程：步驟、誰審查、何時停、送審前自掃清單、Linear 操作注意事項 | 主對話 |
| `references/規範 - Linear 交付.md` | 寫法規則（帶短名）、審查方式、門檻值 | 撰寫者、稽核者、盲測主持者 |
| `references/範本 - Linear 交付.md` | 段落骨架與占位，不放規則 | 撰寫者 |
| `references/範例 - Linear 交付.md` | 凍結快照的撰寫示範，取材自真實交付但不與 Linear 同步；附各結構件出現的理由 | 撰寫者、稽核者 |
| `references/blocked-cases-log.md` | 審查問題案例的只追加紀錄，規範演化的原料 | 主對話 |
| `references/CHANGELOG.md` | 規範、範本、範例的版本紀錄 | 不在交付時載入 |

本檔提到的門檻值（合格條件、輪數、受測者人數與模型、驗收條數）只寫在規範檔「門檻值」段，本檔只引用。

## 交付目標宣告

每次交付前，先把任務寫成下列宣告，替換 `<...>` 占位。

```text
# /goal：交付「<模組名>」到 Linear（project <project-id>）

## Outcome
<模組> 的 project 描述、milestone、Feature 票、Task 票〔狀態密集模組另含狀態機圖〕齊備，出處核對與盲測達規範檔的合格條件。撰寫者不自判完成。

## Verification
稽核 sub-agent 依規範檔「審查」段輸出問題清單，每筆引用草稿位置；第二段、第三段盲測由獨立受測者作答。

## Constraint
- 依規範檔、範本、範例撰寫；不以其他既有 issue 當對照。
- 只改本次交付的 project 描述與指定 issue 描述。既有票不動 estimate、assignee、cycle、priority、milestone、labels；新開票依規範設 milestone 與 Label。
- <本次特有限制>

## Iteration Policy
依本檔「審查循環」與規範檔門檻值。

## Error Handling
- 規格來源未定義 → 觸發 oq-manage mode B，交付文件標「另案處理」。
- 達停止條件 → 停下回報 Miles：已試什麼、卡在哪、需要什麼。
```

## 工作流程

| 步驟 | 動作 | 執行者 |
|------|------|-------|
| 1 | 抓已定案規格，清掉上游矛盾 | 主對話 |
| 2 | 依規範、範本、範例產出交付草稿 | 主對話（或派撰寫 sub-agent） |
| 3 | 送審前自掃 | 撰寫者 |
| 4 | 審查：出處核對、第二段與第三段盲測 | 稽核 sub-agent、受測 sub-agent |
| 5 | 審查循環：未合格就修正後重審 | 主對話、稽核 sub-agent |
| 6 | 合格才寫入 Linear，回報每個容器的網址 | 主對話 |

### 步驟 1：抓已定案規格

- 取材順序固定：先 wiki，再情境目錄與 Prototype，最後後端現況。各來源拿什麼見下表。

| 來源 | 拿什麼 | 不拿什麼 |
|------|-------|---------|
| wiki 商業邏輯卡、實體卡、狀態機卡、業務情境卡 | 概述與 Use Case、實體關係、算式、狀態條件 | 欄位表、狀態列舉以外的轉換敘述 |
| wiki 活動清單卡（`04-business-logic/服務藍圖/<流程群組>/`，檢視與輸出在單據存取流程群組） | 權限表的每一列：活動表的執行角色、範圍、依據欄位、操作四欄；各角色看得到的範圍取檢視活動 | 活動編號、活動清單代碼（不寫進 Linear） |
| wiki 實體卡操作段 | 權限表動作的名稱：照抄操作名稱，動作類型用來確認同一單據的動作沒有漏列 | 操作編號（不寫進 Linear） |
| wiki 受控清單 | project 範圍用詞段的定義 | 單據代碼、活動清單代碼 |
| wiki 角色卡 | 使用者故事、Use Case 與驗收的角色名；角色的職位定位 | 權限與範圍（改取活動清單卡） |
| 情境目錄 `erp-prototype-tests/docs/scenario-catalog.md` 與其測試 | 驗收的情境與具名案例（單號、品名、數量、單價、人名）；哪些情境 Prototype 已走通、哪些標「未實作」 | 情境編號、測試檔名（不寫進 Linear） |
| Prototype（`/Users/b-f-03-029/erp/apps/erp/src/app/(prototype)/`）：該模組頁面、`_lib/permissions.js` | 權限表動作的核對、驗證規則的受理條件、前端 Task 票的頁面與控制元件名稱 | 欄位、值域、版面、按鈕文案；驗收的具名案例（改經情境目錄） |
| 後端現況（`sens-print-core`） | 已實作模組的範圍與分享機制，確認票上寫法與現況一致 | 代碼、判定式、權限名稱 |

- 取材時發現上游互相矛盾，依規範「上游矛盾先停」處理，先修上游與測試再寫草稿。後端現況與 wiki 不一致、且還沒有 OQ 承接時，同樣停下。
- 情境目錄缺驗收要用的具名案例，依規範「具名案例照抄情境目錄」先補上游。
- 交付前 Prototype 要先補齊該模組 wiki 已定義的逆流程（退回、收回、作廢、取消連鎖）。情境目錄第十六章標待辦者，先補 Prototype 再交付，不以票文代替畫面。
- 用 `list_projects`、`list_issues` 確認目標 project 與 issue 的既有欄位，避免覆蓋。
- 迭代交付的差異依 wiki/log.md 與 Prototype 的提交紀錄判定，每個模組在交付回報時記下「本次交付到哪個 Prototype 提交」，下次從那裡起算。
- 核心邏輯與狀態機變動投中台 project；業務平台是視圖層，只沿用。
- 開新 project 前確認該平台真有對應模組；平台上沒有的模組，內容以情境擴充段併入該平台既有 project。
- 每條要寫進 Feature 票的規則，先標出它的 wiki 正本卡與領域標籤，判斷是否為沿用規則（依「沿用規則不寫」）。
- 來源缺口的處理：wiki 有、Prototype 沒有的動作先補 Prototype；Prototype 有、wiki 沒有的行為先回 wiki 落卡（`wiki-amend`）；兩邊都沒有的開 OQ 標另案。

### 步驟 2：產出交付草稿

- 撰寫前讀規範檔、範本檔、範例檔，以及 `/Users/b-f-03-029/.claude/output-styles/ste100-pm.md`（受控句法）與 `/Users/b-f-03-029/Sens/memory/shared/non-business-terms.md`（非商業術語對照）。
- 草稿由 sub-agent 代寫時，任務書附上述檔案的路徑。
- 不拿其他需求或 issue 的內容當對照。實例會被修改或刪除，對照即失效。
- 既有票改寫成現行結構，或整個 project 重整時，照下列順序，順序不可顛倒：

| 順序 | 動作 |
|------|------|
| 1 | 先定 Project 的 Scope：一條一張 Feature 票，每條寫「做完後使用者能做到什麼」 |
| 2 | 每張 Feature 票切功能節，一節一個動作，節名受詞加動詞；節名有「與」或頓號時，檢查是否兩個動作 |
| 3 | 列全票功能節名表：一條規則只在一節 |
| 4 | 依功能節的動作列後端要開的 API，依 Prototype 列前端的頁面與控制元件 |

跳過這個順序直接搬舊段落，Task 票會整段複寫規則本體，審查反覆出現同型問題。

### 步驟 3：送審前自掃

撰寫者送審前依下表掃過全部票的全部段，不只掃上一輪被點名的位置。句法類問題不計入合格條件，靠這張表在送審前擋下。結構性交付缺結構件者不得送審。

| 掃什麼 | 怎麼掃 |
|-------|-------|
| 一條一件事 | 實體關係、驗證規則逐條掃。受理條件、受理後的寫入、對其他單據的影響各寫一條。「拒絕並回傳」「重算並回傳」是一個動作的連帶結果，算一件事 |
| 句法 | 依 `ste100-pm.md`：句長、一句一事、不用分號串接三件以上、不用名詞化 |
| 數量詞 | 列舉前不寫死數量詞，如「五個單元」 |
| 具名案例回情境目錄核對 | 每個單號、品名、人名、數值回情境目錄查到原文。人名另查 mock 裡的角色與指派是否相符。歷程類驗收照 Prototype 實際寫入的字樣抄 |
| 沿用規則不寫 | 每條規則的 wiki 正本卡領域標籤與本 project 領域不同，就刪掉，改在 Out of Scope 寫一次沿用 |
| 改規則前列出全部出現處 | 改一條規則前，先列出它出現的每一處：Use Case、Scope、概述、功能節、權限表、milestone 描述。一次改完 |
| 驗收對得到規則 | 每條驗收在同節規則段找到對應條目，找不到依「驗收對不到規則先停」 |
| 實體關係不越界 | 實體關係不複寫狀態轉換、不寫畫面排序與顯示方式 |
| 權限表 | 一列一個動作、一格一個範圍；動作照抄實體卡操作名稱；角色與範圍照抄活動清單卡的執行角色欄與範圍欄 |
| Task 清單 | 只寫名稱；不寫規則、出處、新增標記、串接對應 |
| 來源標記 | 票上沒有情境編號、情境目錄連結、測試檔名 |
| 提及與編號 | issue 寫識別碼、project 用原生提及、不用 Markdown 連結；段內編號各自從 1 起 |
| 收合 | 超過規範檔「收合門檻」的段已收合；功能節整節收合 |

### 步驟 4：審查

| 審查 | 誰做 | 讀什麼 | 產出 |
|------|-----|-------|------|
| 出處核對 | 稽核 sub-agent，模型用 Opus | 完整草稿、規範檔、範例檔，以及 wiki 與情境目錄 | 依規範檔「審查輸出格式」的問題清單 |
| 第二段盲測（wiki → Linear） | 受測 sub-agent，人數與模型依規範檔「盲測受測者」 | 只讀 Linear 草稿 | 判定題答案，與第一段標準答案比對 |
| 第三段盲測（Linear → 開發設計） | 受測 sub-agent，扮演後端或前端，人數與模型同上 | Linear 草稿與開發看得到的 wiki、Prototype | API 清單或頁面與控制元件清單、會回頭問 PM 的問題；Miles 判定 |

- 撰寫者、稽核者、受測者三方分離。受測者之間互不知道答案。
- 盲測在出處核對達合格條件後才跑。盲測找到的問題由主對話依規範檔「問題依嚴重度分類」歸類，併入下一輪問題清單。
- 審查只看規範符合性與出處，不重新審查上游設計（依規範檔「審查範圍」）。
- 是否可免審查，依規範檔門檻值「免派稽核者」。

### 步驟 5：審查循環

| 階段 | 稽核者 | 判不判停 |
|------|-------|---------|
| 換人稽核輪 | 每輪換新稽核者，擴大覆蓋 | 不判停 |
| 續核輪 | 同一位稽核者續核，讓問題收斂為上輪修正的連帶效應 | 依規範檔「停止條件」 |
| 任何輪次 | — | 達規範檔「輪數安全上限」即停 |

輪數與停止條件的值見規範檔門檻值。

- 格式類問題由撰寫者自修，不必為它重審（依規範檔「格式問題自修」）。
- 每輪重審都餵完整的修正後草稿，不暗示改了什麼、上輪哪一筆被點名。
- 不以撰寫者自掃代替重審，未合格不得寫入。
- 每輪記錄：第幾輪、改了什麼、前兩類各幾筆、下一步。
- 前兩類問題追加到 `references/blocked-cases-log.md`，不論最終是否合格。
- 不為了收斂而放水、降標或表面改字。修正必須是真實修正。
- 問題的根源在上游時，依「上游矛盾先停」「驗收對不到規則先停」停下，不在 Linear 上補。
- 規格缺口無法不捏造時，觸發 `oq-manage` mode B，交付文件標「另案處理」。這屬合法缺口，不算問題。

### 步驟 6：寫入 Linear

合格才寫入。依下方「Linear 操作注意事項」寫入，回報每個容器的網址，並請 Miles 確認狀態機圖渲染。

開票順序：

| 順序 | 動作 | 注意 |
|------|------|------|
| 1 | 建 milestone | 名稱依「Milestone 名寫需求主題」 |
| 2 | 開全部 Feature 票 | PM team 建立、不轉隊；掛 milestone 與 Label；取得識別碼 |
| 3 | 覆寫 project 描述 | 把 Feature 票識別碼與範圍句填進 Scope |
| 4 | 依阻擋順序開 Task 票 | PM team 建立，再轉入 FE 或 BE team，以 parentId 掛回 Feature 票 |
| 5 | 建 blocking 關係 | 建在 Task 層，Feature 票不掛 blocked by |
| 6 | 回填原生提及 | project 描述的 Scope 清單在各票建立後回填識別碼 |

## Linear 操作注意事項

| 主題 | 注意事項 |
|------|---------|
| 新 issue 先開在 PM team 再轉隊 | PM team 掛有「同步建立 GitHub backlog issue」自動化；直接開在 FE、BE team 不會產生同步票。流程：`save_issue` 帶 `team: "PM"` 建立，再帶 `id` 與目標 team 轉移。識別碼會換新，GitHub 附件保留 |
| 轉隊會靜默解除 project 關聯 | 目標 team 不在 project 的 teams 清單時，轉隊會拿掉 project 關聯且不報錯。開票前先 `save_project` 帶 `addTeams` 把 FE、BE 加進 project；轉隊後逐票驗回傳的 `projectId` 非空 |
| save_project 觸發狀態跳轉 | 更新 project 描述時，Linear 自動化會把狀態帶到「Kick off」。`save_project` 同時帶交付前的原狀態抑制 |
| 既有票只傳描述 | 覆寫既有票時 `save_issue` 只傳 `id` 與 `description`，其他欄位不傳即不動。例外：Project 全域規劃 milestone、補齊標題前綴與 Label 時可傳 |
| 設 parent 用 UUID | `parentId` 傳識別碼可能不生效，傳 UUID 才穩定。寫入後逐票驗 `parentId` |
| 原生提及的寫法 | 依規範「引用 Linear 資源用原生提及」。issue 寫純識別碼即可，不必先查 UUID；猜錯 UUID 會被降級成純連結 |
| 長內容整份重傳 | `save_issue` 的 `patch` 對中文 `old_string` 常回「not found」。只插一段用 `insert_before`；改多處時重傳完整 `description` |
| save_project 描述是整段覆寫 | 更新某段時重傳完整描述，避免回退既有內容 |
| 進行中的 issue 不覆寫 | 已有內容且 In Progress 的 issue 不覆寫，只由 project 描述引用 |

## 規範演化

交付出現新型錯誤、或要調整審查方式時，依下列順序處理：

| 順序 | 動作 |
|------|------|
| 1 | 把 Miles、稽核者或受測者皺眉的具體原因記進 `references/blocked-cases-log.md` |
| 2 | 歸類到規範檔既有章節；真的放不進既有章節才新增章節 |
| 3 | 寫成帶短名的具體規則，附反例 |
| 4 | 門檻值只改規範檔「門檻值」段 |
| 5 | 用改好的規範檔重新審查範例檔；範例不合格時直接改範例，不回頭追隨 Linear 現行內容 |
| 6 | 在 `references/CHANGELOG.md` 追加版本與理由 |

規範、範本、範例同一次 commit 更新。
