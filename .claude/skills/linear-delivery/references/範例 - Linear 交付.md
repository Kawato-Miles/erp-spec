```markdown
## 概述

需求單讓客戶還在談、尚未成交的印刷需求有一張獨立的單據承載。談成時業務一鍵轉出訂單，談不成時留下流失原因。

現行報價靠業務與印務主管在 Slack 討論，以人工經驗試算，沒有系統化的計價紀錄。談不成的需求沒有留下原因，管理層無從分析流失趨勢。

## 使用情境

### Use Case

1. 業務接到詢價，建立需求單，逐筆登記印件項目與難易度。
2. 業務指定印務主管送出成本評估。
3. 印務主管在討論串回覆成本或自行填入，業務依回覆補齊成本估算。
4. 業務或諮詢按評估完成。
5. 業務進入議價，與客戶逐件談單價。
6. 客戶接受時業務標記成交並轉出草稿訂單；不接受時標記流失並選原因。

### Scope（功能票清單）

1. **需求單建立**：業務把客戶要印的東西登記成一張需求單並送出成本評估。　PM-1207
2. **成本評估與報價**：印務主管填成本、業務拿到報價依據、與客戶談定單價並標記成交。　PM-1215
3. **需求單結案與轉單**：業務把已成交的需求單轉成訂單，談不成的標記流失，客戶回頭時重新啟動。　PM-1338
4. **需求單複製與改派**：業務從過往需求單起手，業務主管與 Supervisor 在人員異動時換接單業務。　PM-1216

**Out of Scope**

* 成交轉訂單後各欄位在訂單上的行為：歸 <project id="4927231b-7fe3-407e-8d1f-94eddc3f0a84" href="https://linear.app/sensationdeveloper/project/%E4%B8%AD%E5%8F%B0-%E8%A8%82%E5%96%AE%E7%AE%A1%E7%90%86-414a81747028/overview">中台 - 訂單管理</project>。
* 諮詢單的受理與轉需求單動作：歸 <project id="9fd00109-9eb8-4c5e-95c7-7e2f2698f303" href="https://linear.app/sensationdeveloper/project/%E4%B8%AD%E5%8F%B0-%E8%AB%AE%E8%A9%A2%E5%96%AE%E7%AE%A1%E7%90%86-22b742656b48/overview">中台 - 諮詢單管理</project>。
* 單據分享的層級與代理行為：沿用 <project id="4927231b-7fe3-407e-8d1f-94eddc3f0a84" href="https://linear.app/sensationdeveloper/project/%E4%B8%AD%E5%8F%B0-%E8%A8%82%E5%96%AE%E7%AE%A1%E7%90%86-414a81747028/overview">中台 - 訂單管理</project> 的 PM-1086。

>>> ### 需求單狀態機

​```mermaid
stateDiagram-v2
    direction LR

    [*] --> s_confirm : 業務建立需求單／諮詢轉入自動建立

    state "進行中" as InProgress {
        direction LR
        state "需求確認中" as s_confirm
        state "待評估成本" as s_wait
        state "已評估成本" as s_est
        state "議價中" as s_nego
        s_confirm --> s_wait : 業務送印務評估 · 印件項目難易度皆已填
        s_wait --> s_est : 業務或諮詢評估完成 · 全部印件項目成本估算填畢
        s_est --> s_nego : 業務進入議價
        s_nego --> s_wait : 重新評估報價 · 議價後價格不滿意
    }

    state "終態" as Final {
        state "成交" as s_won
        state "流失" as s_lost
    }

    s_nego --> s_won : 客戶接受報價，業務標記成交
    InProgress --> s_lost : 業務標記流失 · 須選流失原因
    s_lost --> s_wait : 業務重新啟動 · 須填重啟原因

    s_won --> [*]
    s_lost --> [*]
    InProgress --> [*] : 刪除需求單 · 接單業務、建立者或被分享（編輯）者
    Final --> [*] : 刪除需求單 · 接單業務、建立者或被分享（編輯）者

    note right of s_won
        終態，成交後需求單鎖定
    end note
    note right of s_lost
        終態，業務可重新啟動
    end note
​```

>>> ## 成本估算與預計產線修改

身為印務主管，我要把各筆印件項目的成本填進需求單，以讓業務直接拿到數字、不必在 Slack 來回。

**實體關係**

1. 每次修改成本估算，系統記下修改人，以及修改前與修改後的值。
2. 報價紀錄保留評估當下的成本估算，不隨之後的修改改變。
3. 修改成本估算後，系統依成本評估完成節的利潤率算式，重算該筆印件項目的利潤率。

**驗證規則**

1. 需求單在需求確認中、待評估成本、已評估成本，才可修改成本估算與預計產線。
2. 需求單在議價中時，開啟印件側板會提示要改成本請按重新評估。

**驗收**

1. 假設 Q-20261012-01 的接單業務為洪嘉駿、被指派的評估印務主管為吳國豪，需求單停在待評估成本、甲印件成本估算 20，當吳國豪把成本估算改為 25，則成本估算為 25，活動紀錄記「吳國豪 編輯印件「甲印件」成本估算（未稅）：20 → 25」。
2. 假設 Q-20261012-01 停在已評估成本、報價紀錄一筆且其中甲印件成本估算 25，當吳國豪把成本估算改為 35，則成本估算為 35，該筆報價紀錄的成本估算仍為 25。
3. 假設 Q-20261012-01 在議價中，當洪嘉駿開啟甲印件的印件側板，則成本估算與預計產線不可修改，並提示「議價中不可直接改成本，要改請按「重新評估」」。

>>> ## 成本評估完成

身為業務，我要在成本填齊後按評估完成，以留下一份當下的報價依據。

**實體關係**

1. 按評估完成時，系統寫入一筆報價紀錄。報價紀錄記下輪次，以及各印件項目當下的成本估算、單價、小計與利潤率。
2. 一張需求單有多筆報價紀錄，輪次逐次加一。
3. 報價紀錄記評估者與評估時間。評估者是按評估完成的人。

**驗證規則**

1. 需求單在待評估成本才可評估完成。
2. 需求單沒有任何印件項目時，不可評估完成。
3. 任一印件項目成本估算為空時，不可評估完成，系統列出缺漏的印件項目。
4. 單價未填不擋評估完成。

**算式**

​```
利潤率 ＝（小計 − 成本估算）÷ 小計，以百分比呈現，四捨五入至小數點後兩位
​```

1. 小計為空或為 0 時，利潤率為空。

**驗收**

1. 假設 Q-20261012-01 的接單業務為洪嘉駿，需求單停在待評估成本、甲印件成本估算 25、單價未填，當洪嘉駿按評估完成，則狀態轉已評估成本，新增一筆報價紀錄，評估者為洪嘉駿，甲印件的利潤率為空。
2. 假設 Q-20261012-01 經重新評估回到待評估成本、甲印件數量 100、單價 0.5、成本估算 25，當洪嘉駿按評估完成，則新增第二筆報價紀錄，其中甲印件利潤率 50.00%。
3. 假設 Q-20261012-01 停在待評估成本、甲印件成本估算為空，當洪嘉駿按評估完成，則系統不受理並列出甲印件，狀態仍為待評估成本。

>>> ## 單價修改

身為業務，我要逐件填入與客戶談定的單價，以讓每筆金額都有依據。

**實體關係**

1. 單價填在印件項目上，每筆印件項目一個單價。
2. 單價修改後，系統依算式重算小計，小計算出即定案。
3. 小計重算後，系統依成本評估完成節的利潤率算式，重算該筆印件項目的利潤率。

**驗證規則**

1. 需求單在議價中才可修改單價。

**算式**

​```
小計 ＝ 數量 × 單價，四捨五入至整數元
​```

**驗收**

1. 假設 Q-20261012-01 的接單業務為洪嘉駿，需求單在議價中，當洪嘉駿把數量 100 的甲印件單價填為 0.5，則甲印件單價為 0.5、小計 50。
2. 假設 Q-20261012-01 停在已評估成本，當洪嘉駿開啟甲印件的印件側板，則單價不可修改。

>>>

>>> ## 重新評估報價

身為業務，我要在客戶改規格或嫌價格時把需求單退回重估，以讓新的報價有成本依據。

**實體關係**

1. 重新評估時既有報價紀錄保留，再次評估完成會新增一筆。
2. 重新評估時可選填調整說明，填了就記進活動紀錄。
3. 重新評估後，系統在這張需求單原本的 Slack 討論串回覆，帶入操作者與調整說明，並提及全部評估印務主管。
4. 找不到原本的討論串時，系統改在需求單頻道發一則新訊息。
5. 通知發送失敗時，系統自動重試。
6. 重試仍失敗時，需求單照常轉待評估成本。

**驗證規則**

1. 需求單在議價中才可重新評估報價。

**驗收**

1. 假設 Q-20261012-01 的接單業務為洪嘉駿，需求單在議價中、報價紀錄一筆，當洪嘉駿按重新評估並填調整說明「客戶改磅數」送出，則狀態轉待評估成本，報價紀錄仍為一筆，活動紀錄留下「客戶改磅數」。
2. 假設 Q-20261012-01 在議價中、已有 Slack 討論串、評估印務主管為吳國豪，當洪嘉駿按重新評估並填調整說明「客戶改磅數」送出，則原討論串新增一則回覆，內容含洪嘉駿與「客戶改磅數」，並提及吳國豪。

>>>

>>> ## 成交標記

身為業務，我要在客戶接受報價後標記成交，以把談定的金額落定。

**實體關係**

1. 成交後需求單的單頭一般欄位與印件項目鎖定，不可再修改。
2. 需求備註在成交後仍可修改。

**驗證規則**

1. 需求單在議價中才可成交。
2. 需求單沒有任何印件項目時，不可成交。
3. 任一印件項目單價為空時不可成交，系統列出缺漏的印件項目。

**驗收**

1. 假設 Q-20261012-01 的接單業務為洪嘉駿，需求單在議價中、甲印件單價 0.5，當洪嘉駿按成交，則狀態轉成交。
2. 假設 Q-20261012-01 已成交，當洪嘉駿修改甲印件，則系統提示「需求單已成交，印件不可再修改」。
3. 假設 Q-20261012-01 在議價中、甲印件單價為空，當洪嘉駿按成交，則系統不受理並列出甲印件，狀態仍為議價中。

| 一節一個動作 | 修改成本估算與預計產線、評估完成、修改單價、重新評估、標記成交各有自己的規則，拆開才看得出各自的規則與驗收；成本估算與預計產線在同一個側板一起送出，算一個動作 |
| 算式段在成本評估完成與單價修改 | 利潤率算式放在成本評估完成，修改成本或單價後依它重算；小計算式放在單價修改。同一條算式只寫一處 |
| 每條驗收都有同節規則 | 例如成本評估完成驗收 3 對到驗證規則 3；開發照規則實作、照驗收自測 |
| 另案處理 | 來源尚未定案的項目放在功能節之後，不散進節內 |
