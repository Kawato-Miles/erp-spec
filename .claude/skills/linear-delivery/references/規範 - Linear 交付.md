# 規範 - Linear 交付

交付到 Linear 的寫法規則與評分標準，只寫在本檔。撰寫者照本檔寫，評分者照本檔評。

- 骨架（段落與占位）：`範本 - Linear 交付.md`。骨架不放規則。
- 合規樣貌：`範例 - Linear 交付.md`。範例是依本檔評分達合格分數的真實交付。
- 流程（何時做什麼、誰評分、何時停）：`SKILL.md`。流程用到的門檻值見本檔 § 十一。
- 規則以粗體短名開頭。其他檔以短名引用本檔規則，不複寫內容。

---

## 一、正本邊界

1. **Linear 自包含**：對開發而言 Linear 是交付正本。交付內容讀得懂、做得出來，不需要打開別的系統。跨單據只以 Linear 識別碼互指。
2. **不外露內部檔**：交付內容不出現 `openspec/...` 路徑、任何 `.md` 內部檔路徑、內部檔名、內部問題編號（OQ 編號）與 PM 內部流程術語（change、delta、archive）。
3. **不引用 Notion**：不以 Notion 頁面或資料庫連結作為交付依據。
4. **不寫欄位表**：資料欄位的正本在 wiki 實體卡，開發直接查閱。交付不產資料欄位段、不複寫欄位表。
5. **介面歸 Prototype**：操作方式、畫面動線與版型以 Prototype 為準。交付不文字重述操作動線，不附 Prototype 參照格，不另附「為準／不為準」邊界表，不開設計票。
6. **不寫指路句**：不寫「欄位正本：wiki ○○卡」「狀態列舉正本為 wiki ○○卡」。wiki 是取材來源，不出現在票文。
7. **不寫 meta 導覽句**：不寫「實作由本票底下的 sub-issue 承載」「本票是○○的商業邏輯與驗收條件正本」「詳細規則請見上層 project 描述」「需求本體見○○」。巢狀關係、Label 與 blocking 關係本身就是資訊。
8. **引用 Linear 資源用原生提及**：引用 project 或 issue 時產生 Linear 原生提及。issue 直接寫識別碼（如 `PM-1084`），寫入後 Linear 自動轉成提及元素。project 寫 `<project id="<UUID>" href="<URL>/overview">名稱</project>` 元素。不用純文字「本 project」，不用 Markdown `[名稱](URL)` 連結。
9. **wiki 卡不外連**：票內提到 wiki 卡時用純文字，不外連 GitHub。

## 二、分層與顆粒度

| 層 | 是什麼 | 顆粒度 | Label |
|----|--------|--------|-------|
| Project | 薄目錄＋商業脈絡 | 一個平台的一個模組 | — |
| Milestone | 需求主題 | 一組要一起交付的功能 | — |
| Feature 票 | 一個需求主題的需求正本 | 一票一個需求主題；票內一個功能節裝一個功能顆粒 | Type/Feature、Product、Role/PM |
| Task 票 | 該功能的職能實作 | 一職能一張 | Type/Task、Product、Role/Backend 或 Frontend |
| Sub-Task 票、Bug 票 | Task 再往下切 | 開發自行判斷 | 依需要 |

1. **由大到小順讀**：project 讀方向、milestone 讀這批要交付什麼、Feature 票讀需求本體、Task 票讀自己要交付的行為。讀者不需回頭跳層。
2. **功能節是顆粒度載體**：一節出現兩條互不相干的流程主線，或驗收條件超過 § 十一的上限，就拆節。沒有這兩種情形時不拆節：同一功能的規則，不因規則類別不同而拆成多節。需求主題之間互不相干才拆票，拆出的票掛同一個 milestone。
3. **內容只在一層寫**：

| 內容 | 正本層 | 其他層怎麼寫 |
|---|---|---|
| 狀態列舉、狀態流轉、轉換條件 | project 的狀態機圖 | 一句「狀態流轉見 ○○ 的○○狀態機」加原生提及 |
| 商業規則、值域、驗收條件 | Feature 票 | Task 票以規則短名括註，不複寫 |
| 該職能的實作契約、衍生資料、介面回傳 | Task 票 | project 與 Feature 票不寫 |
| 模組層 What、Use Case、功能票清單 | project 描述 | 票內不重述 |

4. **不複寫狀態機**：Feature 票與 Task 票不把狀態流轉改寫成表格或條列。票只寫該層要實作的衍生行為。
5. **沿用規則不寫**：規則的家在別的功能時，本 project 的 Feature 票不寫、project 描述不寫，也不寫「套用某處規則」的引用句。Task 票以規則名直接引用（如「依訂單的可見範圍過濾」）。判準見下表，任一成立即為沿用規則。

| 判準 | 例子 |
|------|------|
| 規則的 wiki 正本卡領域不等於本 project 領域 | 訂單可見範圍的規則家在訂單管理，出現在款項管理 project |
| 同平台既有 Feature 票已有該規則的功能節 | 開票前用 `list_issues` 掃同平台 Feature 票的功能節名 |

6. **規則重複代表拆錯**：同一條規則出現在兩張以上 Feature 票，代表拆法錯，或規則的家在別的功能。先修拆法。搬進 project、或改寫成引用句都不算修好。
7. **Task 票單一歸屬**：一張 Task 票只服務一張 parent Feature 票。出現多個主要歸屬，代表 Feature 票切太細，回頭以功能顆粒重切。
8. **改規則同掃各層**：改一條規則時，同時檢查 project 描述、milestone 描述、Feature 票、Task 票。改動只落在一處，其餘各處的舊說法會變成矛盾。改 Feature 票規則段時，核對旗下 Task 票的短名引用是否仍指得到；短名改名或刪除時同步修 Task 票。

## 三、Project 描述

必要區塊：概述、使用情境（Use Case、Scope）、測試決策、另案處理、狀態機（狀態密集模組）。

1. **概述**：寫商業目標與現行問題痛點，取材 wiki 痛點卡與商業邏輯卡的「現況」段。不寫功能清單。
2. **Use Case**：業務敘事白話句，寫「角色 × 業務動作」。可跨 project 講完整業務故事。取材 wiki 業務情境。
3. **Scope 一條一票**：一條 Scope 對應一張 Feature 票。每條寫票名、一句用戶故事式範圍句與原生提及。範圍句講清楚誰用它做到什麼。

| 正例 | 反例 |
|------|------|
| **印件製作細節確認**：訂單管理人逐張確認印件的製作條件，確認後生產端拿到工單草稿。 | **印件製作細節確認**：處理印件製作細節的相關邏輯與流程。（看不出誰用、做到什麼） |

4. **Out of Scope 附歸屬**：每條不做項寫明歸屬：延後批次、其他 project 或其他平台。
5. **測試決策只寫一處**：列受測介面（數量見 § 十一），每個介面一句「從外部可觀察到什麼行為」。寫明測試基準（只驗可觀測行為）與測試先行（期望值取自 Feature 票驗收條件，不由實作重算）。這段說明只在 project 寫一次，票內不重複。
6. **另案處理**：來源尚未定案的缺口列在這裡，附現狀處置。
7. **不設角色的解讀節**：權限主詞一律用 wiki 角色名。角色與權限組合的設計，正本在角色權限管理模組的 Feature 票。
8. **Project 不放的內容**：功能的需求描述、商業邏輯與驗收條件（歸 Feature 票）、操作方式（歸 Prototype）、實作契約（歸 Task 票）、資料欄位表（歸 wiki）、職能分工區塊與票號對照（Label 與父子階層已承載）。
9. **擴充融入既有段落**：迭代交付擴充 project 描述時，在原清單上加條目，缺的標準區塊可新增。不在描述尾端另起一個平行的完整區塊。
10. **後續批次只長清單**：後續批次在 Scope 加條目、開新 Feature 票掛新 milestone，project 不長章節。

## 四、Milestone

1. **Milestone 名寫需求主題**：如「工單主流程」「印件製作細節」。不寫日期或批次名（如「2026-08 工單編輯批」「第三批」）。
2. **一個 milestone 收多張 Feature 票**：先後順序即整合順序。
3. **建了就全掛**：是否建 milestone 依該批拍板；建了就每張 Feature 票都掛。
4. **全域規劃時既有票補掛**：Project 全域規劃 milestone 時，既有票一律補掛，含已完成的票。

## 五、Feature 票

1. **Feature 標題格式**：`[ Feature ] - <功能語意>`。前綴之後只寫功能語意，不帶職能字樣。
2. **概述一句**：一句話講這張票讓誰做到什麼，所屬模組以 project 原生提及帶出。需要時另起一句狀態流轉引用句（依「內容只在一層寫」），不算違反本條。
3. **功能節段落齊備**：每個功能節固定包含節名、使用者故事、規則、驗收條件。缺任一段不得發布。
4. **功能節整節收合**：節名留在收合外，使用者故事、規則、驗收條件都在收合內。清單頁只看得到節標題。
5. **節名業務讀得懂**：念給沒參與討論的業務或開發聽，對方說得出這節在做什麼。不用內部造詞與縮寫。
6. **使用者故事**：一句「身為（角色），我要（動作），以（業務目的）」。角色寫 wiki 角色名，不寫「使用者」「系統管理者」。業務目的寫這件事對生意的作用。

| 正例 | 反例 |
|------|------|
| 身為訂單管理人，我要在訂單確認後逐張確認印件的製作細節，以讓生產端拿到可以開工的工單草稿。 | 本功能提供印件製作細節的確認機制，供訂單管理人使用。（功能說明句） |

7. **適用範圍歸規則**：「僅適用線下單」這類句子寫在規則段，不寫在使用者故事。
8. **規則帶短名**：每條規則以粗體短名開頭（如「**稅額取整**：稅額＝未稅金額 × 5%，小數捨去」）。短名是跨票引用鍵，兩條規則不得同名。編號只供票內閱讀，不作為引用介面。
9. **規則結構化**：依 § 七「結構化寫法」選表格、算式區塊或編號條列。
10. **算式只在 Feature 票**：金額、數量、日期的推導只寫在 Feature 票功能節的算式區塊。
11. **Feature 票不寫實作**：本票不是開發工作票，不寫實作內容。
12. **Feature 票結構件**：掛 milestone、掛 Label（見 § 二）、作為其 Task 票的 parent。
13. **驗收有對應規則**：每條驗收條件檢查的行為，同一節的規則段都有對應的規則。只寫在驗收、規則段沒寫的行為，要補進規則段。驗收只驗本功能的規則；沿用規則的行為不寫進驗收，由它的正本票驗收。權限規則的反面（其他人不能改）屬本功能規則，規則段要寫。
14. **Feature 另案段**：本票來源未定案的項目，放在所有功能節之後的「另案處理」收合段。這一段不是功能節，不受「功能節段落齊備」約束。

## 六、Task 票

1. **Task 標題格式**：`[ Task ] - <功能語意>`。前綴之後只寫功能語意，不帶「（前端）」「（後端）」「FE」「BE」。
2. **Task 段落齊備**：背景、規則、驗收、範圍都要有。
3. **背景寫使用者故事**：一句，講這個職能要交付什麼。不寫錨點句與 meta 句。
4. **規則是實作契約**：只寫這個職能要保證的行為：介面回傳、檢核、衍生資料、錯誤處置、邊界值處理。每條規則括註至少一條 Feature 票規則短名（如「依『稅額取整』」），不重述判準與門檻數字。沒有括註的規則，只允許「通用實作契約」所列；其他沒有括註的規則視為過度設計。
5. **不寫手段詞**：交易、回滾、鎖、快取、樂觀更新、查詢時聚合、旗標、序列產生器、多對多、可空關聯等技術手段一律不寫。手段由開發決定。

| 正例 | 反例 |
|------|------|
| 訂單管理人確認製作細節時，印件狀態推進與工單草稿建立要同時成立，不允許只成立其中一件。 | 印件印製維度推進與空工單建立為同一個交易，任一步失敗一起回滾。 |

6. **通用實作契約**：下列規則不需括註 Feature 規則短名即可寫：

| 通用實作契約 | 說明 |
|------------|------|
| 值域外不受理 | 送來的值不在規則定的值域內，就拒絕 |
| 拒絕時回覆原因 | 拒絕時回覆使用者讀得懂的原因 |

7. **Task 規則不新增可見行為**：Task 規則不新增使用者看得到的按鈕、欄位、狀態或提示文字內容。這些只能來自 Feature 票；介面呈現歸 Prototype。
8. **Task 票不寫算式**：以短名括註引用 Feature 票的算式，不重抄。
9. **驗收落在受測介面**：驗收條數見 § 十一。每條標受測介面，受測介面要在 project 測試決策議定的範圍內；範圍外的介面先回頭補議定。
10. **期望值取自具名案例**：驗收的前提情境取自 parent 驗收條件的具名案例；期望結果可以再加上本票規則段的行為。期望值必須是受測介面上看得到的值，不與實作同式重算，不用引擎中間值。
11. **範圍段內容**：只取用、不自行實作的依賴；判定為不做的項目，附原因。
12. **不寫 Blocked by 段**：阻擋關係以 Linear 原生 blocking 建在 Task 層。
13. **Task 票平鋪**：背景與驗收永遠平鋪；單一段落超過 § 十一的收合門檻時才收合該段。
14. **Task 票結構件**：掛 Label（見 § 二），parent 掛對 Feature 票。
15. **Task 票不空洞**：不可只剩「見父票」一句而沒有規則與驗收。

## 七、共用寫法

1. **受控句法**：依 `~/.claude/output-styles/ste100-pm.md` 撰寫：白話完整句、一句一事、業務主管唸得順。
2. **禁中英夾雜**：英文識別碼用「中文（英文）」格式。
3. **現在式**：只寫系統現在是什麼。不寫設計對比語言（合一、統一、取代、不再、原本）。
4. **精練不複寫**：wiki 到 Linear 是精練：每過一站只准變準、不准變厚。票文不標 wiki 卡名。
5. **權限主詞用角色名**：寫業務主管、生管、印務，不寫「具全公司檢視權限者」。
6. **流程用表格，規則用句子**：

| 內容性質 | 判準 | 呈現方式 |
|---------|------|---------|
| 流程 | 有角色接力或時序先後 | 表格，欄位固定：步驟、角色、行為、系統結果 |
| 規則 | 單點的 if-then、約束、門檻、適用範圍 | 受控句法句子 |

判不出時問：刪掉這句，讀者是否就不知道下一棒是誰。是，就是流程；否，就是規則。功能節沒有角色接力或時序先後時，不放流程表；把規則改寫成表格也不算流程表。流程表的「行為」欄只寫業務動作，不寫畫面區塊、按鈕、點擊等操作方式。

7. **結構化寫法**：

| 內容性質 | 用什麼 |
|---|---|
| 誰存什麼、哪種情況走哪條路、狀態怎麼推導 | 表格 |
| 金額、數量、日期的推導 | 程式碼區塊，一行一式 |
| 條件與限制 | 編號條列，一條一件事 |

不寫：一句塞多條規則、括號裡再套括號、分號串接三件以上、算式夾在敘事句中間。

8. **段內各自編號**：每個小標題底下的編號清單從 1 開始，不跨段續編。編號無法正確呈現時，整張票改用項目符號。
9. **長段收合**：超過 § 十一收合門檻的流程表格、狀態機圖、逐條規則清單收進收合區塊。Feature 功能節依 § 五「功能節整節收合」。
10. **收合先試寫**：批次套用收合前，先寫一張票，確認 Linear 與 GitHub 同步票兩面都渲染正常，再套用其餘票。渲染不如預期時改回平鋪。
11. **Label 分類**：

| 分類 | 值域 | 用途 |
|----|------|------|
| Role | Backend、Frontend、Design、PM | 承載職能 |
| Product | ERP、EC、編輯器 | 承載產品線 |
| Type | Feature、Task、Bug | 承載層級 |

Label 取工作區既有分組，不自創新值。Type 必掛且與標題前綴一致。缺 Label 等於缺資訊。

12. **Linear 已呈現的不寫**：

| 不寫 | 原因 |
|---|---|
| 巢狀關係、Blocked by | 介面已呈現 |
| 日期註記（如「（2026-08-26 補齊）」） | 妨礙閱讀；拍板紀錄在 wiki |
| 父票已寫的規則 | 同一條規則只在一處維護 |
| 票內已寫的內容再寫進留言 | 同上 |

## 八、狀態機

1. **狀態機逐一附圖**：狀態密集模組的每個狀態機附一張 Mermaid `stateDiagram-v2` 圖，含狀態節點、轉換箭頭、觸發或條件標籤。關鍵終態與不可逆轉換用 `note` 標。
2. **狀態機忠實轉繪**：狀態列舉與轉換取材 wiki 狀態機卡，不畫來源未定義的轉換。
3. **雙維度分開畫**：雙維度狀態（如審稿與印製、開票與收款）各畫一張，不擠成一張。
4. **視圖層沿用**：視圖層 project 沿用核心 project 的圖，不另繪；已在其他 project 繪製的狀態機用原生提及引用。
5. **狀態圖寫法**：中文狀態代號不加標點。轉換標籤不用半形括號，改用「·」或全形。
6. **渲染眼見確認**：寫入後請 Miles 開頁面確認渲染成圖。顯示為程式碼時改其他形式。

## 九、修正與留言

1. **票主體是正本**：內容與現行定案不符就直接改票主體，不因票已完成而保留錯的內容。
2. **修正性質決定承載**：

| 修正性質 | 承載方式 |
|---|---|
| 行為與定案不符（缺陷） | 改票主體並寫留言；票已完成時狀態改回 Todo |
| 既有功能加新行為（優化） | 開 Task sub-issue，parent 掛該功能的原票 |
| 牽出一個新功能顆粒 | 開新 Feature 票 |

3. **開票前先問**：開 sub-issue 或新 Feature 票前先問 Miles。
4. **缺陷留言分訂正與實測**：

| 留言 | 標題 | 內容 |
|---|---|---|
| 訂正紀錄 | 票主體訂正的內容 | 原本怎麼寫、現行定案是什麼，用對照表；新補的內容也列進表 |
| 實測修正 | `<YYYY-MM-DD> 實測後要請開發修正的內容` | 現況問題（系統現行行為對期望行為的表格）、修正規則（編號條列）、確認不是問題的項目 |

5. **主體附留言連結**：改寫的段落後加「（[參考留言](<票網址>#comment-<留言 id 前 8 碼>)）」，指向訂正紀錄。
6. **實測留言 tag 負責人**：實測修正留言的標題下一行寫 `@<負責人 displayName>`，displayName 以 `get_user` 查。
7. **留言不寫手段**：不列程式碼檔案位置、函式名或改法。
8. **留言不寫依據與 meta 句**：不寫依據卡名、日期、拍板人，不寫「票已從 Done 轉回 Todo」「詳見下一則留言」。
9. **同次訂正只留一則**：範圍擴充併入既有訂正紀錄。
10. **刪留言前先遷移**：舊留言仍被主體連結引用時，先把有效內容併入新留言、把連結改指新留言，再刪舊留言。
11. **不做的也寫**：判定不做時，寫進範圍段或留言並附原因。
12. **改回 Todo 要說明**：已完成的票改回 Todo 會清空完成時間並移入當前 cycle，交付回報時說明。

## 十、評分維度

評分者依下表逐維度給分，每個維度引用草稿的具體位置作為證據。

| 維度 | 檢查的規則 | 2 分 | 1 分 | 0 分 |
|------|-----------|------|------|------|
| D1 正本邊界 | § 一 | 無任何違規 | 有違規，但未達 0 分所列情形 | 核心內容指向內部檔，或指路句、meta 導覽句成片出現 |
| D2 分層與顆粒度 | § 二、§ 五 使用者故事至算式、§ 六 規則至算式、§ 七 | 分層乾淨；使用者故事、流程表格、規則短名合格；Task 票全為實作契約且無手段詞 | 有違規，但未達 0 分所列情形 | project 藏規則本體、Task 票空洞或成段複寫 Feature 規則、手段詞成片、寫法系統性違規 |
| D3 完整性 | § 三 必要區塊、§ 五 驗收有對應規則、§ 八 | 必要區塊齊、狀態機圖齊、每個有業務結果的功能節有驗收條件且未混入通用品質門檻 | 有缺漏，但未達 0 分所列情形 | 狀態密集卻無圖、缺核心區塊、有業務結果的功能完全無驗收 |
| D4 真實性 | 下方「真實性」 | 全部有據，缺口已標另案 | 無 1 分 | 任一處捏造 |
| D5 交付結構 | § 三 測試決策、§ 四、§ 五 標題與結構件、§ 六 標題、驗收與結構件、§ 七 收合與 Label | 結構件全齊，Task 驗收落在受測介面且期望值取自具名案例 | 有缺漏，但未達 0 分所列情形（如單張 Task 票缺範圍段、單張票 Label 缺一類） | 系統性缺失（單節裝多功能、全部 Task 票無驗收、無測試決策、全批未掛 milestone） |

**真實性**：交付內容的規則、狀態、數值都來自已定案的 wiki 與 OpenSpec。來源未定義時停下，觸發 `oq-manage` mode B，交付文件標「另案處理」。不用「應該、大概、通常」的推測當定案，不為了看起來完整補上沒有依據的轉換、公式或驗收情境。標另案不扣分。

**評分範圍**：評分只看交付文件是否符合本檔、規則能否對應到整理來源、缺料處是否已標另案。不重新審查上游設計。

```

D3 完整性：...
D4 真實性：2 / 0

```
