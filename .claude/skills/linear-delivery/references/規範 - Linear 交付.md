# 規範 - Linear 交付

交付到 Linear 的寫法規則與評分標準，只寫在本檔。撰寫者照本檔寫，評分者照本檔評。

- 骨架（段落與占位）：`範本 - Linear 交付.md`。骨架不放規則。
- 合規樣貌：`範例 - Linear 交付.md`。範例是依本檔評分達合格分數的真實交付。
- 流程（何時做什麼、誰評分、何時停）：`SKILL.md`。流程用到的門檻值見本檔 § 十一。
- 規則以粗體短名開頭。其他檔以短名引用本檔規則，不複寫內容。

---

## 一、正本邊界

1. **Linear 自包含**：對開發而言 Linear 是交付正本。交付內容讀得懂、做得出來，不需要打開別的系統。跨單據只以 Linear 識別碼互指。
2. **不外露內部檔**：交付內容不出現 `openspec/...` 路徑、任何 `.md` 內部檔路徑、內部檔名、內部問題編號（OQ 編號）與 PM 內部流程術語（change、delta、archive）。
3. **不引用 Notion**：不以 Notion 頁面或資料庫連結作為交付依據。
4. **不寫欄位表**：資料欄位的正本在 wiki 實體卡，開發直接查閱。交付不產資料欄位段、不複寫欄位表。
5. **介面歸 Prototype**：開發對著 Prototype 實作。欄位有哪些、值域、版面、按鈕、操作動線、單一欄位的必填與格式都以 Prototype 為準，交付不文字重述，不附 Prototype 參照格，不另附「為準／不為準」邊界表，不開設計票，不寫「其餘依 Prototype」這類句子。
6. **不寫指路句**：不寫「欄位正本：wiki ○○卡」「狀態列舉正本為 wiki ○○卡」。wiki 是取材來源，不出現在票文。
7. **不寫 meta 導覽句**：不寫「實作由本票底下的 sub-issue 承載」「本票是○○的商業邏輯與驗收條件正本」「詳細規則請見上層 project 描述」「需求本體見○○」。巢狀關係、Label 與 blocking 關係本身就是資訊。
8. **引用 Linear 資源用原生提及**：引用 project 或 issue 時產生 Linear 原生提及。issue 直接寫識別碼（如 `PM-1084`），寫入後 Linear 自動轉成提及元素。project 寫 `<project id="<UUID>" href="<URL>/overview">名稱</project>` 元素。不用純文字「本 project」，不用 Markdown `[名稱](URL)` 連結。
9. **wiki 卡不外連**：票內提到 wiki 卡時用純文字，不外連 GitHub。
10. **權限不寫實作**：票只寫權限名稱、動作、範圍。權限代碼、角色與權限的對應、後端怎麼判定都由後端決定，不寫進票。

## 二、分層與顆粒度

| 層 | 回答的問題 | 顆粒度 | Label |
|----|-----------|--------|-------|
| Project | 這個模組為什麼存在、誰用它做什麼、要做哪幾塊 | 一個平台的一個模組 | — |
| Milestone | 這批要一起交付什麼 | 一組要一起交付的 Feature 票 | — |
| Feature 票 | 這一塊做完，使用者能完成什麼事 | 一票一個需求主題；票內一個功能節裝一個動作 | Type/Feature、Product、Role/PM |
| Task 票 | 這個職能要交付什麼行為 | 一職能一張 | Type/Task、Product、Role/Backend 或 Frontend |
| Sub-Task 票、Bug 票 | Task 再往下切 | 開發自行判斷 | 依需要 |

1. **由大到小順讀**：project 讀方向、milestone 讀這批要交付什麼、Feature 票讀需求本體、Task 票讀自己要交付的行為。讀者不需回頭跳層。
2. **功能節是顆粒度載體**：一節寫使用者的一個動作。一節出現兩個互不相干的動作，或驗收條數超過 § 十一的上限，就拆節。需求主題之間互不相干才拆票，拆出的票掛同一個 milestone。
3. **內容只在一層寫**：

| 內容 | 正本層 | 其他層怎麼寫 |
|---|---|---|
| 狀態列舉、狀態流轉、轉換條件 | project 的狀態機圖 | 一句「狀態流轉見 ○○ 的○○狀態機」加原生提及 |
| 權限、實體關係、驗證規則、算式、驗收條件 | Feature 票 | Task 票以功能節名括註，不複寫 |
| 該職能的實作契約、衍生資料、介面回傳 | Task 票 | project 與 Feature 票不寫 |
| 模組層 What、Use Case、Scope | project 描述 | 票內不重述 |
| 欄位、值域、版面、操作動線 | Prototype | 各層都不寫 |

4. **不複寫狀態機**：Feature 票與 Task 票不把狀態流轉改寫成表格或條列。功能節的驗證規則只寫該動作要求的狀態條件。
5. **沿用規則不寫**：規則的家在別的功能時，本 project 的 Feature 票不寫、project 描述不寫，也不寫「套用某處規則」的引用句。Task 票以功能節名直接引用（如「依訂單的可見範圍過濾」）。判準見下表，任一成立即為沿用規則。

| 判準 | 例子 |
|------|------|
| 規則的 wiki 正本卡領域不等於本 project 領域 | 訂單可見範圍的規則家在訂單管理，出現在款項管理 project |
| 同平台既有 Feature 票已有該規則的功能節 | 開票前用 `list_issues` 掃同平台 Feature 票的功能節名 |

6. **規則重複代表拆錯**：同一條規則出現在兩張以上 Feature 票，代表拆法錯，或規則的家在別的功能。先修拆法。搬進 project、或改寫成引用句都不算修好。
7. **Task 票單一歸屬**：一張 Task 票只服務一張 parent Feature 票。出現多個主要歸屬，代表 Feature 票切太細，回頭以功能顆粒重切。
8. **改規則同掃各層**：改一條規則時，同時檢查 project 描述、milestone 描述、Feature 票、Task 票。改動只落在一處，其餘各處的舊說法會變成矛盾。改功能節名時同步修 Task 票的括註。

## 三、Project 描述

必要區塊：概述、使用情境（Use Case、Scope）、另案處理、狀態機（狀態密集模組）。

1. **概述**：寫商業目標與現行問題痛點，取材 wiki 痛點卡與商業邏輯卡的「現況」段。不寫功能清單。
2. **Use Case**：業務敘事白話句，寫「角色 × 業務動作」。可跨 project 講完整業務故事。取材 wiki 業務情境。
3. **Scope 一條一票**：一條 Scope 對應一張 Feature 票。每條寫票名、一句「做完後使用者能做到什麼」與原生提及。

| 正例 | 反例 |
|------|------|
| **需求單建立**：業務把客戶要印的東西登記成一張需求單並送出成本評估。 | **需求單建立**：處理需求單建立的相關邏輯與流程。（看不出誰用、做到什麼） |

4. **Out of Scope 附歸屬**：每條不做項寫明歸屬：延後批次、其他 project 或其他平台。
5. **另案處理**：來源尚未定案的缺口列在這裡，附現狀處置。
6. **不設角色的解讀節**：使用者故事與 Use Case 的主詞一律用 wiki 角色名。角色預設持有哪些權限，正本在角色權限管理模組，功能票不寫。
7. **Project 不放的內容**：功能的需求描述、權限、驗證規則與驗收條件（歸 Feature 票）、操作方式與測試觀察點（歸 Prototype）、實作契約（歸 Task 票）、資料欄位表（歸 wiki）、職能分工區塊與票號對照（Label 與父子階層已承載）。
8. **擴充融入既有段落**：迭代交付擴充 project 描述時，在原清單上加條目，缺的標準區塊可新增。不在描述尾端另起一個平行的完整區塊。
9. **後續批次只長清單**：後續批次在 Scope 加條目、開新 Feature 票掛新 milestone，project 不長章節。

## 四、Milestone

1. **Milestone 名寫需求主題**：如「工單主流程」「印件製作細節」。不寫日期或批次名（如「2026-08 工單編輯批」「第三批」）。
2. **一個 milestone 收多張 Feature 票**：先後順序即整合順序。
3. **建了就全掛**：是否建 milestone 依該批拍板；建了就每張 Feature 票都掛。
4. **全域規劃時既有票補掛**：Project 全域規劃 milestone 時，既有票一律補掛，含已完成的票。

## 五、Feature 票

1. **Feature 標題格式**：`[ Feature ] - <需求主題>`。前綴之後只寫需求主題，不帶職能字樣。
2. **概述一句**：一句「這張票做完，誰能做到什麼」，所屬模組以 project 原生提及帶出。需要時另起一句狀態流轉引用句（依「內容只在一層寫」），不算違反本條。
3. **權限表在票頭**：概述之後放一張權限表，三欄固定：權限名稱、動作、範圍。權限名稱寫「動詞＋受詞」或「動詞＋模組」（如「檢視需求單模組」「檢視全公司需求單」「填寫需求單成本」）。範圍只用四個詞：全公司、自己負責、被指派、被分享（可註明檢視或編輯層級）。同一個動作在不同範圍是兩個權限，各一列。表不寫角色、不寫狀態條件、不寫反面句。
4. **功能節段落齊備**：每個功能節固定包含節名、使用者故事、實體關係、驗證規則、驗收。有金額、數量、日期推導時加算式段，放在驗證規則之後。缺任一必要段不得發布。
5. **功能節整節收合**：節名留在收合外，其餘段都在收合內。清單頁只看得到節標題。
6. **節名受詞加動詞**：節名寫「受詞＋動詞」，念出來就知道使用者在做什麼（如「印件項目建立」「送印務評估」「成交轉訂單」）。不用內部造詞與縮寫，不用「○○與金額」這類看不出動作的名稱。
7. **使用者故事**：一句「身為（角色），我要（動作），以（業務目的）」。角色寫 wiki 角色名，不寫「使用者」「系統管理者」。業務目的寫這件事對生意的作用。

| 正例 | 反例 |
|------|------|
| 身為業務，我要逐筆登記客戶要印的東西與數量，以讓印務主管有規格可估、客戶有金額可談。 | 本功能提供印件項目的登記機制，供業務使用。（功能說明句） |

8. **實體關係段**：寫這個動作牽涉的單據與項目怎麼對應：一對多、一對一、帶入哪些內容、共用、留痕。不寫欄位清單。
9. **驗證規則段**：寫流程面的受理條件：這個動作要求的狀態條件、必填是否填齊、前置是否完成、拒絕時系統給什麼。狀態條件寫成「需求單在待評估成本才可評估完成」。必填寫成「建立需求單時驗證必填欄位是否填寫，未填齊則無法建立」，不逐欄列哪個欄位必填、不寫值域。

| 正例 | 反例 |
|------|------|
| 任一印件項目難易度未填時不可送評估，系統列出缺漏的印件項目。 | 難易度必填，1 到 10 的整數。（單欄必填與值域，Prototype 已呈現） |

10. **算式段**：金額、數量、日期的推導用程式碼區塊，一行一式。取整方式寫在式子裡。算式正本在 wiki 時仍抄一行並註明引用，開發才看得到。
11. **驗收段**：編號條列由 1 起，每條「假設＜前提＞，當＜動作＞，則＜可觀測結果＞」。前提用 Prototype 既有資料的具名案例：實際單號、品名、數量、單價、人名。不用「某筆」「一張」這類泛稱，除非該情境 Prototype 沒有現成資料。
12. **驗收有對應規則**：每條驗收檢查的行為，同一節的實體關係、驗證規則或算式有對應條目。只寫在驗收、規則段沒寫的行為，要補進規則段。驗收只驗本功能的規則；沿用規則的行為不寫進驗收，由它的正本票驗收。
13. **段內各自編號**：實體關係、驗證規則、算式、驗收四段的編號各自從 1 起。
14. **Feature 票不寫實作**：本票不是開發工作票，不寫實作內容。
15. **Feature 票結構件**：掛 milestone、掛 Label（見 § 二）、作為其 Task 票的 parent。
16. **Feature 另案段**：本票來源未定案的項目，放在所有功能節之後的「另案處理」收合段。這一段不是功能節，不受「功能節段落齊備」約束。

## 六、Task 票

1. **Task 標題格式**：`[ Task ] - <功能語意>`。前綴之後只寫功能語意，不帶「（前端）」「（後端）」「FE」「BE」。
2. **Task 段落齊備**：背景、規則、驗收、範圍都要有。
3. **背景寫使用者故事**：一句，講這個職能要交付什麼。不寫錨點句與 meta 句。
4. **規則是實作契約**：只寫這個職能要保證的行為：介面回傳、檢核、衍生資料、錯誤處置、邊界值處理。每條規則括註它對應的 Feature 票功能節名（如「依『印件項目建立』」），不重述判準與門檻數字。沒有括註的規則，只允許「通用實作契約」所列；其他沒有括註的規則視為過度設計。
5. **不寫手段詞**：交易、回滾、鎖、快取、樂觀更新、查詢時聚合、旗標、序列產生器、多對多、可空關聯等技術手段一律不寫。手段由開發決定。

| 正例 | 反例 |
|------|------|
| 訂單管理人確認製作細節時，印件狀態推進與工單草稿建立要同時成立，不允許只成立其中一件。 | 印件印製維度推進與空工單建立為同一個交易，任一步失敗一起回滾。 |

6. **通用實作契約**：下列規則不需括註功能節名即可寫：

| 通用實作契約 | 說明 |
|------------|------|
| 值域外不受理 | 送來的值不在 Prototype 呈現的值域內，就拒絕 |
| 拒絕時回覆原因 | 拒絕時回覆使用者讀得懂的原因 |

7. **Task 規則不新增可見行為**：Task 規則不新增使用者看得到的按鈕、欄位、狀態或提示文字內容。這些只能來自 Feature 票與 Prototype。
8. **Task 票不寫算式**：以功能節名括註引用 Feature 票的算式，不重抄。
9. **驗收寫在哪個頁面看到**：驗收條數見 § 十一。編號條列由 1 起，每條標在 Prototype 的哪個頁面或側板看到結果。
10. **期望值取自具名案例**：驗收的前提情境取自 parent 驗收的具名案例；期望結果可以再加上本票規則段的行為。期望值必須是頁面上看得到的值，不與實作同式重算，不用引擎中間值。
11. **範圍段內容**：只取用、不自行實作的依賴；判定為不做的項目，附原因。
12. **不寫 Blocked by 段**：阻擋關係以 Linear 原生 blocking 建在 Task 層。
13. **Task 票平鋪**：背景與驗收永遠平鋪；單一段落超過 § 十一的收合門檻時才收合該段。
14. **Task 票結構件**：掛 Label（見 § 二），parent 掛對 Feature 票。
15. **Task 票不空洞**：不可只剩「見父票」一句而沒有規則與驗收。

## 七、共用寫法

1. **受控句法**：依 `~/.claude/output-styles/ste100-pm.md` 撰寫：白話完整句、一句一事、業務主管唸得順。
2. **禁中英夾雜**：英文識別碼用「中文（英文）」格式。
3. **現在式**：只寫系統現在是什麼。不寫設計對比語言（合一、統一、取代、不再、原本）。
4. **精練不複寫**：wiki 到 Linear 是精練：每過一站只准變準、不准變厚。票文不標 wiki 卡名。
5. **主詞用角色名**：使用者故事、Use Case、驗收的主詞寫業務主管、生管、印務，不寫「具全公司檢視權限者」。權限表例外，權限表不出現角色。
6. **不放流程表**：角色接力與時序由 project 的 Use Case 一句話版與 Prototype 承載，功能節不放步驟表。
7. **結構化寫法**：

| 內容性質 | 用什麼 |
|---|---|
| 權限 | 票頭三欄表 |
| 哪種情況走哪條路、帶入對應 | 表格或編號條列 |
| 金額、數量、日期的推導 | 程式碼區塊，一行一式 |
| 條件與限制 | 編號條列，一條一件事 |

不寫：一句塞多條規則、括號裡再套括號、分號串接三件以上、算式夾在敘事句中間。

8. **段內各自編號**：每個小標題底下的編號清單從 1 開始，不跨段續編。編號無法正確呈現時，整張票改用項目符號。
9. **長段收合**：超過 § 十一收合門檻的狀態機圖、逐條規則清單收進收合區塊。Feature 功能節依 § 五「功能節整節收合」。
10. **收合先試寫**：批次套用收合前，先寫一張票，確認 Linear 與 GitHub 同步票兩面都渲染正常，再套用其餘票。渲染不如預期時改回平鋪。
11. **Label 分類**：

| 分類 | 值域 | 用途 |
|----|------|------|
| Role | Backend、Frontend、Design、PM | 承載職能 |
| Product | ERP、EC、編輯器 | 承載產品線 |
| Type | Feature、Task、Bug | 承載層級 |

Label 取工作區既有分組，不自創新值。Type 必掛且與標題前綴一致。缺 Label 等於缺資訊。

12. **Linear 已呈現的不寫**：

| 不寫 | 原因 |
|---|---|
| 巢狀關係、Blocked by | 介面已呈現 |
| 日期註記（如「（2026-08-26 補齊）」） | 妨礙閱讀；拍板紀錄在 wiki |
| 父票已寫的規則 | 同一條規則只在一處維護 |
| 票內已寫的內容再寫進留言 | 同上 |

## 八、狀態機

1. **狀態機逐一附圖**：狀態密集模組的每個狀態機附一張 Mermaid `stateDiagram-v2` 圖，含狀態節點、轉換箭頭、觸發或條件標籤。關鍵終態與不可逆轉換用 `note` 標。
2. **狀態機忠實轉繪**：狀態列舉與轉換取材 wiki 狀態機卡，不畫來源未定義的轉換。
3. **雙維度分開畫**：雙維度狀態（如審稿與印製、開票與收款）各畫一張，不擠成一張。
4. **視圖層沿用**：視圖層 project 沿用核心 project 的圖，不另繪；已在其他 project 繪製的狀態機用原生提及引用。
5. **狀態圖寫法**：中文狀態代號不加標點。轉換標籤不用半形括號，改用「·」或全形。
6. **渲染眼見確認**：寫入後請 Miles 開頁面確認渲染成圖。顯示為程式碼時改其他形式。

## 九、修正與留言

1. **票主體是正本**：內容與現行定案不符就直接改票主體，不因票已完成而保留錯的內容。
2. **修正性質決定承載**：

| 修正性質 | 承載方式 |
|---|---|
| 行為與定案不符（缺陷） | 改票主體並寫留言；票已完成時狀態改回 Todo |
| 既有功能加新行為（優化） | 開 Task sub-issue，parent 掛該功能的原票 |
| 牽出一個新功能顆粒 | 開新 Feature 票 |

3. **開票前先問**：開 sub-issue 或新 Feature 票前先問 Miles。
4. **缺陷留言分訂正與實測**：

| 留言 | 標題 | 內容 |
|---|---|---|
| 訂正紀錄 | 票主體訂正的內容 | 原本怎麼寫、現行定案是什麼，用對照表；新補的內容也列進表 |
| 實測修正 | `<YYYY-MM-DD> 實測後要請開發修正的內容` | 現況問題（系統現行行為對期望行為的表格）、修正規則（編號條列）、確認不是問題的項目 |

5. **主體附留言連結**：改寫的段落後加「（[參考留言](<票網址>#comment-<留言 id 前 8 碼>)）」，指向訂正紀錄。
6. **實測留言 tag 負責人**：實測修正留言的標題下一行寫 `@<負責人 displayName>`，displayName 以 `get_user` 查。
7. **留言不寫手段**：不列程式碼檔案位置、函式名或改法。
8. **留言不寫依據與 meta 句**：不寫依據卡名、日期、拍板人，不寫「票已從 Done 轉回 Todo」「詳見下一則留言」。
9. **同次訂正只留一則**：範圍擴充併入既有訂正紀錄。
10. **刪留言前先遷移**：舊留言仍被主體連結引用時，先把有效內容併入新留言、把連結改指新留言，再刪舊留言。
11. **不做的也寫**：判定不做時，寫進範圍段或留言並附原因。
12. **改回 Todo 要說明**：已完成的票改回 Todo 會清空完成時間並移入當前 cycle，交付回報時說明。

**評分範圍**：評分只看交付文件是否符合本檔、規則能否對應到整理來源、缺料處是否已標另案。不重新審查上游設計。
