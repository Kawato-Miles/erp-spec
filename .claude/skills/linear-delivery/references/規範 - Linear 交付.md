# 規範 - Linear 交付

交付到 Linear 的寫法規則與審查標準，只寫在本檔。撰寫者照本檔寫，稽核者與盲測主持者照本檔審。

- 骨架（段落與占位）：`範本 - Linear 交付.md`。骨架不放規則。
- 合規樣貌：`範例 - Linear 交付.md`。範例是凍結快照的撰寫示範，取材自真實交付，但不與 Linear 同步。
- 流程（何時做什麼、誰審查、何時停）：`SKILL.md`。流程用到的門檻值見本檔 § 十一。
- 規則以粗體短名開頭。其他檔以短名引用本檔規則，不複寫內容。

---

## 一、正本邊界與取材

1. **Linear 自包含**：對開發而言 Linear 是交付正本。交付內容讀得懂、做得出來，不需要打開別的系統。跨單據只以 Linear 識別碼互指。
2. **不外露內部檔**：交付內容不出現 `openspec/...` 路徑、任何 `.md` 內部檔路徑、內部檔名、內部問題編號（OQ 編號）與 PM 內部流程術語（change、delta、archive）。
3. **不引用 Notion**：不以 Notion 頁面或資料庫連結作為交付依據。
4. **不寫欄位表**：資料欄位的正本在 wiki 實體卡，開發直接查閱。交付不產資料欄位段、不複寫欄位表。
5. **介面歸 Prototype**：開發對著 Prototype 實作。欄位有哪些、值域、版面、按鈕、操作動線、單一欄位的必填與格式都以 Prototype 為準，交付不文字重述，不附 Prototype 參照格，不另附「為準／不為準」邊界表，不開設計票，不寫「其餘依 Prototype」這類句子。
6. **不寫指路句**：不寫「欄位正本：wiki ○○卡」「狀態列舉正本為 wiki ○○卡」。wiki 是取材來源，不出現在票文。
7. **不寫 meta 導覽句**：不寫「實作由本票底下的 sub-issue 承載」「本票是○○的商業邏輯與驗收條件正本」「詳細規則請見上層 project 描述」「需求本體見○○」。巢狀關係、Label 與 blocking 關係本身就是資訊。
8. **引用 Linear 資源用原生提及**：引用 project 或 issue 時產生 Linear 原生提及。issue 直接寫識別碼（如 `PM-1084`），寫入後 Linear 自動轉成提及元素。project 寫 `<project id="<UUID>" href="<URL>/overview">名稱</project>` 元素。不用純文字「本 project」，不用 Markdown `[名稱](URL)` 連結。
9. **wiki 卡不外連**：票內提到 wiki 卡時用純文字，不外連 GitHub。
10. **權限項目歸後端**：票只寫動作、可執行角色、資料範圍。權限項目怎麼切、叫什麼名字、權限代碼、後端怎麼判定，都由後端決定，不寫進票。
11. **Linear 只整理不產生**：Linear 只把上游已定案的內容整理、拆層級。上游沒有的規則、案例、驗收，Linear 不產生。上游指 wiki、Prototype、情境目錄與 mock。
12. **驗收取材情境目錄**：Feature 票的驗收從 Sens `erp-prototype-tests/docs/scenario-catalog.md` 情境目錄與其測試整理。資料流固定為 wiki → Prototype → Linear，情境的源頭是 wiki 業務情境卡，情境目錄依情境卡展開。
13. **不寫來源標記**：Linear 上不寫任何來源標記或外部指引。不標情境編號、不附情境目錄或測試的連結、不寫測試檔名。
14. **上游矛盾先停**：wiki、Prototype、情境目錄、mock 之間互相矛盾時，停下列給 Miles 裁決。先修上游與測試，再寫 Linear。
15. **具名案例照抄情境目錄**：驗收裡的單號、品名、人名、數值，只用情境目錄寫的。情境目錄寫「自建一張需求單」這類起點時，前提照它寫。情境目錄沒有可用的案例時停下，依序補 wiki 業務情境卡、mock、情境目錄，再寫驗收。
16. **驗收對不到規則先停**：驗收對不到同節規則時，先回 wiki 查這條規則。wiki 有、票上漏寫，屬整理漏項，照 wiki 補進規則段。wiki 沒有，就停下列給 Miles 裁決。不在 Linear 自創規則，也不為了通過審查刪驗收。

## 二、分層與顆粒度

| 層 | 回答的問題 | 顆粒度 | Label |
|----|-----------|--------|-------|
| Project | 這個模組為什麼存在、誰用它做什麼、要做哪幾塊 | 一個平台的一個模組 | — |
| Milestone | 這批要一起交付什麼 | 一組要一起交付的 Feature 票 | — |
| Feature 票 | 這一塊做完，使用者能完成什麼事 | 一票一個需求主題；票內一個功能節裝一個動作 | Type/Feature、Product、Role/PM |
| Task 票 | 後端要支援哪些功能、前端要做哪些頁面 | 一職能一張 | Type/Task、Product、Role/Backend 或 Frontend |
| Sub-Task 票、Bug 票 | Task 再往下切 | 開發自行判斷 | 依需要 |

1. **由大到小順讀**：project 讀方向、milestone 讀這批要交付什麼、Feature 票讀需求本體、Task 票讀自己要支援的功能或要做的頁面清單。讀者不需回頭跳層。
2. **功能節是顆粒度載體**：一節寫使用者的一個動作。一節出現兩個互不相干的動作，或驗收條數超過 § 十一的上限，就拆節。需求主題之間互不相干才拆票，拆出的票掛同一個 milestone。
3. **內容只在一層寫**：

| 內容 | 正本層 | 其他層怎麼寫 |
|---|---|---|
| 狀態列舉、狀態流轉、轉換條件 | project 的狀態機圖 | 一句「狀態流轉見 ○○ 的○○狀態機」加原生提及 |
| 權限、實體關係、驗證規則、算式、驗收條件 | Feature 票 | Task 票不寫 |
| 後端要支援的功能清單、前端的頁面與控制元件清單 | Task 票 | project 與 Feature 票不寫 |
| 模組層 What、Use Case、Scope | project 描述 | 票內不重述 |
| 欄位、值域、版面、操作動線 | Prototype | 各層都不寫 |

4. **不複寫狀態機**：Feature 票與 Task 票不把狀態流轉改寫成表格或條列。功能節的驗證規則只寫該動作要求的狀態條件。
5. **沿用規則不寫**：規則的家在別的功能時，本 project 的 Feature 票與 Task 票都不寫，也不寫「套用某處規則」的引用句。沿用關係只在 project 的 Out of Scope 寫一次。判準見下表，任一成立即為沿用規則。

| 判準 | 例子 |
|------|------|
| 規則的 wiki 正本卡領域不等於本 project 領域 | 訂單可見範圍的規則家在訂單管理，出現在款項管理 project |
| 同平台既有 Feature 票已有該規則的功能節 | 開票前用 `list_issues` 掃同平台 Feature 票的功能節名 |

6. **規則重複代表拆錯**：同一條規則出現在兩張以上 Feature 票，代表拆法錯，或規則的家在別的功能。先修拆法。搬進 project、或改寫成引用句都不算修好。
7. **Task 票單一歸屬**：一張 Task 票只服務一張 parent Feature 票。出現多個主要歸屬，代表 Feature 票切太細，回頭以功能顆粒重切。
8. **改規則同掃各層**：改一條規則時，同時檢查 project 描述、milestone 描述與 Feature 票。改動只落在一處，其餘各處的舊說法會變成矛盾。Task 票不寫規則，不在檢查範圍內。

## 三、Project 描述

必要區塊：概述、使用情境（Use Case、Scope）、另案處理、狀態機（狀態密集模組）。

1. **概述**：寫商業目標與現行問題痛點，取材 wiki 痛點卡與商業邏輯卡的「現況」段。不寫功能清單。
2. **Use Case**：業務敘事白話句，寫「角色 × 業務動作」。可跨 project 講完整業務故事。取材 wiki 業務情境。
3. **Scope 一條一票**：一條 Scope 對應一張 Feature 票。每條寫票名、一句「做完後使用者能做到什麼」與原生提及。

| 正例 | 反例 |
|------|------|
| **需求單建立**：業務把客戶要印的東西登記成一張需求單並送出成本評估。 | **需求單建立**：處理需求單建立的相關邏輯與流程。（看不出誰用、做到什麼） |

4. **Out of Scope 附歸屬**：每條不做項寫明歸屬：延後批次、其他 project 或其他平台。
5. **另案處理**：來源尚未定案的缺口列在這裡，附現狀處置。
6. **不設角色的解讀節**：使用者故事與 Use Case 的主詞一律用 wiki 角色名。角色能做哪些動作，寫在各 Feature 票的權限表，project 不另設角色節。
7. **範圍用詞段**：Feature 權限表用到的資料範圍用詞，都要在 project 描述的「範圍用詞」段定義。定義照抄 wiki 受控清單卡的範圍用詞，一個用詞一列。開發只讀 Feature 票時，回 project 就查得到用詞的意思。
8. **Project 不放的內容**：功能的需求描述、權限、驗證規則與驗收條件（歸 Feature 票）、操作方式與測試觀察點（歸 Prototype）、功能與頁面清單（歸 Task 票）、資料欄位表（歸 wiki）、職能分工區塊與票號對照（Label 與父子階層已承載）。
8. **擴充融入既有段落**：迭代交付擴充 project 描述時，在原清單上加條目，缺的標準區塊可新增。不在描述尾端另起一個平行的完整區塊。
9. **後續批次只長清單**：後續批次在 Scope 加條目、開新 Feature 票掛新 milestone，project 不長章節。

## 四、Milestone

1. **Milestone 名寫需求主題**：如「工單主流程」「印件製作細節」。不寫日期或批次名（如「2026-08 工單編輯批」「第三批」）。
2. **一個 milestone 收多張 Feature 票**：先後順序即整合順序。
3. **建了就全掛**：是否建 milestone 依該批拍板；建了就每張 Feature 票都掛。
4. **全域規劃時既有票補掛**：Project 全域規劃 milestone 時，既有票一律補掛，含已完成的票。

## 五、Feature 票

1. **Feature 標題格式**：`[ Feature ] - <需求主題>`。前綴之後只寫需求主題，不帶職能字樣。
2. **概述一句**：一句「這張票做完，誰能做到什麼」，所屬模組以 project 原生提及帶出。需要時另起一句狀態流轉引用句（依「內容只在一層寫」），不算違反本條。
3. **權限表在票頭**：概述之後放一張權限表，三欄固定：動作、可執行角色、資料範圍。
   - 一列一個動作，不合併。同一個動作的角色或範圍不同時，分成多列。
   - 權限表列出本票所有動作。只有附帶規則的動作才開功能節；沒有附帶規則的動作只列在權限表。
   - 動作寫「動詞＋受詞」，如「送印務評估」「修改印件項目」，取自 wiki 實體卡操作段的操作名稱。有功能節的動作，用該節的動作詞。
   - 每一列取自 wiki 活動清單卡的一列活動：可執行角色照抄執行角色欄，資料範圍照抄範圍欄。活動清單卡沒有列出的角色與範圍組合不寫（未列即不可做）。
   - 可執行角色寫 wiki 角色名。同一範圍的多個角色可同列，以頓號分隔。被分享範圍不限角色，可執行角色寫「所有角色」。
   - 資料範圍只用受控清單的範圍用詞，照抄：全公司、自己負責、被分享（檢視）、被分享（編輯）、所屬產線。一格只寫一個用詞。
   - 建立類動作沒有既有單據可限縮，資料範圍寫「—」。
   - 範圍只回答看得到或做得到哪些單。動作要求的狀態條件寫在該功能節的驗證規則段。
   - 表不寫權限名稱、權限代碼、反面句。

| 正例 | 反例 |
|------|------|
| 送印務評估｜業務、諮詢｜自己負責 | 編輯需求單模組｜建立需求單、修改單頭、送印務評估｜自己負責，或被分享編輯（權限名稱、一列多動作、一格兩範圍） |
| 送印務評估｜所有角色｜被分享（編輯） | 送印務評估｜具編輯權限者｜被指派（角色不是 wiki 角色名，範圍不是受控清單用詞） |

4. **功能節段落齊備**：每個功能節固定包含節名、使用者故事、實體關係、驗證規則、驗收。有金額、數量、日期推導時加算式段，放在驗證規則之後。缺任一必要段不得發布。
5. **功能節整節收合**：節名留在收合外，其餘段都在收合內。清單頁只看得到節標題。
6. **節名受詞加動詞**：節名寫「受詞＋動詞」，念出來就知道使用者在做什麼（如「印件項目建立」「送印務評估」「成交轉訂單」）。不用內部造詞與縮寫，不用「○○與金額」這類看不出動作的名稱。
7. **使用者故事**：一句「身為（角色），我要（動作），以（業務目的）」。角色寫 wiki 角色名，不寫「使用者」「系統管理者」。業務目的寫這件事對生意的作用。

| 正例 | 反例 |
|------|------|
| 身為業務，我要逐筆登記客戶要印的東西與數量，以讓印務主管有規格可估、客戶有金額可談。 | 本功能提供印件項目的登記機制，供業務使用。（功能說明句） |

8. **實體關係段**：寫這個動作牽涉的單據與項目怎麼對應：一對多、一對一、帶入哪些內容、共用、留痕。不寫欄位清單。
9. **驗證規則段**：寫流程面的受理條件：這個動作要求的狀態條件、必填是否填齊、前置是否完成、拒絕時系統給什麼。狀態條件寫成「需求單在待評估成本才可評估完成」。必填寫成「建立需求單時驗證必填欄位是否填寫，未填齊則無法建立」，不逐欄列哪個欄位必填、不寫值域。

| 正例 | 反例 |
|------|------|
| 任一印件項目難易度未填時不可送評估，系統列出缺漏的印件項目。 | 難易度必填，1 到 10 的整數。（單欄必填與值域，Prototype 已呈現） |

10. **算式段**：金額、數量、日期的推導用程式碼區塊，一行一式。取整方式寫在式子裡。算式正本在 wiki 時仍照抄進票，開發才看得到；票上不標 wiki 卡名。
11. **驗收段**：編號條列由 1 起，每條「假設＜前提＞，當＜動作＞，則＜可觀測結果＞」。前提與結果依「驗收取材情境目錄」與「具名案例照抄情境目錄」：實際單號、品名、數量、單價、人名都照情境目錄。不用「某筆」「其任務」這類泛稱。
12. **驗收有對應規則**：每條驗收檢查的行為，同一節的實體關係、驗證規則或算式有對應條目。對不到時依「驗收對不到規則先停」處理。驗收只驗本功能的規則；沿用規則的行為不寫進驗收，由它的正本票驗收。
13. **段內各自編號**：實體關係、驗證規則、算式、驗收各段的編號各自從 1 起。
14. **Feature 票不寫實作**：本票不是開發工作票，不寫實作內容。
15. **Feature 票結構件**：掛 milestone、掛 Label（見 § 二）、作為其 Task 票的 parent。
16. **Feature 另案段**：本票來源未定案的項目，放在所有功能節之後的「另案處理」收合段。這一段不是功能節，不受「功能節段落齊備」約束。

## 六、Task 票

Task 票只回答一件事：後端要支援哪些功能，前端要做哪些頁面。規則、權限、算式、驗收都在 parent Feature 票，Task 票不寫。這樣改規則時只動 Feature 票，Task 票只在功能或頁面增減時才改。

1. **Task 標題格式**：後端寫 `[ Task ] - <需求主題>的資料操作`，前端寫 `[ Task ] - <需求主題>的頁面`。需求主題與 parent Feature 票相同。不帶「（前端）」「（後端）」「FE」「BE」。
2. **Task 段落齊備**：每張票都有「要做什麼」與主體清單。後端的主體清單是「要支援的功能」，前端是「頁面與控制元件」。有依賴時再加「不用自己做」。
3. **要做什麼**：一句工作說明，寫這張票交付後誰能在哪裡完成什麼。不寫錨點句與 meta 句。
4. **要支援的功能**：編號條列，一條一個畫面功能。
   - 功能名稱取自 Prototype 畫面上的功能，如「出貨單列表資料呈現與篩選」「批次拋單」。Prototype 沒有的功能不列。
   - 讀取類功能也各列一條，如列表、檢視、下載。
   - 一條只寫功能名稱。不加說明，不寫對應哪個功能節。商業邏輯都在 Feature 票。
   - 一個功能要開幾支 API、怎麼拆，由後端決定。
   - 不列欄位。欄位以 Prototype 為準。
   - 畫面看不到的系統自動動作不列，由 Feature 票承載。如通知發送、物流商回傳、取消連鎖。

| 正例 | 反例 |
|------|------|
| 1. 需求單列表資料呈現與篩選 | 1. GET /quotes?status=（路徑由後端設計） |
| 2. 評估完成 | 2. 評估完成：任一印件項目成本估算為空時拒絕，並列出缺漏項目（規則屬 Feature 票） |
| 3. 報價紀錄頁籤資料呈現 | 3. 報價紀錄讀取、報價紀錄輪次讀取、報價紀錄明細讀取（逐支 API，拆法屬後端） |
| 不列重新評估後的 Slack 通知 | 8. 重新評估報價的 Slack 通知（畫面看不到的系統自動動作，由 Feature 票承載） |

5. **頁面與控制元件**：巢狀條列。第一層是頁面，如需求單列表頁、需求單詳情頁。第二層是控制元件，依類型分行：動作按鈕、對話框、側板、頁籤。名稱用 Prototype 上的名稱。只寫名稱。

| 正例 | 反例 |
|------|------|
| 動作按鈕：評估完成、進入議價、重新評估、成交 | 動作按鈕：進入議價只在已評估成本出現（出現條件屬 Feature 票） |
| 對話框：完成成本評估 | 對話框：完成成本評估（新建），串接評估完成 API（新建標記與串接對應會隨迭代脫鉤） |

6. **清單不寫的內容**：功能清單與頁面清單都不寫下列內容。
   - 規則、條件、出現時機、拒絕時的處置
   - 規則出處，如「依『成本評估完成』」
   - 新增或調整、新建或加功能這類標記
   - 路徑、方法、資料格式、欄位、版面
   - 前端清單不寫要串哪支 API
7. **清單名稱有來源**：功能名稱、頁面與控制元件名稱都來自 Prototype。不列 Prototype 沒有的項目。列出名稱是工作清單，不算重述 Prototype。Prototype 與情境目錄的名稱不一致時，依「上游矛盾先停」處理。
8. **不用自己做**：寫這張票會用到、但由別張票或別的模組提供的東西，並寫明由誰提供。別張 issue 用識別碼，別的 project 用原生提及。未定案的項目不寫在這裡，歸 Feature 票的「另案處理」。
9. **Task 票不寫驗收**：驗收的正本是 parent Feature 票的驗收段，前後端都依它自測。
10. **不寫 Blocked by 段**：阻擋關係以 Linear 原生 blocking 建在 Task 層。
11. **Task 票結構件**：掛 Label（見 § 二），parent 掛對 Feature 票。
12. **Task 票不空洞**：主體清單至少一項。不可只剩「見父票」一句。

## 七、共用寫法

1. **受控句法**：依 `~/.claude/output-styles/ste100-pm.md` 撰寫：白話完整句、一句一事、業務主管唸得順。
2. **禁中英夾雜**：英文識別碼用「中文（英文）」格式。
3. **現在式**：只寫系統現在是什麼。不寫設計對比語言（合一、統一、取代、不再、原本）。
4. **精練不複寫**：wiki 到 Linear 是精練：每過一站只准變準、不准變厚。票文不標 wiki 卡名。
5. **主詞用角色名**：使用者故事、Use Case、驗收的主詞與權限表的可執行角色，都寫 wiki 角色名，如業務主管、生管、印務。不寫「具全公司檢視權限者」。
6. **不放流程表**：角色接力與時序由 project 的 Use Case 一句話版與 Prototype 承載，功能節不放步驟表。
7. **結構化寫法**：

| 內容性質 | 用什麼 |
|---|---|
| 權限 | 票頭三欄表 |
| 哪種情況走哪條路、帶入對應 | 表格或編號條列 |
| 金額、數量、日期的推導 | 程式碼區塊，一行一式 |
| 條件與限制 | 編號條列，一條一件事 |

不寫：一句塞多條規則、括號裡再套括號、分號串接三件以上、算式夾在敘事句中間。

8. **段內各自編號**：每個小標題底下的編號清單從 1 開始，不跨段續編。編號無法正確呈現時，整張票改用項目符號。
9. **長段收合**：超過 § 十一收合門檻的狀態機圖、逐條規則清單收進收合區塊。Feature 功能節依 § 五「功能節整節收合」。
10. **收合先試寫**：批次套用收合前，先寫一張票，確認 Linear 與 GitHub 同步票兩面都渲染正常，再套用其餘票。渲染不如預期時改回平鋪。
11. **Label 分類**：

| 分類 | 值域 | 用途 |
|----|------|------|
| Role | Backend、Frontend、Design、PM | 承載職能 |
| Product | ERP、EC、編輯器 | 承載產品線 |
| Type | Feature、Task、Bug | 承載層級 |

Label 取工作區既有分組，不自創新值。Type 必掛且與標題前綴一致。缺 Label 等於缺資訊。

12. **Linear 已呈現的不寫**：

| 不寫 | 原因 |
|---|---|
| 巢狀關係、Blocked by | 介面已呈現 |
| 日期註記（如「（2026-08-26 補齊）」） | 妨礙閱讀；拍板紀錄在 wiki |
| 父票已寫的規則 | 同一條規則只在一處維護 |
| 票內已寫的內容再寫進留言 | 同上 |

## 八、狀態機

1. **狀態機逐一附圖**：狀態密集模組的每個狀態機附一張 Mermaid `stateDiagram-v2` 圖，含狀態節點、轉換箭頭、觸發或條件標籤。關鍵終態與不可逆轉換用 `note` 標。
2. **狀態機忠實轉繪**：狀態列舉與轉換取材 wiki 狀態機卡，不畫來源未定義的轉換。
3. **雙維度分開畫**：雙維度狀態（如審稿與印製、開票與收款）各畫一張，不擠成一張。
4. **視圖層沿用**：視圖層 project 沿用核心 project 的圖，不另繪；已在其他 project 繪製的狀態機用原生提及引用。
5. **狀態圖寫法**：中文狀態代號不加標點。轉換標籤不用半形括號，改用「·」或全形。
6. **渲染眼見確認**：寫入後請 Miles 開頁面確認渲染成圖。顯示為程式碼時改其他形式。

## 九、修正與留言

1. **票主體是正本**：內容與現行定案不符就直接改票主體，不因票已完成而保留錯的內容。
2. **修正性質決定承載**：

| 修正性質 | 承載方式 |
|---|---|
| 行為與定案不符（缺陷） | 改票主體並寫留言；票已完成時狀態改回 Todo |
| 既有功能加新行為（優化） | 開 Task sub-issue，parent 掛該功能的原票 |
| 牽出一個新功能顆粒 | 開新 Feature 票 |

3. **開票前先問**：開 sub-issue 或新 Feature 票前先問 Miles。
4. **缺陷留言分訂正與實測**：

| 留言 | 標題 | 內容 |
|---|---|---|
| 訂正紀錄 | 票主體訂正的內容 | 原本怎麼寫、現行定案是什麼，用對照表；新補的內容也列進表 |
| 實測修正 | `<YYYY-MM-DD> 實測後要請開發修正的內容` | 現況問題（系統現行行為對期望行為的表格）、修正規則（編號條列）、確認不是問題的項目 |

5. **主體附留言連結**：改寫的段落後加「（[參考留言](<票網址>#comment-<留言 id 前 8 碼>)）」，指向訂正紀錄。
6. **實測留言 tag 負責人**：實測修正留言的標題下一行寫 `@<負責人 displayName>`，displayName 以 `get_user` 查。
7. **留言不寫手段**：不列程式碼檔案位置、函式名或改法。
8. **留言不寫依據與 meta 句**：不寫依據卡名、日期、拍板人，不寫「票已從 Done 轉回 Todo」「詳見下一則留言」。
9. **同次訂正只留一則**：範圍擴充併入既有訂正紀錄。
10. **刪留言前先遷移**：舊留言仍被主體連結引用時，先把有效內容併入新留言、把連結改指新留言，再刪舊留言。
11. **不做的也寫**：判定不做時，寫進 Feature 票的另案處理或留言，並附原因。
12. **改回 Todo 要說明**：已完成的票改回 Todo 會清空完成時間並移入當前 cycle，交付回報時說明。
13. **進行中票可覆寫的情況**：In Progress 的票只在下列情況可覆寫，其他增減依本節第 2 條承載，開票前先問 Miles。
   - 換清單寫法。
   - 新增功能經 Miles 同意併入，並在對照留言寫明新增哪一條。

## 十、審查

審查找出會影響開發的問題，依嚴重度分類。不逐維度給分。

1. **問題依嚴重度分類**：每個問題歸入下表其中一類。

| 嚴重度 | 定義 | 例子 |
|------|------|------|
| 會讓開發做錯 | 開發照票做，做出來與定案不符，或漏做 | 具名案例把吳國豪當 Q-20260906-01 的評估主管，mock 是林雅婷（與上游不符）；寫入「成交或流失不可變更分享成員」，wiki 與 Prototype 都沒有（捏造）；分享規則整段寫進需求單票，跨票共用的權限只放在一張不相關的票（規則放錯層，開發在別處漏做）；「上限為 0 不列待轉交」只寫在驗收（驗收對不到規則）；票寫「負責業務」而 wiki 是「接單業務」、範圍欄寫「被指派」（用詞或角色與 wiki 不一致）；狀態機漏畫短出結案（與上游不符） |
| 會讓開發要回頭問 | 開發照票做不下去，要回頭問 PM | 功能節缺驗收、缺 Feature 另案段、票未掛 milestone 或缺 Label（缺必要段落或結構件）；後端清單漏了列表、檢視、下載這類讀取功能（功能清單漏項）；Out of Scope 寫「活動紀錄與分享票」沒寫識別碼、驗收用「其任務」泛稱（指向不明） |
| 格式 | 不影響做對，影響讀得順 | 一條寫兩件事、句子過長、寫死「五個單元」（句法）；規則段超過收合門檻未收合（收合）；用 Markdown 連結引 issue（提及格式）；段內編號跨段續編（編號） |

2. **格式問題自修**：格式類問題由撰寫者自行修正，修完不必重新審查。格式類的規則見 § 七，撰寫者送審前依 SKILL.md 的自掃清單掃過。
3. **出處核對**：稽核者逐條核對每條規則、每條驗收，確認對得到 wiki 或情境目錄的原文。對不到者記為「會讓開發做錯」。稽核者同時檢查必要段落、結構件與 Task 清單，缺漏記為「會讓開發要回頭問」。
4. **第二段盲測（wiki → Linear）**：受測者只讀 Linear 草稿，回答第一段盲測（商業需求 → wiki）的判定題。答案要與第一段的標準答案一致。答錯的題目，回頭找出票上造成誤解的位置，記為「會讓開發做錯」。
5. **判定題來源**：判定題與標準答案取自該模組第一段盲測。該模組沒有第一段盲測時，主對話依 wiki 已拍板的內容出題，題目開測前先給 Miles 看。
6. **第三段盲測（Linear → 開發設計）**：受測者扮演後端或前端，只讀 Linear 與開發看得到的 wiki、Prototype。後端從 Feature 票與 Prototype 推出要支援的功能清單，與票上清單比對。前端列出要做的頁面與控制元件。兩者都列出會回頭問 PM 的問題。
7. **第三段通過條件**：涵蓋權限表的每列動作、受測者之間的設計沒有矛盾，由 Miles 判定。受測者會回頭問的問題，記為「會讓開發要回頭問」。
8. **受測者獨立**：每位受測者獨立作答，互不知道彼此與標準答案。受測者人數與模型見 § 十一。
9. **審查範圍**：審查只看交付文件是否符合本檔、規則能否對應到整理來源、缺料處是否已標另案。不重新審查上游設計。
10. **真實性**：交付內容的規則、狀態、數值都來自已定案的 wiki、情境目錄與 Prototype 現況。來源未定義時停下，觸發 `oq-manage` mode B，交付文件標「另案處理」。不用「應該、大概、通常」的推測當定案，不為了看起來完整補上沒有依據的轉換、公式或驗收情境。標另案不算問題。

**審查輸出格式**：

```
[交付審查 · 第 N 輪]
| 嚴重度 | 位置 | 問題 | 違反的規則短名 | 修正方向 |
|--------|------|------|---------------|---------|
| 會讓開發做錯 | <票名 · 段 · 條號> | <...> | <短名> | <...> |
| 會讓開發要回頭問 | ... | ... | ... | ... |
| 格式 | ... | ... | ... | ... |
筆數：會讓開發做錯 N、會讓開發要回頭問 N、格式 N
合格判定：是 / 否
```

## 十二、反例

| 反例 | 違反的規則 |
|------|-----------|
| 標題「工單建立主流程（前端）」，一張票裝六個功能 | Task 標題格式、功能節是顆粒度載體 |
| 概述寫「本票是『工單建立主流程』的商業邏輯與驗收條件正本」「實作由本票底下的 sub-issue 承載」 | 不寫 meta 導覽句 |
| 節名「印件項目與金額」 | 節名受詞加動詞 |
| 「本功能提供印件製作細節的確認機制，僅適用線下單」 | 使用者故事 |
| 權限表寫權限名稱「編輯需求單模組」、一列裝多個動作、一格寫「自己負責，或被分享編輯」 | 權限表在票頭、權限項目歸後端 |
| 權限表可執行角色寫「具編輯權限者」，資料範圍寫「被指派」「相關需求單」 | 權限表在票頭、主詞用角色名 |
| 權限表資料範圍寫「需求單在待評估成本時」 | 權限表在票頭（狀態條件歸驗證規則段） |
| 驗證規則寫「客戶必填」「印件屬性只有打樣、大貨」「其餘單頭欄位依 Prototype 表單」 | 驗證規則段、介面歸 Prototype |
| 驗收寫「假設業務在某筆印件項目上傳一個檔案」 | 驗收段 |
| 驗收用情境目錄沒有的單號與數量，自行編出「福利禮盒外包裝數量 801」 | 具名案例照抄情境目錄、Linear 只整理不產生 |
| 驗收句尾標「（情境 1.3）」，或附情境目錄連結 | 不寫來源標記 |
| 驗收對不到規則，撰寫者在規則段新寫一條 wiki 沒有的「印務主管被移出名單後列表看不到該單」 | 驗收對不到規則先停 |
| wiki 寫評估印務主管可刪除需求單，Prototype 不給刪除鈕，撰寫者挑一邊寫進票 | 上游矛盾先停 |
| 功能節放「步驟、角色、行為、系統結果」四欄步驟表 | 不放流程表 |
| 資料欄位段寫「規格正本：openspec/specs/order-management/spec.md § Data Model」 | 不外露內部檔、不寫欄位表 |
| Task 票寫十三條「依狀態受理或拒絕」的行為條文，開發回報看不出要支援哪些功能 | 要支援的功能、清單不寫的內容 |
| 後端票逐支列「出貨單讀取」「裝箱明細讀取」「物流單歷程讀取」，後端看不出這些讀取是為了哪個畫面 | 要支援的功能 |
| FE 票寫「進入議價的動作只在已評估成本出現」 | 頁面與控制元件、清單不寫的內容 |
| 訂單可見範圍規則寫進款項管理的三張清單票與 project 描述 | 沿用規則不寫、規則重複代表拆錯 |
| 來源未定義「部分退款」判定條件，交付者自行假設「收到任一筆退款即部分退款」畫進狀態圖 | 真實性 |
| 售後建單前提改定案後，只改 Feature 票，project 描述三處與 milestone 描述仍寫舊前提 | 改規則同掃各層 |
