# 交付給開發文件 · 評分標準（Rubric）

> 用法：交付前由**評分者**（與實作者分離的 sub-agent，結構性交付才開；不需 senior-pm——交付內容自 BRD / PRD 整理、上游已定案，評分聚焦 rubric 符合性而非重跑上游查證）逐維度評分；未達合格分數 → 修正 → **重新評分**，以 goal 機制迭代直到達標（硬上限 3 輪、卡住問 Miles、不放水）。
> 重點是 Step 4「**具體拒絕案例（絕對不要做的事）**」—— 禁令越精確，評分者越好抓違規；評分 MUST evidence-anchored（引用草稿具體位置，非空泛評語）。
> **評分尺度（2026-07-06 分數化、2026-07-15 加 D5）**：每維度 **通過 = 2 分 / 部分 = 1 分 / 未通過 = 0 分**，滿分 10 分。**合格分數 = 10 分，且 D4 必須 2 分（一票否決）**；未達 10 分不發布。
> 案例皆取自 2026-06-01 訂單管理交付的真實事件（D5 自 2026-07-15 工作流 v2.0 改版新增）。

---

## 評分輸出格式

```
[交付評分 · 第 N 輪]　總分：N / 10
D1 正本邊界：2 / 1 / 0　← 違反禁令：<引用草稿具體位置> / 修正方向：<...>
D2 分層與顆粒度：...
D3 完整性：...
D4 真實性（不捏造）：2 / 0（一票否決，無 1 分）
D5 交付結構完整性：...
達標判定：是（10 / 10）/ 否
總結：可發布（達標）/ 需迭代（列必修項 → 交回實作者修正後 MUST 重新評分，不得自審放行）
```

## D1 · 正本邊界

**定義**：Linear 為對開發的唯一正本，交付內容自包含、跨單據只以 Linear 識別碼互指（Notion 已停用為 BRD，不引用）。OpenSpec spec 是 PM 內部工作版本，不外露；資料欄位表不寫入交付內容（欄位正本在 wiki 實體卡，開發端直接取得）。

**絕對不要**：
- 絕對不要在交付內容寫 `openspec/specs/...` 或任何 `.md` 內部檔路徑
- 絕對不要把「規格正本」指向開發打不開的內部檔
- 絕對不要引用 Notion 頁面 / DB 連結當交付依據（Notion 已停用為 BRD）
- 絕對不要把 PM 內部流程術語（change / delta / archive / OQ 編號）寫進給開發的內容
- 絕對不要寫「欄位正本：wiki ○○卡」「狀態列舉正本為 wiki ○○卡」類**指路句**——交付內容自包含後這種句子只是把讀者導去別處，Miles 拍板 Linear 不放任何指路內容（2026-08-27；wiki 作為取材來源不變，但不出現在票文）
- 絕對不要寫**meta 導覽句**——「實作由本票底下的 sub-issue 承載，職能與動工順序見各 sub-issue」「本票是○○的商業邏輯與驗收條件正本」「詳細規則請見上層 project 描述」類句子；巢狀關係與 Label 本身就是資訊，再用句子講一遍只是噪音（與 wiki 指路句同族，2026-08-27 Miles 拍板）。**唯一例外**：Task 票背景段末得有一句「需求本體見 <Feature 票原生提及>」（2026-08-31 拍板的票層跳轉錨點），此句不算 meta 句；背景段之外再出現同類句子仍屬違規

**正例**：資料欄位段以自包含欄位表呈現（業務語言、只列本批相關欄位）；跨 issue 以 Linear 識別碼（如 FE-259）互指。

**反例（2026-06-01 真實）**：資料欄位段寫「規格正本：openspec/specs/order-management/spec.md § Data Model」、各 Backend issue `## Ref` 列 `openspec/specs/...`。Miles 指出對開發與公司而言 Linear 上的內容才是正本，內部工作版本引用不該出現。

**評分**：無任何內部引用 = 通過；殘留 1-2 處 = 部分；多處或核心指向內部檔 = 未通過。

## D2 · 分層與顆粒度（v4 巢狀版）

**定義**：各層各司其職——Project＝薄目錄（概述、Use Case、功能票清單、跨票遊戲規則），不藏任何規則本體；Feature 票＝該功能需求描述、商業邏輯與驗收條件的唯一正本（固定三段）；Task 票＝**行為契約**（什麼情況下系統要發生什麼／不許出現什麼）＋驗收測試。內容不重複、由大到小可順讀，讀者不需回頭跳層。

**絕對不要**：
- 絕對不要在 project 描述展開商業邏輯章（正本在 Feature 票；project 每功能只留一句用戶故事式範圍句＋原生提及）
- **絕對不要在 Task 票複寫商業規則本體**——商業背景、跨職能規則、project 狀態機、Feature 票規則的判準與門檻數字都不寫；Task 票規則段只寫該職能的實作契約（介面回傳、檢核、衍生資料、錯誤處置、邊界值處理），對應的商業規則以 Feature 票的規則短名括註（2026-08-31 Miles 拍板推翻 v4.5「允許語意重疊」：層間重疊造成兩處版本漂移與維護矛盾）
- **絕對不要在 Task 票寫實作手段詞**——交易、回滾、鎖、快取、樂觀更新、查詢時聚合、旗標、序列產生器、多對多、可空關聯等；行為要求只寫業務可讀的行為契約句，手段由開發決定
- **絕對不要在 Feature 票或 Task 票複寫 project 的狀態機**——狀態流轉（狀態列舉、轉換、條件）的正本是 project 的狀態機圖，票內改寫成表格或條列即算複寫；票只寫該層要實作的衍生行為，流轉本身一句原生提及引用 project
- **絕對不要只改一層就收工**——同一條規則改動時 MUST 同掃 project 描述、milestone 描述、Feature 票、Task 票四處，殘留舊說法即算未修完
- 絕對不要讓 Task 票只剩「見父票」一句而無行為要求與驗收測試
- 絕對不要讓一張 Task 票出現多個「主要歸屬」——多重歸屬＝ Feature 票切太細，回頭以功能顆粒重切
- **絕對不要把 Feature 票的需求描述寫成功能說明句**——需求描述 MUST 為使用者故事「身為（角色），我要（動作），以（業務目的）」；「本功能提供○○機制」「本票處理○○邏輯」類句子即違規
- **絕對不要把有角色接力或時序先後的流程寫成敘述句**——流程 MUST 表格化（欄：步驟｜角色｜行為｜系統結果）；規則（單點 if-then、約束、門檻）才用句子
- **絕對不要把適用範圍句放在需求描述段**——「僅適用線下單」「只在已收訂金時成立」類句子歸商業邏輯的規則段；需求描述只講誰要什麼、為什麼要

**正例**：不寫「印件印製維度推進與空工單建立為同一個交易，任一步失敗一起回滾」，寫「訂單管理人確認製作細節時，印件狀態推進與工單草稿建立要同時成立——不允許出現印件已推進、工單卻沒建出來的狀況，反之亦然」。流程正例與反例對照見 delivery-template § 八。

**反例（2026-08-19 工單管理真實）**：BE 票寫滿「同一個交易」「樂觀併發前提」「查詢時聚合」等偽技術散文 → BE 開發回報「完全看不懂實際上的工作是什麼」；且票內段落標題要求讀者回頭讀 project 的章，形成 project ↔ 票來回跳讀。

**反例（2026-08-27 GitHub 同步票 #2383 真實）**：功能描述寫「本功能提供印件製作細節的確認機制」（非使用者故事）；三個角色的接力寫成一段敘述句（訂單管理人填寫送出 → 系統推進狀態並建草稿 → 生管接手規劃）；「僅適用線下單」夾在描述段。Miles 檢視後指出「開票內容看不出要實作什麼」。

**評分**：分層乾淨、Feature 票三段合格（使用者故事＋流程表格＋規則句、規則帶短名）、Task 票全為職能實作契約句且無手段詞、無商業規則複寫 = 通過；零星重述、殘留手段詞、或寫法違規 1-3 處 = 部分；project 藏規則本體、Task 票空洞或成段複寫 Feature 票規則、手段詞成片、或需求描述與流程寫法系統性違規 = 未通過。

## D3 · 完整性

**定義**：交付含模組所需的必要區塊；**狀態密集模組每個狀態機附 UML**（狀態 + 轉換 + 觸發）；**有業務可觀測結果的功能附驗收條件**（可勾稽情境、3-5 條、達成 / 未達成二元）。

**絕對不要**：
- 狀態密集模組（多實體各有狀態），絕對不要交付沒有任何狀態流轉圖的文件
- 雙維度狀態（如審稿 / 印製、開票 / 收款），絕對不要擠成一張圖
- 絕對不要漏掉模板規定的必要區塊（概述 / 使用情境 / Spec）；絕對不要把資料欄位表寫進交付內容（欄位正本在 wiki 實體卡）
- 有明確業務結果的功能，絕對不要交付沒有任何驗收條件的 project 描述；絕對不要把通用品質門檻（測試 / code review / 文件）當該模組的驗收條件混進來

**正例**：訂單交付補上 8 類狀態機（訂單 / 印件雙維度 / 打樣 / 訂單異動 / 售後 / 發票 / 折讓 / 請款期次雙維度）各一張 Mermaid 圖。

**反例（本次真實）**：交付初稿涵蓋訂單 / 印件 / 金流 / 發票多個狀態機的模組，卻完全沒有狀態流轉圖 → Miles 指出「只要是狀態的都需要附上 UML」。

**評分**：必要區塊齊 + 狀態機 UML 齊 + 驗收條件齊（可勾稽、未混 DoD）= 通過；缺 1-2 張狀態圖、驗收條件單薄或混入通用門檻、某區塊單薄 = 部分；狀態密集卻無 UML、或缺核心區塊、或有業務結果的功能完全無驗收條件 = 未通過。

## D4 · 真實性（不捏造）｜一票否決

**定義**：交付內容的規則 / 狀態 / 數值 MUST 來自規格正本。來源未定義者，停下來記 OQ + 標「另案處理」，不自編。

**絕對不要**：
- 來源（spec）未定義某邏輯時，絕對不要自編一套規則填入交付文件
- 絕對不要用「應該 / 大概 / 通常」的推測當定案寫入
- 絕對不要為了「看起來完整」而補上沒有依據的狀態轉換 / 公式 / 欄位 / 驗收條件情境

**正例（本次真實）**：要畫付款狀態圖時，發現 spec 未定義「部分退款 / 已退款」判定條件 → 停下來問 Miles + 記 `oq-manage` ORD-027 + 交付文件標「依收款累計推導、完整定義另案處理」，**不畫捏造的轉換**。

**反例**：spec 沒寫就自行假設「收到任一筆退款 = 部分退款、退滿 = 已退款」當定案畫進圖裡、發布給開發。

**評分**：全部有據、缺口已顯性化 = 通過；任一處捏造 = **未通過（整體一票否決，不可發布）**。

## D5 · 交付結構完整性（v4 結構件）

**定義**：交付模板的結構件齊備——Project 含「測試決策」章（受測介面 2-4 個＋測試先行說明，只此一處）與功能票清單（每條附票名、用戶故事式範圍句、原生提及）；milestone 以需求主題命名；每張 Feature 票掛 milestone、掛 Label（Type/Feature＋Product）、為其 Task 票的 parent、每個功能節四段齊備（節名／使用者故事／規則／驗收條件）；每張 Task 票掛 Label（Type/Task＋Role＋Product），段落依模板 § 四（背景／算式／規則／驗收／範圍；驗收每條標受測介面），parent 掛對 Feature 票；阻擋關係以 Linear 原生 blocking 建在 Task 層、票內不列 Blocked by 段。

**絕對不要**：
- **絕對不要一個功能節裝多個功能顆粒**——節內出現兩條互不相干的流程主線、或驗收條件超過 5 條，即為顆粒度違規，拆節；Feature 票承載一個需求主題，主題內多個功能節合法（2026-08-31 Miles 追認），主題之間互不相干才拆票
- **絕對不要在標題帶職能字樣**——「（前端）」「（後端）」「FE」「BE」一律不進標題，職能由 Role Label 承載
- **絕對不要留沒掛 milestone 的 Feature 票，或 Label 三軸不全的票**——Role（Backend／Frontend／Design／PM）、Product（ERP／EC／編輯器）、Type（Feature／Task／Bug）為工作區既有分組，缺一即缺資訊；不自創新值
- **絕對不要用日期或批次當 milestone 名**——「2026-08 工單編輯批」「第三批」類名稱不成立，milestone 名寫需求主題（「工單主流程」）
- **長段絕對不要平鋪**——超過 10 行的流程表格、狀態機圖、逐條規則清單收進收合區塊；且批次套用前 MUST 先以一張票試寫、確認 Linear 與 GitHub 同步票兩面渲染正常（需求描述與驗收條件永遠平鋪、不收合）
- 絕對不要漏掉「測試決策」章；絕對不要另附「Prototype 參照邊界」表（為準／不為準邊界正本在 CLAUDE.md 分工宣告，交付不重述）
- 絕對不要交付缺「規則」或「驗收」段的 Task 票；絕對不要在票內另寫「Blocked by」段（阻擋關係用 Linear 原生 blocking）；票內絕對不要重複測試先行引言（該說明只在「測試決策」章）
- 絕對不要留沒有 parent 的 Task 票、或 parent 掛錯 Feature 票
- 驗收測試絕對不要落在「測試決策」章未議定的受測介面上（含議定文字涵蓋的行為範圍；先回頭補議定，不偷跑）
- 驗收測試的期望值絕對不要用「與實作同一套方式重算」得出（自我循環、永遠會過）——期望值必須取自 Feature 票驗收條件的具名案例，且必須是受測介面上看得到的值（引擎中間值不算）
- 絕對不要另開設計票（DE 票）——操作方式與介面由 Prototype 承載

**評分**：結構件全齊 = 通過；零星缺漏 1-2 處（如個別票漏 Blocked by、單張票 Label 缺一軸）= 部分；系統性缺失（單票裝多功能、全部票無驗收測試、無測試決策章、全批未掛 milestone）= 未通過。
