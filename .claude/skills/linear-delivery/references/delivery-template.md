# Linear 交付標準模板（自包含）

> **本模板是精煉出的標準結構，不引用任何特定 issue / 需求作為對照**（實例會被修改或刪除即失效）。
> 產出時依此模板填空；模板更新走版本控管（見末「版本」）。
> 正本分工：wiki＝商業內容正本（概述與 Use Case 取材處）、spec＝功能行為正本（Feature 商業邏輯與驗收取材處）、**Prototype＝介面與互動正本（操作動線與版型以 Prototype 為準，交付不文字重述、不附參照格）**。
> **三層結構（v3.0）**：**Project＝薄目錄＋商業脈絡**（概述、Use Case、範圍主票清單、跨票遊戲規則）→ **Feature 主票＝一個工作範圍的商業邏輯與驗收條件正本**（PM team，sub-issue 的父票）→ **職能 sub-issue＝該範圍該職能的行為要求與驗收測試**（掛在主票下）。閱讀順序由大到小、內容不重複：Project 讀方向、主票讀規則、sub 讀自己要交付的行為。
> 主票的切分軸線是**工作範圍**（如「工單建立主流程」「預估成本」），不是規格文件的章節——一張 sub-issue 恰好屬於一個主票；切出多重歸屬即代表主票切太細，回頭合併範圍。
> 通篇自包含（Linear 為對開發的交付正本；wiki 為欄位與狀態正本、開發直接查閱），跨單據只以 Linear 識別碼互指，**不出現 `openspec/...` 路徑或內部檔名**。

   1. <子情境>
2. <角色> ...

1. **<範圍名>**：<一句說明>　<主票原生提及>

**Out of Scope**

- <不做項>：<歸屬——延後批次 / 其他 project / 其他平台>

## 測試決策

    <狀態A> --> <狀態B>: <觸發 / 條件>

### 填寫要點

- **概述**：商業目標＋現行問題與痛點，取材 wiki（痛點卡、商業邏輯卡「現況」段）。不寫功能清單（那是 Scope 的事）。
- **Use Case**：業務敘事白話句、角色 × 業務動作；可跨 project 講完整業務故事。取材 wiki 業務情境。
- **Scope（範圍主票清單）**：維度是「工作範圍」——一條 Scope＝一張 Feature 主票＝一組可獨立交付的相關功能（如「工單建立主流程」涵蓋確認、指派、規劃、審核）。每條一句話定位＋主票**原生提及**，商業邏輯本體在主票、不在此展開。後續批次擴充＝加一條清單＋一張新主票，project 不再長章節。
- **Prototype**：介面與互動正本；交付文件不附 Prototype 參照格，也不另附為準／不為準邊界表（邊界正本在 CLAUDE.md 分工宣告）。
- **測試決策**：受測介面（測試觀察點）2-4 個、交付時預先議定——各票驗收測試都必須落在這些介面上（含議定文字涵蓋的行為範圍），測試火力集中在關鍵路徑而非每個邊角。跨主票共用的遊戲規則，留 project 只寫一次。
- **狀態機**：跨票共用的圖留 project；已在其他 project 繪製的狀態機用原生提及引用該 project、不重繪（避免兩處維護不同步）。
- **書寫原則（全篇，含主票與 sub-issue）**：(1) ste100 受控句法——白話完整句、一句一事、業務主管唸得順；(2) 只寫現在式的「系統是什麼」，**禁設計對比語言**（合一 / 統一 / 取代 / 不再 / 原本）；(3) 規則本體只在一處、他處一句引用；(4) 禁中英夾雜（英文識別碼用「中文（英文）」格式）；(5) 成品禁出現內部路徑、檔名、內部問題編號。
- **不放進 Project 的**：功能的商業邏輯與驗收條件（→ Feature 主票）、操作方式與畫面動線（→ Prototype）、行為要求（→ sub-issue）、資料欄位表（→ wiki 實體卡，開發直接查閱）、職能分工區塊與票號對照（父子階層已承載）。

## 二、Feature 主票模板（What 本體層；PM team、sub-issue 的父票）

```markdown
## 概述

1. 本票是 <project 原生提及>「<範圍名>」的商業邏輯與驗收條件正本
2. 範圍一句話：<這個範圍讓誰完成什麼>
3. 實作由本票底下的 sub-issue 承載，職能與動工順序見各 sub-issue

## <功能名 1>

<一句功能描述>

### <Function 名（單 Function 的功能不立此標題）>

**商業邏輯**

- <白話完整句的業務規則：誰、什麼條件、發生什麼、必要時附為什麼>

**驗收條件**

- 假設 <前置情境>，當 <動作 / 觸發>，則 <可觀測結果>（3-5 條，超量拆節）

## <功能名 2>

<同上結構>
```

### Feature 主票填寫要點

- 主票＝原 Key Feature 章的家：一個範圍主票收多個功能章，每章「商業邏輯＋驗收條件」，寫法沿用原 Key Feature 章規範（情境式／規則式、3-5 條、不混 Definition of Done、缺料標另案）。
- 主票掛 **PM team**、為所有 sub-issue 的 parent；主票本身不是開發工作票，不寫實作內容。
- 商業邏輯的單一正本在主票：sub-issue 與其他主票需要時一句引用（原生提及），不複寫。

## 三、職能 sub-issue 描述模板（How 層；掛在 Feature 主票下）

### Sub-issue（一張 sub 恰好一個父主票；職能由開票時指派的 team 承載，不出設計票——操作方式與介面由 Prototype 承載）

```markdown
## 概述

1. 商業規則與驗收條件見父票 <主票原生提及>；本票負責其中 <職能> 的 <一句範圍>
2. <若本票行為同時服務其他主票：一句說明＋該主票原生提及（related 關聯）>

## 行為要求

<可依主題分組；每條為行為契約句>
- [ ] <什麼情況下，系統要發生什麼／不許出現什麼；含條件、結果、邊界，不含實作手段>

## 驗收測試

- [ ] 假設 <前置情境>，當 <動作>，則 <可觀測結果>（受測介面：<名稱>）

## Blocked by

- <阻擋票的 Linear 識別碼與票名>，或「無——可立即開工」

## 依賴與範圍

- [ ] <依賴其他模組 API：標明「只消費、不實作」>
- [ ] <Out of Scope 註記（不含項與歸屬）>
```

### Sub-issue 填寫要點

- **行為要求＝行為契約**：只寫「世界必須長什麼樣子」——觸發條件、必然結果、不許出現的狀態、邊界值處理；**技術手段一個字不寫**（交易、回滾、鎖、快取、樂觀更新、查詢時聚合、旗標、序列產生器、多對多、可空關聯等手段詞全部禁用），用什麼工具達成由開發決定。範例：不寫「兩步做成同一個交易、失敗一起回滾」，寫「印件狀態推進與工單草稿建立要同時成立——不允許出現印件已推進、工單卻沒建出來的狀況，反之亦然」。
- 每句行為要求必須是業務主管唸得順的完整句（ste100）；讀不懂的句子＝寫錯了，不是讀者的問題。
- **概述**：指回父主票＋一句職能範圍；不複寫主票的商業邏輯。引用一律 Linear 原生提及（寫法見 SKILL.md 操作 know-how）。
- **驗收測試**：3-5 條、每條可獨立驗證；期望值取自父主票驗收條件的具名案例（禁與實作同式重算、禁引擎中間值——期望值必須是受測介面上看得到的值）；每條標受測介面（必須在 Project「測試決策」章議定範圍內）。測試先行說明只在 Project「測試決策」章一處，票內直接列清單。
- **Blocked by**：開票順序 blockers-first；用 Linear 原生 blocking 關係建立（阻擋關係建在 sub 層），票內本段同步列出；無阻擋者寫「無——可立即開工」。
- **依賴註記**：跨模組依賴標「只消費不實作」；Out of Scope 項標清楚。
- 進行中（In Progress）且已有內容的 issue **不覆寫**（含既有設計票遺產），只由 project 描述引用。

## 四、狀態機規範

- 狀態密集模組（多實體各有狀態）**每個狀態機附一張 UML**；狀態列舉與轉換正本在 wiki 狀態機卡，交付圖忠實轉繪、**不畫來源未定義的轉換**（缺料記 OQ 標另案）。
- 形式：Mermaid ` ```mermaid ` + `stateDiagram-v2`；每張圖含狀態節點＋轉換箭頭＋觸發 / 條件標籤；關鍵終態 / 不可逆用 `note` 標。
- 雙維度狀態分開各畫一張；視圖層 project 沿用核心 project 的圖、不另繪，以文字交代相關轉換。
- 中文狀態代號無標點符號；轉換標籤避免半形括號（用「·」或全形）。
- 寫入 Linear 後 MUST 請 Miles 確認渲染成圖。

## 五、Milestone 與開票順序

- **Milestone＝縱向整合節點**：每個 milestone 是一條可展示的端到端路徑（例「手動分派走通」），把該路徑相關的票掛入；milestone 的先後即整合順序，讓跨票協作的先後在 Linear 介面上直接可見。
- **開票順序 blockers-first**：先開被依賴的票（取得 Linear 識別碼），再開依賴它的票並建立 Linear 原生 blocking 關係；票內「Blocked by」段同步列出。所有阻擋已完成的票即為可立即開工的前沿。
