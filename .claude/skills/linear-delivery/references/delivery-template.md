# Linear 交付標準模板（自包含）

> **本模板是精煉出的標準結構，不引用任何特定 issue / 需求作為對照**（實例會被修改或刪除即失效）。
> 產出時依此模板填空；模板更新走版本控管（見末「版本」）。
> 正本分工：wiki＝商業內容正本（概述與 Use Case 取材處）、spec＝功能行為正本（Feature 票商業邏輯與驗收取材處）、**Prototype＝介面與互動正本（操作動線與版型以 Prototype 為準，交付不文字重述、不附參照格）**。
> 通篇自包含（Linear 為對開發的交付正本），跨單據只以 Linear 識別碼互指，**不出現 `openspec/...` 路徑或內部檔名**。

## 巢狀結構（v4）

| 層 | 是什麼 | 顆粒度 | Label |
|----|--------|--------|-------|
| Project | 薄目錄＋商業脈絡 | 一個平台的一個模組 | — |
| Milestone | 需求主題 | 一組要一起交付的功能 | — |
| Feature 票 | 單一功能顆粒的需求正本 | **一張票一個功能** | Type/Feature＋Product/ERP |
| Task 票 | 該功能的職能實作 | 一職能一張 | Type/Task＋Role/Backend 或 Frontend＋Product/ERP |
| Sub-Task 票 / Bug 票 | Task 再往下切 | 開發自行判斷 | 依需要 |

- Feature 票掛 milestone；Task 票的 parent 掛 Feature 票；再往下需要時開 Sub-Task 或 Bug。
- 閱讀順序由大到小、內容不重複：project 讀方向、milestone 讀這批要交付什麼、Feature 票讀需求本體、Task 票讀自己要交付的行為。
- **一張 Feature 票只裝一個功能**：一張票塞多個功能（如把確認、指派、規劃、審核裝進「工單建立主流程」）即為顆粒度違規，回頭拆成多張 Feature 票、掛同一個 milestone。

### 填寫要點

- **概述**：商業目標＋現行問題與痛點，取材 wiki（痛點卡、商業邏輯卡「現況」段）。不寫功能清單（那是 Scope 的事）。
- **Use Case**：業務敘事白話句、角色 × 業務動作；可跨 project 講完整業務故事。取材 wiki 業務情境。
- **Scope（功能票清單）**：一條 Scope＝一張 Feature 票＝一個功能顆粒。每條寫「票名＋一句用戶故事式範圍句」——範圍句要講清楚**誰用它做到什麼**，讓讀者只掃 project 層就知道每張票要實作什麼。商業邏輯本體在 Feature 票、不在此展開。後續批次擴充＝加清單條目＋開新 Feature 票掛新 milestone，project 不再長章節。
  - 正例：**印件製作細節確認**：訂單管理人逐張確認印件的製作條件，確認後生產端拿到工單草稿。
  - 反例：**印件製作細節確認**：處理印件製作細節的相關邏輯與流程。（看不出誰用、做到什麼）
- **Prototype**：介面與互動正本；交付文件不附 Prototype 參照格，也不另附為準／不為準邊界表。
- **測試決策**：受測介面（測試觀察點）2-4 個、交付時預先議定——各票驗收測試都必須落在這些介面上（含議定文字涵蓋的行為範圍）。跨票共用的遊戲規則，留 project 只寫一次。
- **狀態機**：跨票共用的圖留 project；已在其他 project 繪製的狀態機用原生提及引用該 project、不重繪。
- **不放進 Project 的**：功能的需求描述、商業邏輯與驗收條件（→ Feature 票）、操作方式與畫面動線（→ Prototype）、行為要求（→ Task 票）、資料欄位表（→ wiki 實體卡，開發直接查閱）、職能分工區塊與票號對照（Label 與父子階層已承載）。

## 二、Milestone 規範

- **Milestone＝需求主題**：名稱寫這批要達成的業務主題，如「工單主流程」「印件製作細節」「成本試算」。
- **禁日期批次名**：不寫「2026-08 工單編輯批」「第三批」類名稱——日期與批次是交付動作的紀錄，不是需求主題，半年後沒人看得出裡面是什麼。
- 一個 milestone 收多張 Feature 票；先後順序即整合順序。
- 是否建 milestone 依該批拍板；建了就每張 Feature 票都要掛，不留無歸屬的票。
- **Project 全域規劃 milestone 時，既有票一律補掛**（含已完成的票）：milestone 是 project 的工作分解容器，漏掛的票在 project 層看不見。此時動既有票的 milestone 不受「既有票欄位保留紀律」限制。

## 二之二、缺陷與實測修正的承載方式

- **Project 與 Issue 是工作分解結構（WBS）**：一張票是一份工作，不是一則待辦事項。
- **票的主體是正本，會一直更新**：內容與現行定案不符就直接改，不因票已完成或驗收中而保留錯的內容。實作與文件對不上的代價遠高於保留一份歷史對照。
- **留言是修正紀錄**：每次修正另寫一則留言，記錄原本怎麼寫、現在的定案是什麼、依據哪張 wiki 卡。
- **主體被修訂處附留言連結**：在改寫的段落後加「（[參考留言](<票網址>#comment-<留言 id 前 8 碼>)）」，讓看票的人查得到這條為什麼變。

**要不要另開票，依修正性質判定**

| 修正性質 | 承載方式 |
|---|---|
| 行為與定案不符（缺陷） | 改票主體＋寫留言；票已完成時狀態改回 Todo |
| 既有功能加新行為（優化） | 開 Task sub-issue，parent 掛該功能的原票 |
| 牽出一個新功能顆粒 | 開新 Feature 票 |

- **開 sub-issue 或新 Feature 票前必須先問**：要不要獨立成票由 Miles 決定，不自行開票。
- **缺陷留言固定兩段**：現況問題（系統現行行為、實測值與期望值的差距、實測日與受測單據編號）→ 修正規則（編號條列，每條一句可實作）。
- **驗收條件不重複維護**：同一組驗收條件已在上層票時，留言不重寫，改為確保上層正確。
- **不做的項目也要寫下來**：判定為不做時，寫進票的範圍段或留言並附原因，避免開發照舊版實作。
- **已完成的票改回 Todo 是預期副作用**：完成時間會被清空、票會被移入當前 cycle，交付回報時要說明。

## 三、Feature 票模板（需求本體層；Type/Feature＋Product/ERP，Task 票的父票）

```
## 概述

<一句話：這張票讓誰做到什麼。所屬模組以 project 原生提及帶出>

>>> ## <功能節名>

<使用者故事：身為（角色），我要（做到什麼），以（避免什麼或達成什麼）>

**<表格標題>**

| <欄> | <欄> |
|---|---|

**算式**

```
<一行一式>
```

**規則**

1. <一條一件事>

**驗收條件**

- 假設<前提>，當<動作>，則<可觀測結果>

>>>

>>> ## <下一個功能節名>
...
>>>
```

### Feature 票填寫要點

- **一節一個功能**：一節裝兩個互不相干的功能就拆節；驗收條件超過 5 條時回頭檢查是不是裝了兩個功能。
- **四段皆為必要**：節名、使用者故事、規則、驗收條件。缺任一段不得發布。
- **節名寫業務讀得懂的功能名**：禁內部造詞與只有我們懂的縮寫。判準是把節名念給沒參與討論的業務或開發聽，對方說得出這節在做什麼。
- **使用者故事一句**：票層的概述講整張票的目的，節層的使用者故事講這個功能對業務的意義。兩者都不寫實作。
- **規則結構化**：依 § 5.7 選表格、算式區塊或編號條列，不寫敘事長句。
- **每個功能節用收合區塊包起來**：清單頁只看得到節標題，展開才看內容。
- **商業邏輯是單一正本**：Task 票與其他 Feature 票需要時以原生提及引用，不複寫。
- **標題格式 `[ Feature ] - <功能語意>`**：前綴保留。
- 掛 milestone、掛 Label（Type/Feature＋Product＋Role/PM）；本票不是開發工作票，不寫實作內容。

## 四、Task 票模板（How 層；parent 掛 Feature 票或該功能的原 Task 票）

```
## 背景

<使用者故事：身為（角色），我要（做到什麼），以（避免什麼或達成什麼）>

## 算式

```
<一行一式；沒有算式時整段不寫>
```

## 規則

1. <一條一件事；寫世界必須長什麼樣子，不寫技術手段>

## 驗收

- 假設<前提>，當<動作>，則<可觀測結果>（受測介面：<分頁名>）

## 範圍

- <只取用不自行實作的依賴>
- 不做：<不做的項目與原因>
```

### Task 票填寫要點

- **背景寫使用者故事**：一句，講這個職能要交付什麼、不交付會怎樣。不寫「本票負責父票某節的後端行為」這種指路句。
- **規則＝行為契約**：只寫觸發條件、必然結果、不許出現的狀態、邊界值處理。技術手段一個字不寫（交易、回滾、鎖、快取、樂觀更新、旗標、序列產生器等手段詞全部禁用）。
- **算式獨立成段**：金額、數量、日期的推導一律進程式碼區塊，一行一式，不塞進規則句。
- **驗收 3 至 5 條**：期望值取父票驗收條件的具名案例，禁與實作同式重算、禁引擎中間值；每條標受測介面，受測介面要在 Project 測試決策章議定的範圍內。
- **範圍段收兩類**：只取用不自行實作的依賴、判定為不做的項目（附原因）。
- **不寫 Blocked by 段**：阻擋關係用 Linear 原生 blocking 建立，介面會呈現，票內不再列一次。
- **標題格式 `[ Task ] - <功能語意>`**：前綴保留，禁「（前端）」「（後端）」字樣。
- **Task 票平鋪不收合**：單一段落超過 10 行時才收合該段。

## 五、共用寫法規範（Feature 票與 Task 票一體適用）

### 5.1 使用者故事格式

- 需求描述固定一句：**身為（角色），我要（動作），以（業務目的）**。
- 角色寫 wiki 角色卡的名稱（訂單管理人、生管、印務、師傅），不寫「使用者」「系統管理者」。
- 業務目的寫這件事對生意的作用，不寫「以完成此功能」類空轉句。
- 正例：身為訂單管理人，我要在訂單確認後逐張確認印件的製作細節，以讓生產端拿到可以開工的工單草稿。
- 反例：本功能提供印件製作細節的確認機制，供訂單管理人使用。（功能說明句，不是使用者故事）

### 5.2 流程表格 vs 規則句二分

| 內容性質 | 判準 | 呈現方式 |
|---------|------|---------|
| 流程 | 有角色接力或時序先後（誰先做、接著誰做） | **一律表格**，欄位固定：步驟｜角色｜行為｜系統結果 |
| 規則 | 單點的 if-then、約束、門檻、適用範圍 | **受控句法句子**（一句一事、主動語態、明確主詞） |

- 流程禁敘述句串接：不寫「訂單管理人填寫後送出，系統推進印件狀態並建出工單草稿，之後生管在清單接手規劃」——三個角色接力擠一句，讀者要自己拆。
- 規則禁硬塞表格：單點規則（如「印件已建工單者不可再次送出確認」）用句子講完最省讀，套成表格只是加框。
- 判不出是流程還是規則時問一句：**刪掉這句，讀者是否就不知道下一棒是誰**。是→流程（表格）；否→規則（句子）。

### 5.3 收合區塊（toggle）

- 用途：長段內容（超過 10 行的流程表格、狀態機圖、逐條規則清單）收進收合區塊，讓票的第一屏看得完。
- 寫法：Linear 描述內用收合區塊語法包住段落；同步到 GitHub 時渲染為 details 元素。
- **批次套用前 MUST 先以一張票試寫驗證**：寫入一張票 → 開 Linear 頁面確認收合正常展開 → 開 GitHub 同步票確認 details 元素正常 → 兩面都對才套用其餘票。渲染不如預期時改回平鋪段落，不硬套。
- 收合的是細節不是重點：需求描述與驗收條件永遠平鋪，不收合。

### 5.4 Label 三軸

| 軸 | 值域 | 用途 |
|----|------|------|
| Role | Backend／Frontend／Design／PM | 承載職能，取代標題裡的「（前端）」「（後端）」 |
| Product | ERP／EC／編輯器 | 承載產品線 |
| Type | Feature／Task／Bug | 承載層級 |

- 三軸為工作區既有分組，不自創新值；Feature 票掛 Type/Feature＋Product＋Role/PM，Task 票掛 Type/Task＋Product＋Role/Backend 或 Frontend。
- **Type 軸必掛且與標題前綴一致**：`[ Task ] ` 前綴的票掛 Type/Task、`[ Feature ] ` 前綴的票掛 Type/Feature。
- Label 齊全是結構件：缺 Label 的票等於缺資訊，發布前逐票檢查。

### 5.5 不寫什麼

Linear 介面已經呈現的資訊，票內不再用文字寫一遍；正本在別處的內容，票內不重複維護。

| 不寫 | 為什麼 |
|---|---|
| 「實作由本票底下的 sub-issue 承載」 | 巢狀關係介面已呈現 |
| 「本票是某某的商業邏輯與驗收條件正本」 | 層級即資訊，不必自述 |
| 「商業規則見父票某某」 | 父票在介面上方，點得到 |
| Blocked by 段 | 原生 blocking 關係介面已呈現 |
| 「欄位正本：wiki 某某卡」 | wiki 指路句，開發直接查 wiki |
| 「（2026-08-26 補齊）」「（2026-08-25 拍板）」 | 日期註記妨礙閱讀；拍板紀錄留在 wiki |
| 父票已寫的規則 | 同一條規則只在一處維護 |
| 票內已寫的內容再寫進留言 | 同上 |
| 內部路徑、檔名、內部問題編號 | 對開發無意義，且會外露內部工作版本 |

### 5.7 規則的結構化寫法

規則一律結構化，三種形式擇一或並用。判準是開發要查某一條時，能不能三秒鐘定位。

| 內容性質 | 用什麼 |
|---|---|
| 誰存什麼、哪種情況走哪條路、狀態怎麼推導 | 表格 |
| 金額、數量、日期的推導 | 程式碼區塊，一行一式 |
| 條件與限制 | 編號條列，一條一件事 |

禁止的寫法：

- 一個句子塞多條規則。
- 括號裡再套括號。
- 分號串接三件以上。
- 把算式寫進敘事句中間。

### 5.6 書寫原則（全篇）

1. ste100 受控句法——白話完整句、一句一事、業務主管唸得順。
2. 只寫現在式的「系統是什麼」，**禁設計對比語言**（合一 / 統一 / 取代 / 不再 / 原本）。
3. 規則本體只在一處、他處一句原生提及引用。
4. 禁中英夾雜（英文識別碼用「中文（英文）」格式）。
5. 成品禁出現內部路徑、檔名、內部問題編號。

## 六、狀態機規範

- 狀態密集模組（多實體各有狀態）**每個狀態機附一張 UML**；狀態列舉與轉換取材 wiki 狀態機卡，交付圖忠實轉繪、**不畫來源未定義的轉換**（缺料記 OQ 標另案）。
- 形式：Mermaid ` ```mermaid ` + `stateDiagram-v2`；每張圖含狀態節點＋轉換箭頭＋觸發 / 條件標籤；關鍵終態 / 不可逆用 `note` 標。
- 雙維度狀態分開各畫一張；視圖層 project 沿用核心 project 的圖、不另繪，以文字交代相關轉換。
- 中文狀態代號無標點符號；轉換標籤避免半形括號（用「·」或全形）。
- 寫入 Linear 後 MUST 請 Miles 確認渲染成圖。

## 七、開票順序

| 步驟 | 動作 | 注意 |
|------|------|------|
| 1 | 建 milestone（需求主題名） | 禁日期批次名 |
| 2 | 開全部 Feature 票 | PM team 建立、**不轉隊**；掛 milestone＋Label（Type/Feature＋Product）；取得識別碼 |
| 3 | 覆寫 project 描述 | 把 Feature 票識別碼與範圍句填進 Scope 清單 |
| 4 | 依 blockers-first 開 Task 票 | PM team 建立（觸發 GitHub 同步）→ 轉入 FE / BE team → 以 parentId 掛回 Feature 票；轉隊前先確認該 team 已在 project teams 清單（見 SKILL.md「轉隊會靜默解除 project 關聯」）|
| 5 | 建 blocking 關係 | 阻擋關係建在 Task 層，Feature 票不掛 blocked by |
| 6 | 回填原生提及 | project 描述 Scope 清單的票號於各票建立後回填 |

## 八、正反例（一組功能的完整對照）

### 反例（把多個功能塞進一張票、標題帶職能、內容全是敘事句）

```markdown
標題：工單建立主流程（前端）

## 概述

1. 本票是「工單建立主流程」的商業邏輯與驗收條件正本
2. 實作由本票底下的 sub-issue 承載，職能與動工順序見各 sub-issue

## 印件製作細節確認

本功能提供印件製作細節的確認機制，僅適用線下單。訂單管理人填寫製作條件後送出，
系統推進印件狀態並建出工單草稿，之後生管在工單清單接手規劃。

## 工單指派
## 製程規劃
## 工單審核
## 預估成本
## 色數登記
```

被擋原因逐條：

| # | 形態 | 違規 |
|---|------|------|
| 1 | 一張票裝六個功能 | 顆粒度違規，票太大看不完（見 § 巢狀結構）|
| 2 | 標題帶「（前端）」 | 職能應由 Role Label 承載（見 § 5.4）|
| 3 | 概述兩句 meta 導覽 | 禁 meta 導覽句（見 § 5.5）|
| 4 | 「本功能提供…機制」 | 需求描述非使用者故事（見 § 5.1）|
| 5 | 角色接力寫成一段敘述句 | 流程未表格化（見 § 5.2）|
| 6 | 「僅適用線下單」寫在描述段 | 適用範圍句應歸商業邏輯（見 § 三填寫要點）|

### 正例（同一功能改寫成一張 Feature 票）

```markdown
標題：印件製作細節確認
Label：Type/Feature、Product/ERP
Milestone：工單主流程

## 需求描述

身為訂單管理人，我要在訂單確認後逐張確認印件的製作細節，以讓生產端拿到可以開工的工單草稿。

## 商業邏輯

### 確認流程

| 步驟 | 角色 | 行為 | 系統結果 |
|------|------|------|---------|
| 1 | 訂單管理人 | 開啟印件的製作細節頁、填寫製作條件 | 系統保留填寫內容 |
| 2 | 訂單管理人 | 送出確認 | 印件印製維度推進、同時建出工單草稿 |
| 3 | 生管 | 在工單清單開啟該草稿 | 草稿可被接手規劃 |

### 規則

- 本功能只適用線下單；線上單的製作條件由下單資料帶入，不走本流程。
- 印件已建出工單者，不可再次送出確認。
- 印件狀態推進與工單草稿建立要同時成立，不允許只成立其中一件。

## 驗收條件

- 假設線下單的印件已填妥製作條件，當訂單管理人送出確認，則工單清單出現一張該印件的工單草稿。
- 假設印件已建出工單，當訂單管理人再次送出確認，則系統不建立第二張工單草稿。
- 假設訂單為線上單，當訂單管理人開啟印件，則畫面不提供製作細節確認。
```
