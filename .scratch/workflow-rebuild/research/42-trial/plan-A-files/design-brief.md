# 轉交單管理：設計工作底稿（照 interface-design 方法產出）

本檔是 interface-design 方法要求的中間產出。需求描述正文在 `../plan-A.md`。
視覺數值一律以 erp `Designs.md` 為準，本檔的色彩世界與特徵只用來理解使用情境，不轉成配色或自訂元件。

## 一、意圖（Intent First）

| 問題 | 答案 |
|------|------|
| 這個人是誰 | 生管（依 wiki；需求原文寫廠務，見 plan-A.md 未定事項）。坐在工廠辦公室桌機前。五分鐘前剛看到印刷站報工出一批良品；五分鐘後會接到現場電話或 Slack，問某一趟貨到了沒 |
| 他要完成什麼 | 把報工出來的良品排成一趟搬運並指定負責廠務；找出卡在哪一段的單（還沒人搬、在路上、卸了沒人收）；撤掉點收前不該這樣送的單 |
| 該有什麼感覺 | 像貨運站的出車調度板：一眼看出哪幾趟還沒出發、哪幾趟擱最久。密度高、安靜，數字對得上比好看重要 |

合理假設（方法允許先假設再進行）：使用者以 wiki 的建單與作廢角色為準。

## 二、產品領域探索（四項產出）

| 項目 | 內容 |
|------|------|
| 領域概念（5 項以上） | 一趟（以推車推去哪一條產線定義）、目的產線與站點、搬運數量對點收量、簽收照片、轉交可申請上限（額度）、待搬運的單擱了多久、紙本工單跟著貨走的舊做法 |
| 色彩世界（5 項以上） | 推車的鍍鋅灰鐵、棧板原木色、紙堆的白、裁切機警示黃黑條、現場標籤貼紙的紅與綠、白板馬克筆藍 |
| 特徵 | 每條明細「排了多少、收了多少」兩個數並排，差額看得見（wiki 原意：差額留在明細上看得見） |
| 要避開的預設 | 見下方「建議與提問」的拒絕列 |

拿掉產品名的檢驗：只看「一趟、目的產線、搬運數量對點收量、簽收照片、額度回到來源任務」，讀者可認出是工廠站間搬運單據，通過。

## 三、每個畫面的焦點

| 畫面 | 焦點 | 降級的資訊 |
|------|------|-----------|
| 轉交單清單 | 每張單的狀態與建單時間（並看可知擱多久） | 所屬印件、備註 |
| 轉交單明細 | 每條明細的搬運數量與點收量 | 歷程紀錄、修正紀錄 |
| 建立轉交單 | 每筆的搬運數量與轉交可申請上限 | 目的站點（唯讀帶出） |

## 四、建議與提問（Suggest + Ask 區塊）

```
Domain:     一趟、目的產線與站點、搬運數量對點收量、簽收照片、轉交可申請上限、擱置時間
Color world:鍍鋅灰鐵、棧板原木、紙白、警示黃黑、標籤紅綠、白板藍
Signature:  明細行的搬運數量與點收量並排，差額看得見
Rejecting:  空白新增表單建單 → 從待轉交任務勾選帶出；
            狀態只是一欄標籤 → 預設只列在途、擱最久的在上；
            作廢做成刪除 → 填作廢原因、單留著可查
Direction:  調度板式的高密度清單，焦點放在單停在哪一段
```

方法要求接著問「這個方向對嗎」。本次是子代理受測，無法向 PM 提問；且 erp 規範下視覺方向不由 PM 決定（見 plan-A.md 不相容紀錄）。

## 五、每個元件前的檢查點（Before Writing Each Component）

| 項目 | 內容 | 為什麼 |
|------|------|-------|
| Intent | 生管排趟、找卡住的單、撤單 | 見第一節 |
| Hierarchy | 見第三節焦點 | 使用者要做的動詞決定誰先 |
| Palette | 白容器、中性灰、單一藍主色，狀態色只用於狀態 | erp `Designs.md` §3 既定，不依色彩世界調整 |
| Depth | 表格外框 1px 邊加 12 圓角 | erp `Designs.md` §5、§6.2 既定 |
| Surfaces | 版面底灰、容器白 | erp `Designs.md` §3 既定 |
| Typography | Noto Sans TC，基準 14，字級表照 §4 | erp 既定，不另選字體 |
| Spacing | 8 起跳的間距表 | erp `Designs.md` §5 既定 |

## 六、交付前檢查（The checks）

| 檢查 | 結果 |
|------|------|
| 換掉字體與版型會不會不同（Swap test） | 不會不同。erp 規定套標準配方與固定字體，依方法判定屬「預設」；以 erp 為準 |
| 瞇眼看層次（Squint test） | 無法執行，本階段沒有畫面 |
| 特徵出現在五個具體位置（Signature test） | 明細表的搬運數量與點收量欄、每條明細的點收紀錄、搬運數量修正紀錄、建單時搬運數量對轉交可申請上限、作廢後額度回到來源任務（待轉交任務的上限回升） |
| 唸出變數名稱是否屬於本產品（Token test） | 不屬於。erp 變數為通用名稱（accent、neutral），由 Figma 產出；以 erp 為準 |
