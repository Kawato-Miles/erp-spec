# 地圖：工作環境重建

## Destination

Miles 只給需求。代理依 matt 的 skill 流程，從釐清一路做到交付，中斷後能自行接續。
Miles 不再花時間做對齊工作（wiki 用詞、規劃單、Prototype、Linear 之間的一致）。
環境（AGENTS.md、記憶檔、skill、hook）只留實際用得到的內容。
抵達判準：用一個真實需求走完整流程，記錄 Miles 投入的時間與用量，結果 Miles 接受。

## Notes

- 本地圖含執行：決策票解完後，task 票直接動手改環境，不另開規劃。
- 不帶包袱：現行規則、skill、記憶卡都是輸入，不是限制。該重構、搬遷、刪除的直接做。
- 完整照 matt 的 skill 走一遍，先不調整；走完才決定哪裡要改（Miles 2026-11-11）。Sens 自己的 skill 只補 matt 沒有的領域知識與稽核。
- Miles 不在 Obsidian 讀檔，只在對話裡問。進度與結論一律在對話回報，檔案由代理控管；代理要能自行接續。
- 換對話一律用 matt 的 `handoff` 交接，不另寫任務書（Miles 2026-11-12）。兩種情況都適用：一張票做完換下一張；同一張票做到一半、對話接近上限。做法照 `~/.claude/plugins/cache/mattpocock/mattpocock-skills/1.3.2/skills/productivity/handoff/SKILL.md`：交接文件存到系統暫存資料夾，寫明建議載入的 skill，地圖、票、提交已有的內容不重抄、只寫路徑。開新對話時，`start_session` 的指令只寫交接文件的路徑與「讀它並接續」。
- 每個工作階段只解一張票（research 票除外），解完提交。
- 給 Miles 的建議寫四項：做法、建議、風險、預期結果。反例檢查在內部做，回覆不列反例段（Miles 2026-11-11）。
- 要不要開新對話由代理自行判斷並交接，不問 Miles。指標用 `mcp__ccd_session_mgmt__get_usage` 讀實際數字，每張票開工前與每個步驟結束時各讀一次：對話用量達 25 萬 token，做完手上這一步就交接；方案的 5 小時額度用到 85%，不再派新的子代理，先把狀態寫進檔案；一張票結案後，下一張票一律開新對話。
- Miles 的最終目標：只給需求，設計、Prototype、交付都由代理處理；他只會問「現在該做什麼」。
- 新對話開啟時，新對話把自己移出子對話，並封存上一則對話（Miles 2026-11-12）。上一則對話開著「保持電腦喚醒」時封存會被擋下，要請 Miles 關掉或自己封存。
- 移動對話（移出子對話）或開新對話時，把它放進與這項工作相同的側邊欄區段；本地圖的對話都放「工作流程優化」（Miles 2026-11-12）。
- 對話命名當成專案管理看（Miles 2026-11-12）。主線對話用專案名命名，票號放後面：「工作流程重置 - 票 NN」。不用票名開頭，因為執行時票會跳號。主線是正在解票的那一個對話，同一時間只有一個，Miles 問「現在該做什麼」就找它。旁支調研命名「調研・票 NN」。做完可封存的命名「已結案・票 NN 票名」。主線對話結案時把自己改成「已結案」，開新對話後把新對話命名為主線。用 `mcp__ccd_session_mgmt__set_session_title`。
- 已確定的事實：
  - 工作管理放本 repo 的 Markdown 檔，不放 Linear。Linear 只收交付給開發的內容。
  - Linear 的議題狀態不能改；PM team 建票會同步開一張 GitHub issue；方案是 Basic，沒有私有團隊。
  - Linear 現行交付結構：專案 → 里程碑 → Feature 票（PM team）→ 前端與後端 Task 子票。
  - Prototype 在 erp repo，用該 repo 的 skill 實作，不做前後端分離。
  - 主檢出停在 master，代理一律在工作樹作業。
- 以初始化整個專案的角度重構：先做「環境清場」，後面的決策票才開工，避免在舊環境上重工（Miles 2026-11-11）。
- Miles 的工作只有四件：維護 wiki、做 Prototype、開 Linear 議題給前後端追蹤、專案管理。整個工作流可以重構（Miles 2026-11-11）。
- erp 程式庫不動、不清場；Miles 只用其中製作 Prototype 與部署到 dev 的 skill。
- Miles 回報的痛點：wiki、Prototype、開發實作的資料對不齊；開發最常問介面操作規則（欄位防呆不一致、與後端給的資料不同）；開發的提交進不了規劃釐清；Miles 只認得商業層情境（正流程、逆流程），不知道測試的顆粒度；測試一跑半天。
- 順序：專案環境先處理好，再到應用。環境清場、環境相關的決策票、重寫環境在前；「現況同步」的試做與真實需求試跑在後（Miles 2026-11-12）。
- 調研既有做法時要讀完原始檔、完全理解後才評估，不只看簡介（Miles 2026-11-12）。
- 派工（任務書、子代理、新對話）要用資深 PM 的角度看這件工作：資深 PM 會怎麼做、在意什麼。不確定時先去找既有做法，不自己想（Miles 2026-11-12）。
- 調研要拆領域去找（例：議題管理、知識庫管理、BRD 撰寫），不找「整套工作流」的現成答案。每個人的工作流不同，但拆開後每一段都是已存在的領域知識（Miles 2026-11-12）。
- 商業需求走 matt 的流程進 wiki，不進記憶；同一件事只留一個家。環境的設置與去重要提前，不等到最後重寫（Miles 2026-11-12）。
- 操作手冊要持續維護，預計改到 GitBook；手冊相關的檔不清（Miles 2026-11-12）。
- 調研產出放 `research/`，每筆結論附網址與原文句；查不到就標未查證。
