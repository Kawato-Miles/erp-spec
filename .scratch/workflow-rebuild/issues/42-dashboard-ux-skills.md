| 步驟 | 來源 | 取用的內容 |

- 選 Ant Design 官方規範的理由：erp 的元件庫就是 Ant Design，規範講的是版型判斷，不涉及元件的程式介面，版本差異不影響。
- `office-web-ui-system` 只取結構規則。不取它的視覺風格（玻璃質感、藥丸頂欄），不加它的語意類別，不執行它的掃描腳本。`visual-language.md`、`locator-class-contract.md` 與掃描腳本主對話沒讀，不取用。
- 選版型的結果寫進交給 erp skill 的需求描述。erp skill 的第 1 步本來就由 PM 決定頁型，這一步等於替 Miles 先備好選項。

#### 證據：Prototype 現況

統計範圍是 erp 的 `(prototype)/` 目錄 258 個檔。數字是關鍵字命中的行數，代表量級，不是精確件數。

| 問題 | 現況 |
|------|------|
| 手寫字級 | 100 處。套用 erp 字體階層的只有 17 處 |
| 字級不在 erp 階層內 | 27 處：13px 有 20 處、11px 有 5 處、18px 與 22px 各 1 處。erp 階層只有 12、14、16、20、24 |
| 字重不在 erp 載入範圍內 | 600 有 2 處。erp 只載入 400、500、700 |
| 手寫字重 | 12 處，另有 28 處用元件屬性加粗。erp 只規定「標題用 700」 |
| 手寫色碼 | 25 處、24 種值。其中 `#1677ff`、`#ff4d4f`、`#fa8c16` 是 Ant Design 預設色，不是 erp 的色彩 |
| 狀態標籤的顏色 | 用了 14 種顏色名。約一半是語意色（成功、錯誤、進行中等），約一半是調色盤色（gold、cyan、geekblue、lime、purple 等） |
| 提示泡泡（Tooltip） | 261 處，其中欄位標籤旁的問號說明 63 處 |
| 提示超過 20 個字 | 55 處。最長的把整段業務規則寫進提示 |
| 輸入框灰字重複欄位名稱 | 86 處是「請輸入」或「請選擇」加欄位名 |

- 字級的例子：`orders/_components/detail/billing/ReconciliationPanel.js` 同一個檔有 7 處手寫 13px。
- 提示文字的例子：`production-floor/transfers/page.js` 的提示寫「建單時取自各條明細目的站點所屬的產線，改單不可改；之後任務改了目的站點，這張單也不跟著改。要改去處請作廢後從待轉交任務重新建單。」
- erp 的 `Designs.md` 第 4 節已寫「不要自訂 font-size」，第 8 節把手寫 font-size 列為禁止。字級問題的主因是既有規則沒有人檢查，不是缺規則。
- erp 沒有管提示文字的量。
- erp 對「什麼情境用哪一個」的規定：字級沒有；字重只有「標題用 700」；顏色有用色紀律（主色只有藍、狀態色只用於狀態、紫色只作點綴），但沒有「哪個業務狀態用哪個顏色」，也沒有「文字顏色四階各用在哪」。

#### 兩個來源對這兩個問題的規則

| 問題 | interface-design | Impeccable |
|------|-----------------|-----------|
| 字級選用 | 要代理自己挑一個比例算出字級（例：11、14、16、18、22、28）；層級要同時用字級、字重、顏色；要避開預設字型 | 後台介面用固定字級、單一字族、級距小；同一種角色在各畫面保持一致；一個畫面至多 3 至 4 個字級、2 至 3 個字重 |
| 字重選用 | 同一字級用字重分三層，用到 600（erp 沒有載入 600） | 一個畫面至多 2 至 3 種字重 |
| 顏色選用 | 文字顏色分四階，各有用途（內文、輔助、中繼資料、停用）；只用一個強調色；色盤要代理從產品的世界自己找 | 強調色只用在主要操作、目前選取、狀態指示；狀態用語要標準化；語意色要搭配文字或圖示 |
| 提示文字過多 | 沒有規則。只有一句「把畫面上每一句字當使用者讀一遍」 | 有。說明文字只回答使用者沒說出口的問題，不重述控制項；輸入框灰字是範例不是標籤；每件事只說一次；少見的細節收起來，要用才展開 |

#### 與 erp 既有規範的衝突

| 來源 | 衝突 |
|------|------|
| interface-design | 整體目標是做出與別人不同的視覺（原文：「no two interfaces should look the same.」）。要代理自訂字級、字型、間距數值、陰影、token 命名。erp 禁止手寫數值，字型與色彩由 Figma 控制。兩者方向相反 |
| Impeccable | 後台介面的規則大致與 erp 一致（沿用標準元件、一致優先）。下列幾句衝突：內文至少 16px（erp 是 14px，原文附例外條件）；「灰底加單一強調色」被評為不合格（erp 規定白、中性灰、單一藍）；評審的說明文件一項，情境提示越多分數越高，會讓代理加提示 |

#### 規則能不能只取文字

| 來源 | 結論 |
|------|------|
| interface-design | 可以。全部是文字檔，沒有程式 |
| Impeccable | 可以只取文字。整套裝起來就不行：主檔要求每個對話先執行啟動腳本，腳本會下載執行檔；字體檢查與評審兩個流程都要跑它的偵測程式 |

#### 採用方式

兩個來源都不安裝。

| 問題 | 做法 | 取自 |
|------|------|------|
| 字級選用 | erp skill 做完後，用指令搜尋本次改動裡的手寫字級與字重，有命中就退回重做。這一步是機械檢查，不靠代理自律 | erp 的 `Designs.md` 既有規則；票 20 的結論（零例外規則改用機械檢查） |
| 字級選用 | 畫面檢查清單加三條：同一種角色用同一級；一個畫面至多 3 至 4 級；先用字重與文字顏色分層級 | Impeccable 的 `operate`、`typeset`、`distill` |
| 字重與顏色選用 | 機械檢查加兩項：手寫字重、手寫色碼。畫面檢查清單加字重與顏色的條目（下一節） | erp 的 `Designs.md` 用色紀律；Impeccable 的 `operate`、`distill`；interface-design 的文字四階用途 |
| 提示文字過多 | 畫面檢查清單加禁止清單（下一節） | Impeccable 的 `clarify`、`distill` |

- interface-design 只取一句：文字顏色四階的用途，剛好對上 erp 已有的四階文字色。其餘不取用：字級、字重、色盤都要代理自訂數值，與 erp 衝突；提示文字沒有規則。它的「優先用專案既有元件」與 erp skill 已有的規則重複。
- Impeccable 的評審流程（`critique`）不取用。它的說明文件評分會獎勵多加提示，與 Miles 要禁止的事相反。
- 「哪種畫面角色用哪一級字」的對照表，erp 沒有，兩個來源也給不出來。票 11 從 erp 共用元件現行的用法整理，不自創。

#### 禁止清單草稿（待 Miles 看過）

畫面細節屬於 Miles 決定的領域。下列是草稿。

字級：

1. 不手寫字級與字重，只用 erp 字體階層的五級。
2. 同一種角色在所有頁面用同一級。
3. 一個畫面至多用 3 至 4 級。
4. 要分層級時，先用字重與文字顏色，不另加一級字。

字重：

1. 不手寫字重，只用 erp 字體階層附帶的 400、500、700。
2. 一個畫面至多用 2 至 3 種字重。

顏色：

1. 不手寫色碼，只用 erp 的色彩 token。
2. 藍色只用在主要操作、目前選取的項目、狀態指示，不拿來裝飾。
3. 狀態標籤只用語意色，不用調色盤色名。同一個狀態在所有頁面同色。
4. 文字顏色四階各有固定用途：內文、輔助說明、中繼資料、停用。
5. 顏色不單獨表達意思，要搭配文字或圖示。

提示文字：

1. 輸入框的灰字只放格式範例。不寫「請輸入」加欄位名稱。
2. 欄位旁的說明至多一句，只回答使用者此刻會問的問題。不重述欄位名稱。
3. 業務規則的全文不寫進畫面。規則留在 wiki 與操作手冊。
4. 圖示按鈕的提示只寫動作名稱。操作的後果只寫在破壞性操作的確認視窗。
5. 同一件事在同一個畫面只說一次。

未定的兩點：

- 顏色第 3 條需要一張「業務狀態對顏色」的對照表。語意色只有五種，訂單、工單、生產任務的狀態都超過五種。哪些狀態共用一色，要 Miles 決定。
- 提示文字第 3 條會拿掉現有的長提示。這些提示是代理把 wiki 規則搬進畫面的結果，使用者是否需要其中一部分，要 Miles 判斷。
