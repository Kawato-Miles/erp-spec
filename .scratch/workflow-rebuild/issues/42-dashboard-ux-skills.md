# 42：做 Prototype 時把關畫面組合的 UX skill

Type: research
Status: open
Blocked by: —

## Question

代理用 erp 的 `prototype-from-prompt` 做畫面時，常見的問題不是缺元件，是元件的組合方式錯。
有哪些既有的 skill 能把關後台管理介面（Dashboard）的畫面組合？

- Miles 點名的兩個：`https://github.com/pbakaus/impeccable`、`https://github.com/Dammyjay93/interface-design`（Miles 2026-11-13 更正：他要看的是 interface-design，不是 ui-skills）。
- 其他熱門的同類 skill。
- 每一個的內容是什麼、技術前提是什麼（erp 用 Next.js、Ant Design 5.22、styled-components）、有沒有談頁面層級的組合（列表頁、詳情頁、表單、資料表）。
- 哪些可以直接用，哪些與 erp 的元件庫或既有規範衝突。

評估分兩層（Miles 2026-11-13）：

| 層 | 要解決的問題 | Miles 的原話 |
|----|-------------|-------------|
| 版型 | 元件的組合方式錯 | 「很多時候不是缺少元件，是元件的組合方式錯」 |
| 細節 | 代理生成的畫面在細節上不合格，Miles 要禁止並解決 | 「Impeccable 應該不是針對後台版型，是指細節的地方，你現在生成的前端畫面，字及選用、提示文字過多等，都是我要禁止與解決的」 |

- Miles 2026-11-13 確認並擴大：「是字級沒錯，字重與顏色的選用也算」。細節層要查的項目：字級的選用、字重的選用、顏色的選用、提示文字過多。
- Impeccable 與 interface-design 用細節層的標準評估，不用「有沒有版型規則」評估。

實測比對（Miles 2026-11-13）：

- 原話：「基本上 Prototype 的製作，erp skill 都處理好了，我要針對的是稽核，實際比對安裝這兩個 skill 後的差異，其中 interface-design 應該是用在規劃與設計，把內容整理給 erp skill，Impeccable 是做完的稽核，依照稽核迭代，不限於文字，我記得他有很多模式可以用」「用這樣去評估你建議的方案兩者差異」。
- 重點在做完之後的稽核。畫面製作本身由 erp skill 負責，不評估。

| 方案 | 做畫面之前 | 做完之後 |
|------|-----------|---------|
| 甲：用兩個 skill | interface-design 做規劃與設計，把內容整理給 erp skill | Impeccable 稽核，依稽核結果迭代；用它的多種模式，不限於文字規則 |
| 乙：主對話先前的建議 | 版型選擇表 | 畫面檢查清單、禁止清單、機械檢查 |

- 比對要實際跑，不能只讀檔下結論。派子代理執行，主對話只當主控。
- Impeccable 的偵測程式納入實測（Miles 2026-11-14：「要包含」）。實測分兩輪，結果分開標明：
  - 第一輪不含偵測程式：照 Impeccable 主檔寫明的「啟動器不可用」流程跑。
  - 第二輪含偵測程式：Miles 自己在終端機安裝後補跑。代理不下載、不執行安裝；安裝位置用實測的 erp 本機工作樹，不裝進 erp 主檢出。

評估範圍與第二回實測（Miles 2026-11-14，看完第一回結果後）：

- 原話：「我在意的不只有你列的那四項目，還有整體的 UX，ERP UX 佈局很重要，例如：對系統的心智模型是否相同，編輯、修改這種用字就是很重要指引」「不用考慮鍵盤操作」。
- 評估範圍是整體 UX：佈局、使用者對系統的心智模型是否一致、操作用字是否一致，加上字級、字重、顏色、提示文字。鍵盤操作不列入。
- 原話：「我覺得用一個新的功能嘗試會比較準，一樣用甲乙兩個方式進行，且這時候或許可以用 matt 的試做流程，先不考慮測試與功能，快速用 erp skill 做畫面就好」。
- 第二回：挑一個還沒有 Prototype 的新功能，甲乙兩個方案各走一遍完整流程（規劃、用 erp skill 做畫面、稽核、迭代）。照 matt 的 `prototype`（用完即丟的驗證草稿）的做法，不管測試與功能，只求快速做出畫面。

## 緣由

Miles 2026-11-13：「我認為需要 Dashboard UX 的 Skill 納入考量，這樣用 erp skill 時，才能組合出正確的畫面，很多時候不是缺少元件，是元件的組合方式錯。」

## 限制

- erp 程式庫與 erp 的 skill 不動。新 skill 只能加在 Sens 這一側，在 erp skill 之前（選版型）與之後（檢查畫面）使用。
- 調研階段不安裝、不執行來源裡的任何檔案。

## 完成的樣子

- `research/42-dashboard-ux-skills.md`：每個 skill 附網址、檔案清單、原文句、技術前提、熱門程度、授權。
- 主對話讀完要採用的 skill 檔全文，再向 Miles 說明採用哪些、用在流程的哪一步。結論交票 09 與票 11。

- 用詞是 Miles 點名的重點，乙一個都沒抓到：禁止清單沒有管操作名稱與心智模型的條目。這是乙的缺口。
- 提示文字是差距最大的一類：乙抓到 17 個裡的 16 個，甲兩輪只抓到 3 至 4 個。
- 顏色類甲第二輪抓得多，多出來的主要是文字與標籤的對比不足。這些要自訂色才改得掉，erp 規定顏色只能用 Figma 產出的代號，所以甲自己攔下沒改。
- 四類以外甲抓得多：鍵盤操作與可及名稱、空白與錯誤狀態、同一個操作兩種叫法（列上按鈕叫「編輯」，對話框叫「修改轉交單」）。
- 偵測程式的貢獻：甲第二輪 38 項發現裡，偵測程式抓到 5 項，其餘 33 項是代理讀程式抓的。原始碼掃描對範圍內 8 個檔是 0 筆（它對 `.js` 只做文字比對）；字級與顏色的規則要讀 `DESIGN.md`，erp 的檔名是 `Designs.md`；字重與提示文字沒有偵測規則。渲染頁面掃描 23 筆，其中 P1 掃到的是登入頁。

#### 證據：Prototype 現況

統計範圍是 erp 的 `(prototype)/` 目錄 258 個檔。數字是關鍵字命中的行數，代表量級，不是精確件數。

| 問題 | 現況 |
|------|------|
| 手寫字級 | 100 處。套用 erp 字體階層的只有 17 處 |
| 字級不在 erp 階層內 | 27 處：13px 有 20 處、11px 有 5 處、18px 與 22px 各 1 處。erp 階層只有 12、14、16、20、24 |
| 字重不在 erp 載入範圍內 | 600 有 2 處。erp 只載入 400、500、700 |
| 手寫字重 | 12 處，另有 28 處用元件屬性加粗。erp 只規定「標題用 700」 |
| 手寫色碼 | 25 處、24 種值。其中 `#1677ff`、`#ff4d4f`、`#fa8c16` 是 Ant Design 預設色，不是 erp 的色彩 |
| 狀態標籤的顏色 | 用了 14 種顏色名。約一半是語意色（成功、錯誤、進行中等），約一半是調色盤色（gold、cyan、geekblue、lime、purple 等） |

- 字級的例子：`orders/_components/detail/billing/ReconciliationPanel.js` 同一個檔有 7 處手寫 13px。
- 提示文字的例子：`production-floor/transfers/page.js` 的提示寫「建單時取自各條明細目的站點所屬的產線，改單不可改；之後任務改了目的站點，這張單也不跟著改。要改去處請作廢後從待轉交任務重新建單。」
- erp 的 `Designs.md` 第 4 節已寫「不要自訂 font-size」，第 8 節把手寫 font-size 列為禁止。字級問題的主因是既有規則沒有人檢查，不是缺規則。
- erp 沒有管提示文字的量。
- erp 對「什麼情境用哪一個」的規定：字級沒有；字重只有「標題用 700」；顏色有用色紀律（主色只有藍、狀態色只用於狀態、紫色只作點綴），但沒有「哪個業務狀態用哪個顏色」，也沒有「文字顏色四階各用在哪」。

#### 兩個來源對這兩個問題的規則

| 問題 | interface-design | Impeccable |
|------|-----------------|-----------|
| 字級選用 | 要代理自己挑一個比例算出字級（例：11、14、16、18、22、28）；層級要同時用字級、字重、顏色；要避開預設字型 | 後台介面用固定字級、單一字族、級距小；同一種角色在各畫面保持一致；一個畫面至多 3 至 4 個字級、2 至 3 個字重 |
| 字重選用 | 同一字級用字重分三層，用到 600（erp 沒有載入 600） | 一個畫面至多 2 至 3 種字重 |
| 顏色選用 | 文字顏色分四階，各有用途（內文、輔助、中繼資料、停用）；只用一個強調色；色盤要代理從產品的世界自己找 | 強調色只用在主要操作、目前選取、狀態指示；狀態用語要標準化；語意色要搭配文字或圖示 |
| 提示文字過多 | 沒有規則。只有一句「把畫面上每一句字當使用者讀一遍」 | 有。說明文字只回答使用者沒說出口的問題，不重述控制項；輸入框灰字是範例不是標籤；每件事只說一次；少見的細節收起來，要用才展開 |

#### 與 erp 既有規範的衝突

| 來源 | 衝突 |
|------|------|
| interface-design | 整體目標是做出與別人不同的視覺（原文：「no two interfaces should look the same.」）。要代理自訂字級、字型、間距數值、陰影、token 命名。erp 禁止手寫數值，字型與色彩由 Figma 控制。兩者方向相反 |
| Impeccable | 後台介面的規則大致與 erp 一致（沿用標準元件、一致優先）。下列幾句衝突：內文至少 16px（erp 是 14px，原文附例外條件）；「灰底加單一強調色」被評為不合格（erp 規定白、中性灰、單一藍）；評審的說明文件一項，情境提示越多分數越高，會讓代理加提示 |

#### 規則能不能只取文字

| 來源 | 結論 |
|------|------|
| interface-design | 可以。全部是文字檔，沒有程式 |
| Impeccable | 可以只取文字。整套裝起來就不行：主檔要求每個對話先執行啟動腳本，腳本會下載執行檔；字體檢查與評審兩個流程都要跑它的偵測程式 |

#### 採用方式

兩個來源都不安裝。

| 問題 | 做法 | 取自 |
|------|------|------|
| 字級選用 | erp skill 做完後，用指令搜尋本次改動裡的手寫字級與字重，有命中就退回重做。這一步是機械檢查，不靠代理自律 | erp 的 `Designs.md` 既有規則；票 20 的結論（零例外規則改用機械檢查） |
| 字級選用 | 畫面檢查清單加三條：同一種角色用同一級；一個畫面至多 3 至 4 級；先用字重與文字顏色分層級 | Impeccable 的 `operate`、`typeset`、`distill` |
| 字重與顏色選用 | 機械檢查加兩項：手寫字重、手寫色碼。畫面檢查清單加字重與顏色的條目（下一節） | erp 的 `Designs.md` 用色紀律；Impeccable 的 `operate`、`distill`；interface-design 的文字四階用途 |
| 提示文字過多 | 畫面檢查清單加禁止清單（下一節） | Impeccable 的 `clarify`、`distill` |

- interface-design 只取一句：文字顏色四階的用途，剛好對上 erp 已有的四階文字色。其餘不取用：字級、字重、色盤都要代理自訂數值，與 erp 衝突；提示文字沒有規則。它的「優先用專案既有元件」與 erp skill 已有的規則重複。
- Impeccable 的評審流程（`critique`）不取用。它的說明文件評分會獎勵多加提示，與 Miles 要禁止的事相反。
- 「哪種畫面角色用哪一級字」的對照表，erp 沒有，兩個來源也給不出來。票 11 從 erp 共用元件現行的用法整理，不自創。

#### 禁止清單草稿（待 Miles 看過）

畫面細節屬於 Miles 決定的領域。下列是草稿。

字級：

1. 不手寫字級與字重，只用 erp 字體階層的五級。
2. 同一種角色在所有頁面用同一級。
3. 一個畫面至多用 3 至 4 級。
4. 要分層級時，先用字重與文字顏色，不另加一級字。

字重：

1. 不手寫字重，只用 erp 字體階層附帶的 400、500、700。
2. 一個畫面至多用 2 至 3 種字重。

顏色：

1. 不手寫色碼，只用 erp 的色彩 token。
2. 藍色只用在主要操作、目前選取的項目、狀態指示，不拿來裝飾。
3. 狀態標籤只用語意色，不用調色盤色名。同一個狀態在所有頁面同色。
4. 文字顏色四階各有固定用途：內文、輔助說明、中繼資料、停用。
5. 顏色不單獨表達意思，要搭配文字或圖示。

提示文字：

1. 輸入框的灰字只放格式範例。不寫「請輸入」加欄位名稱。搜尋框例外：照 erp 配方，灰字列出可搜尋的條件。
2. 欄位旁的說明至多一句，只回答使用者此刻會問的問題。不重述欄位名稱。
3. 業務規則的全文不寫進畫面。規則留在 wiki 與操作手冊。
4. 圖示按鈕的提示只寫動作名稱。操作的後果只寫在破壞性操作的確認視窗。
5. 同一件事在同一個畫面只說一次。

未定的兩點：

- 顏色第 3 條需要一張「業務狀態對顏色」的對照表。語意色只有五種，訂單、工單、生產任務的狀態都超過五種。哪些狀態共用一色，要 Miles 決定。
- 提示文字第 3 條會拿掉現有的長提示。這些提示是代理把 wiki 規則搬進畫面的結果，使用者是否需要其中一部分，要 Miles 判斷。
