## Answer

Miles 於 2026-11-12 確認定案。例子都取自票 17 的需求單實測。

1. 正本：正本是唯一可以改的地方。商業邏輯的正本是 wiki。畫面與動線的正本是 Prototype。後端的介面契約（`sensationsprint/api-docs`）是開發實作的現況，只讀、不改、不當來源。
2. 現況同步：代理讀該領域的 wiki 卡、後端契約與變更紀錄、正式前端的驗證檔（`packages/shared/services/<模組>/schemas.js`），經 GitHub 讀取，不動本機 erp 與後端資料夾。現行規則「規劃只讀 Prototype」作廢。
   - 時點有兩個。規劃功能時：Miles 給需求之後、開始釐清之前，代理自動做。驗收之前：前後端都做完、專案到 Ready for UAT，Miles 問「現在該做什麼」時代理查 Linear 後做；先比對欄位與可選值，Miles 只驗情境。
   - 差異分三類。技術命名與型別直接採用後端（例：印件交期用後端的 `delivery_date`）。wiki 有寫而開發不同，開票給開發（例：wiki 寫帳務公司「已評估成本前可改」，後端沒有擋）。wiki 沒寫或可選值不同，集中問 Miles（例：帳務公司 wiki 2 家、後端 4 家；數量 wiki 沒寫範圍、後端要求大於 0）。
   - 程式能比的是欄位、狀態與可選值、操作是否存在。規則的邏輯（轉換條件、算式、權限）由代理讀後端程式碼判讀，判讀結果附程式位置。
3. 欄位防呆：wiki 實體卡的欄位表不重做，只補數值範圍、長度、格式、明列的可選值。怎麼補併入票 06。
4. Linear 議題管理：
   - 專案層：專案是一個有結果、會結束的需求。模組首次交付算一個專案，里程碑是需求主題。專案還沒 Release 時，需求改變留在原專案處理，多出來的功能加一張 Feature 進對應的里程碑。專案已 Release 時，原專案不動，開新專案，名稱照「模組 - 這次改什麼」，描述連回原專案。
   - 票層（Feature 與 Task 各自適用）：還沒開工，直接改票文、不留言。開發中，改票文，另加一則「原本／現行」對照表留言。已完成或已上線，原票不動，開新票連回原票。開發沒照票做，也照此處理。票文一律整段改寫，不加補充段。
   - Task：只有原 Task 已完成才多開一張 Task，掛在同一張 Feature 下並連回原 Task。整張 Feature 已完成就開新 Feature 與它的 Task。
   - 開發的提交：不要求開發在提交寫票號（實測前端 6%、後端 23%）。代理不逐筆讀提交，改讀後端的介面契約與變更紀錄，用在第 2 項的兩個時點。
   - 票文寫多細、怎麼從 wiki 產生，另開票 24。
5. Miles 只看商業層情境（情境卡的正流程、逆流程）。測試分層與提速併入票 07。
6. 跨需求追蹤與交接併入票 10。範圍已定：每個需求從 Miles 給需求到 Release，含 wiki 維護；開發中的進度直接讀 Linear，不另記一份。不含 Linear 上不是本環境開出去的專案。
